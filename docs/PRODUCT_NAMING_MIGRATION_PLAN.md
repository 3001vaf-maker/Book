# Product Naming Migration Plan

**Проект:** текущий SaaS с рабочим техническим названием `Book`  
**Статус:** PLANNED / НЕ НАЧИНАТЬ ДО ОТДЕЛЬНОГО РЕШЕНИЯ  
**Цель:** подготовить безопасную замену временного названия `Book` на будущее коммерческое название без массового глобального Replace, без поломки production, Amvera, GitHub, БД, браузерного состояния, документов и интеграций.

---

## 0. Обязательное правило до начала переименования — NAMING FREEZE

До утверждения нового коммерческого названия запрещено создавать новые технические зависимости от слова `Book`.

### Запрещено добавлять новое

- новые функции и методы вида `getBook...`, `setBook...`, `loadBook...`, `canUseBook...`;
- новые переменные/константы вида `BOOK_*`, если это не временное отображаемое имя бренда;
- новые поля БД/Prisma вида `...Book`, например аналоги `isOwnerBook`;
- новые SQL-функции, triggers, indexes, constraints и другие DB-объекты с префиксом `book_`;
- новые browser-storage ключи вида `book.*`;
- новые browser/custom events вида `book:*`;
- новые технические namespace с `book`;
- новые внутренние имена Docker volumes, database/user/service names с `book`;
- новые тестовые логины, секреты, fixtures и staging identifiers с `book`, если можно использовать нейтральное имя;
- новые API/архитектурные сущности, где `Book` обозначает не бренд, а Tenant / Platform / Account / Workspace / Product;
- новые файлы и папки с `BOOK_*`, если название относится к архитектуре, а не к историческому документу;
- новые жёстко прописанные зависимости от `book.va-tools.ru`, если можно использовать существующий environment/config слой.

### Разрешено временно

`Book` можно использовать только как текущее отображаемое название продукта в пользовательском тексте, если без названия текст сейчас невозможен.

Примеры:
- `<title>Book</title>`;
- «Открыть Book»;
- текущие юридические документы существующей редакции;
- историческая документация и уже применённые migrations.

### Правило для нового кода

Если новое имя относится к архитектуре, использовать нейтральные понятия:

- `Tenant`
- `Platform`
- `Product`
- `Account`
- `Workspace`
- `Access`
- `Capability`
- конкретное имя доменной сущности

Новый коммерческий бренд **не должен становиться новым техническим namespace**.

---

# Правила выполнения будущего переименования

1. Никакого глобального `Book -> НовоеИмя`.
2. Один слой = одно отдельное задание.
3. Один чат получает только одно законченное задание.
4. Перед изменением фиксируется полный список затрагиваемых мест этого слоя.
5. Старый контракт не удаляется, пока не проверена миграция, если от него зависят существующие данные/пользователи.
6. После каждого слоя выполняются автоматические проверки и ручная проверка соответствующего поведения.
7. Следующий слой не начинается, пока предыдущий не имеет статус `VERIFIED`.
8. Никаких попутных архитектурных переделок.
9. Старые применённые Prisma migrations не редактировать.
10. Подписанные юридические документы прошлых редакций не переписывать.
11. Production-инфраструктуру, GitHub и Amvera менять только отдельными согласованными шагами.
12. После каждого этапа обновлять этот документ: `PLANNED -> IN PROGRESS -> VERIFIED -> LEGACY REMOVED`, где применимо.

# Задание 1. Видимое название продукта

## Цель
Заменить только пользовательское отображаемое имя `Book` на утверждённый бренд.

## Типичные места
- `<title>Book</title>`;
- `Book Admin`;
- «Мой Book»;
- «Открыть Book»;
- «Book временно недоступен»;
- onboarding;
- invite;
- Telegram-тексты;
- admin UI;
- client UI.

## Не входит
- функции;
- переменные;
- storage;
- events;
- БД;
- домены;
- GitHub;
- Amvera;
- юридические документы.

## Проверка
- основное приложение;
- клиентский интерфейс;
- admin;
- API/служебные страницы, где есть UI;
- Telegram-visible тексты;
- поиск остаточных пользовательских строк.

## Готово когда
Новый бренд отображается пользователю, а техническое поведение не изменилось.

# Задание 5. Browser storage namespace

## Цель
Без потери существующего состояния заменить технические storage keys.

## Известные примеры
- `book.auth.token`;
- `book.account.token.*`;
- `book.account.email.*`;
- `book.people.sort`;
- `book.onboarding.*`;
- `book:workplace-context`.

## Обязательная миграционная схема
1. Ввести новый нейтральный key.
2. Читать новый key.
3. При его отсутствии читать legacy `book.*`.
4. Перенести значение в новый key.
5. Проверить существующий браузерный профиль.
6. Только отдельным будущим шагом удалить legacy support.

## Запрещено
Просто переименовать строки и тем самым разлогинить пользователей или потерять UI/session state.

# Задание 11. GitHub repository / Amvera deployment connection

## Цель
Без остановки deployment переименовать repository `3001vaf-maker/Book`.

## Критическая зависимость
Amvera связана с GitHub repository и `main`.

Переименование GitHub нельзя выполнять как изолированную косметическую операцию.

## Метод
1. Зафиксировать текущий production commit.
2. Зафиксировать текущую GitHub -> Amvera configuration.
3. Переименовать repository.
4. Немедленно проверить repository URL/remotes/integrations.
5. Проверить Amvera source connection.
6. При необходимости обновить repository reference в Amvera.
7. Сделать безопасный docs/test commit через обычный release flow.
8. Подтвердить, что Amvera получила именно новый commit.
9. Проверить production deployment.
10. Проверить четыре production domains.

## Готово когда
GitHub и Amvera снова подтверждённо смотрят на один и тот же `main` commit и production работает.

# Порядок выполнения

Рекомендуемый порядок:

`1 -> 2 -> 4 -> 6 -> 5 -> 7 -> 8 -> 3 -> 9 -> 10 -> 11 -> 12`

Почему:
- сначала изолируется бренд от пользовательского UI;
- затем очищается активный код;
- затем мигрируются state/contracts;
- затем данные и инфраструктура;
- GitHub/Amvera меняются почти в конце;
- юридический контур меняется только после окончательного утверждения бренда.

# Статусы

Использовать только:

- `PLANNED` — запланировано, не начато;
- `IN PROGRESS` — выполняется только этот слой;
- `VERIFIED` — изменение выполнено и проверено;
- `LEGACY REMOVED` — старый compatibility layer удалён после отдельной проверки;
- `BLOCKED` — слой нельзя продолжать до устранения конкретной зависимости.

# Текущее решение

На момент создания этого документа:

- название `Book` остаётся временным;
- переименование **не начинается**;
- существующий код не переписывается ради названия;
- действует `NAMING FREEZE`: новые технические зависимости от слова `Book` не создавать;
- новые архитектурные имена должны быть нейтральными;
- этот план хранится до момента утверждения окончательного названия продукта.

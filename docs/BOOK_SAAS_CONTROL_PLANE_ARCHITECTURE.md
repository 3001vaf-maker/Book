# Book SaaS — архитектура управляющего слоя

Статус: утверждено владельцем продукта.

## 1. Базовый принцип

Один `Tenant` = один персональный Book одного частного мастера.

Book мастера остается его личным рабочим инструментом. Клиенты, календарь, журнал, настройки, рабочие пространства и другие бизнес-данные одного мастера не смешиваются с данными другого мастера.

Салон, сотрудники внутри одного Book, общий календарь салона, общий журнал и сеть филиалов сейчас не проектируются. Это будущие надстройки.

## 2. Существующий Book владельца продукта

Первый существующий Book остается без переноса и копирования.

В управляющей панели он отображается отдельно как `Мой Book`, но технически остается обычным Tenant.

Для него действуют те же механизмы доступов и лимитов, что и для Book других мастеров. Поэтому владелец платформы может отключать себе отдельные разделы и бизнес-функции.

## 3. Control Plane

Поверх персональных Book создается отдельный управляющий слой SaaS — `Control Plane`.

Он не владеет бизнес-данными мастеров. Он управляет только:

- регистрацией мастеров;
- состоянием Book;
- тарифами;
- доступными возможностями;
- индивидуальными исключениями;
- числовыми лимитами.

Admin-интерфейс является отдельным desktop-сайтом с левым меню, верхним toolbar и большой рабочей областью. Он не наследует мобильный shell Book шириной 390 px.

## 4. Capability — единица доступа

Все управляемые возможности Book описываются единым каталогом `Capability`.

Capability может быть двух типов:

1. `BOOLEAN` — включено / выключено.
2. `LIMIT` — числовой лимит или без ограничения.

Примеры ключей:

- `clients.access`
- `calendar.access`
- `journal.access`
- `chat.access`
- `workplaces.max`
- будущие внутренние возможности модулей, например `finance.analysis`.

Конкретный модуль не должен знать название тарифа. Он проверяет только итоговое право или лимит.

## 5. Тарифы

Тариф — шаблон набора Capability.

Тариф не прошивается внутрь Клиентов, Календаря, Журнала, Финансов или других доменов.

Схема разрешения права:

1. индивидуальное исключение конкретного Tenant;
2. значение из тарифа;
3. системное значение Capability по умолчанию.

Это позволяет менять состав тарифов без переписывания Book и отдельно выдавать конкретному мастеру дополнительное право или другой лимит.

## 6. Поведение при отсутствии доступа

Отключенная возможность должна блокироваться на двух уровнях.

### UI

Пользователь не видит:

- папку;
- кнопку;
- пункт меню;
- экран;
- действие.

### Server

Сервер не выполняет закрытую команду и не отдает закрытые данные даже при ручном обращении к API.

Скрытие только в интерфейсе не считается защитой.

## 7. Лимиты

Лимиты являются серверными правилами, а не только UI-подсказкой.

Пример:

`workplaces.max = 3`

После трех рабочих пространств сервер запрещает создать четвертое. Интерфейс одновременно не предлагает недоступное действие.

Для `LIMIT` значение `null` означает `без ограничения`.

## 8. Регистрация нового мастера

Свободная регистрация в первой версии не используется.

Новый мастер создается владельцем платформы из Admin.

Сценарий:

1. Admin вводит имя, email, тариф и при необходимости индивидуальные лимиты/исключения.
2. В одной транзакции создаются пустой Tenant, SaaS-настройка Tenant и приглашение.
3. Мастер получает ссылку-приглашение.
4. Мастер создает пароль.
5. Создается или переиспользуется `User` по email.
6. Создается `Membership` этого User в созданном Tenant с ролью `OWNER`.
7. Приглашение помечается принятым.
8. Мастер входит в свой персональный Book.

Мастер не видит чужие Tenant и не получает доступ к Admin.

## 9. Платформенный администратор

Права владельца SaaS не должны смешиваться с `MembershipRole` внутри Book.

Для этого вводится отдельная сущность `PlatformAdmin`, связанная с существующим `User`.

Пользователь может одновременно:

- быть владельцем своего персонального Book через `Membership`;
- быть администратором всей платформы через `PlatformAdmin`.

## 10. Новые серверные сущности

Над текущей схемой добавляются:

- `PlatformAdmin` — кто имеет доступ к Admin;
- `Capability` — каталог возможностей и лимитов;
- `Plan` — тариф;
- `PlanCapability` — состав тарифа;
- `TenantAccess` — состояние SaaS конкретного Book, выбранный тариф и признак `Мой Book`;
- `TenantCapabilityOverride` — индивидуальное исключение конкретного Book;
- `MasterInvitation` — приглашение нового мастера.

Существующие `Tenant`, `User`, `Membership`, `Profile`, `WorkspaceState` и бизнес-домены не заменяются и не дублируются.

## 11. Безопасное внедрение

Внедрение выполняется поэтапно.

### Этап 1

Добавить новые SaaS-сущности в БД. Никакие текущие экраны и API Book еще не проверяют Capability. Поведение существующего Book не меняется.

### Этап 2

Добавить серверный resolver итоговых прав и лимитов. Пока он только умеет читать настройки и не блокирует существующий Book.

### Этап 3

Заполнить каталог Capability и назначить существующему `Мой Book` значения, сохраняющие текущее поведение.

### Этап 4

Подключать проверки по одному модулю: сначала UI, затем соответствующий server guard/service rule, с регрессиями Check Book.

### Этап 5

Добавить Admin desktop UI и сценарий приглашения мастеров.

## 12. Неприкосновенные правила Book

- бизнес-данные остаются server-owned;
- существующие Core-домены не дублируются;
- один объект — один владелец — одна реализация;
- Admin не становится владельцем данных Клиентов, Календаря, Журнала и других доменов;
- `main` не используется как среда разработки;
- изменения проходят `feature/* -> PR to staging -> Check Book -> staging verification -> release PR to main`.

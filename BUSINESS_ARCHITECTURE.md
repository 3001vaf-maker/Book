# BUSINESS_ARCHITECTURE

Нормативный бизнес-слой приложения. Этот файл отвечает не за геометрию UI, а за то, **какие рабочие поверхности существуют, какие возможности доступны внутри них и когда пользователь вообще должен их видеть**.

UI-геометрия и визуальные владельцы определяются `UI_ALPHABET.md`. Технические ограничения проекта определяются `PROJECT_STATE.md`.

---

## 1. Главный принцип

Приложение строится не вокруг профессии, а вокруг бизнес-действий.

Профессия/сфера деятельности используется только как стартовый пресет. Реальная выдача интерфейса определяется тем, **как конкретный предприниматель работает**.

Наличие функции в системе **не означает наличие отдельной F-карточки**.

Пример:
- функция `Продажа` существует универсально;
- у магазина `Продажи` могут быть основной F-рабочей поверхностью;
- у специалиста по записи отдельной F `Продажи` может не быть: продажа товара выполняется из события Журнала или из A-меню Журнала;
- складское и финансовое последствия такой продажи всё равно создаются общими механизмами.

---

## 2. Четыре уровня бизнес-архитектуры

### F — родительская рабочая папка

F допускается только если у неё есть самостоятельный бизнес-смысл и пользователь реально может сказать: «сейчас я иду сюда работать / управлять этим доменом».

F не создаётся только потому, что в системе появилась новая сущность или функция.

### E — самостоятельный инструмент внутри крупного F-домена

E используется, когда внутри одного бизнес-домена есть несколько самостоятельных рабочих инструментов.

Подтверждённые примеры:
- `Финансы` → `Касса`, `ДДС`, `Z-отчёт`;
- `Склад` → `Остатки`, `Движения`, `Заказ поставщику`, `Инвентаризация`.

### Режим / представление

Режим не является E. Он показывает или обрабатывает те же данные другим способом.

Пример:
- `Журнал` → День / Месяц / Список — один F и одни события, а не три E.

### Вложенная сущность / функция

Не F и не E. Живёт внутри рабочего контура и вызывается там, где нужна.

Примеры:
- рабочее пространство внутри Профиля;
- этап заказа;
- продажа внутри события Журнала;
- предоплата внутри Заказа;
- группа и посещение внутри соответствующего рабочего процесса;
- расход материалов при выполнении услуги;
- возврат по конкретной продаже.

---

## 3. Capability ≠ F

`Capability` — возможность системы. Она может быть доступна в нескольких рабочих контурах и не иметь собственной карты.

Обязательное правило:

> Пользователь не должен вручную переносить одну бизнес-операцию между несколькими F.

Если основная работа выполняется в Журнале, текущая операция должна завершаться из Журнала. Финансы, Склад, Контакты и другие домены получают последствия автоматически либо через вложенное действие, не заставляя пользователя переключаться между карточками.

Примеры:

### Специалист по записи

Основной F: `Журнал`.

Из Журнала он может:
- выполнить услугу;
- добавить товар;
- сделать отдельную продажу без записи через A-меню;
- привязать продажу к человеку или оставить обезличенной;
- принять оплату;
- породить расход материалов;
- завершить событие.

Отдельный F `Продажи` не обязателен.

### Магазин

Основной F: `Продажи`.

Рабочий цикл:
`товар → количество → покупатель необязательно → скидка → оплата → следующий`.

Здесь `Продажи` — рабочая поверхность, а не только capability.

---

## 4. Главный рабочий контур

Для каждой конфигурации пользователя должен быть определён `primary workspace` — F, в которой человек проводит основную часть рабочего дня и которая может открываться по умолчанию.

Предварительная классификация:

| Модель деятельности | Основной рабочий F |
|---|---|
| услуги по предварительной записи | Журнал |
| индивидуальное обучение / коучинг по времени | Журнал |
| розничная торговля | Продажи |
| проектная / заказная работа | Заказная работа — точное имя F ещё не зафиксировано |
| изготовление под заказ | Заказная работа — точное имя F ещё не зафиксировано |
| гостиница / аренда ресурса | Бронирования — точное имя F ещё не зафиксировано |
| серийное производство | требует отдельного решения; F Производство пока не утверждён |

У пользователя может быть более одного рабочего контура только если у его бизнеса действительно есть несколько независимых ежедневных процессов.

---

## 5. Классы F по назначению

Это бизнес-классификация, а не отдельная UI-геометрия.

### Рабочие F

Поверхности, в которых совершается основная ежедневная операция:
- Журнал;
- Продажи — если торговля является основным контуром;
- Заказная работа — кандидат;
- Бронирования ресурсов — кандидат;
- Производство — кандидат только для самостоятельного производственного контура.

### Управляющие / обзорные F

Нужны для просмотра и управления данными, но не должны заставлять пользователя завершать в них каждую текущую операцию:
- Контакты;
- Финансы;
- Склад;
- Лояльность.

### Конфигурационные F

Используются реже, в основном для настройки модели работы:
- Профиль;
- Сервис;
- График — только для управления бронируемой доступностью;
- Настройки.

---

## 6. Условная видимость и развитие пользователя

Функция может существовать архитектурно, но не показываться пользователю до необходимости.

Правило:

> Сложность интерфейса появляется только вслед за реальной сложностью бизнеса.

Примеры:
- одно рабочее пространство → никаких селекторов «все пространства» и «общий график»;
- второе пространство появилось → появляется управление несколькими пространствами;
- склад не ведётся → F Склад может быть скрыт;
- пользователь начал учитывать материалы → Склад включается без смены типа аккаунта;
- нет онлайн-записи → соответствующие настройки не показываются;
- нет групповой работы → групповые параметры не показываются;
- нет заказов → заказные статусы и этапы не показываются.

Скрытие F не удаляет capability из архитектуры и не создаёт отдельный «тип аккаунта».

---

## 7. График, режим работы и сроки — разные сущности

### F `График`

Предназначен только для управления **доступностью человека/исполнителя для бронирования времени**.

Примеры, где F логичен:
- парикмахер;
- коуч;
- репетитор;
- массажист.

### Режим работы пространства

Свойство рабочего пространства, а не F `График`.

Примеры:
- магазин 10:00–21:00;
- гостиница 24/7;
- мастерская 09:00–18:00;
- отдельные выходные/исключения.

Если у бизнеса одно пространство и нет причины выбирать между пространствами, пользователь не должен видеть понятия «общий график» или «все пространства».

### Срок / дедлайн

Свойство Заказа, Этапа или другой длительной работы. Не относится к F `График`.

---

## 8. Журнал — один F, разные контракты события

Запрещено создавать разные архитектурные Журналы по профессиям.

Есть один F `Журнал`, одна навигация и общие режимы День / Месяц / Список.

Различается **контракт события**.

Событие должно определять как минимум:
- источник / связанный объект;
- тип действия;
- участников;
- дату/время;
- результат;
- что означает завершение;
- какие дополнительные данные нужны при выполнении.

Примеры:

### Услуга специалиста

Событие связано с записью.

Завершение может означать:
- услуга выполнена;
- расчёт;
- оплата;
- списание материалов;
- закрытие записи.

### Замер

Событие связано с Заказом/Этапом.

Результат:
- размеры;
- фото;
- заметка;
- следующий шаг.

Завершение события завершает только замер, а не весь Заказ.

### Выезд архитектора

Результат:
- заметка;
- фото/файлы;
- решение;
- следующий шаг.

Завершение фиксирует факт выезда и не закрывает Проект/Заказ.

### Занятие

Результат может включать:
- участников;
- посещение;
- тему;
- заметку.

Завершение означает завершение занятия, а не курса/абонемента.

## 9. Универсальные capabilities, которые не требуют отдельной F

Ниже — системные возможности. Наличие capability само по себе не даёт права создавать новую F/E.

- Продажа как операция;
- отдельная продажа без записи;
- привязка продажи к Контакту или обезличенная продажа;
- возврат / частичный возврат;
- Событие;
- Этап;
- дедлайн;
- повторяемость;
- группа;
- посещение;
- предоплата;
- план платежей;
- частичная оплата;
- дополнительная работа;
- изменение состава/стоимости заказа;
- адрес / несколько точек заказа;
- доставка;
- депозит / залог;
- фактическое время работы;
- расход материалов;
- резерв материала/товара;
- состояние ресурса;
- выдача / возврат ресурса;
- абонемент / право / подписка;
- рецептура / спецификация;
- файлы / фото / размеры / заметки результата.

## 10. Склад — не только продажи

Склад используется минимум в трёх сценариях:

1. **Товар для продажи** — шампунь, одежда, готовый товар.
2. **Материал для выполнения работы** — краситель, оксид, ткань, расходник.
3. **Компонент производства** — сырьё, упаковка, полуфабрикат.

Поэтому отсутствие F `Продажи` не означает отсутствие необходимости в Складе.

Пример развития специалиста:
- сначала он оказывает услугу без учёта материалов;
- затем включает Склад;
- связывает услугу с расходуемыми материалами;
- после завершения услуги движение Склад создаётся из рабочего контура Журнала;
- сам Журнал при этом не меняется на другой рабочий контур.

## 11. Найденные недостающие бизнес-домены

### Продажи

Capability обязателен универсально для торговой операции.

Отдельный F `Продажи` нужен только когда продажа является основным самостоятельным рабочим контуром.

### Смета + Заказ

Смета и Заказ — разные сущности:
- Смета может существовать до принятия обязательства;
- из согласованной Сметы может возникнуть Заказ;
- после согласования изменения не должны молча переписывать исходную договорённость.

Пока не утверждено, должны ли `Сметы` и `Заказы` быть E одного родительского F. Создание двух отдельных F без отдельного решения запрещено.

### Бронируемый ресурс

Нужна базовая сущность `Resource` для объектов, которые не расходуются после использования:
- номер гостиницы;
- квартира;
- кабинет;
- зал;
- автомобиль;
- оборудование.

Ресурс может бронироваться на период и иметь состояние.

`Resource` не является Складом и не является Рабочим пространством.

Точное пользовательское имя F/E для бронирования пока не зафиксировано.

### Производство

Нужна поддержка преобразования материалов в готовую продукцию:
`материалы → операция производства → готовая продукция`.

Отдельный F `Производство` допускается только если производство является самостоятельным рабочим контуром. Для индивидуального изготовления внутри Заказа отдельный F не требуется.

## 12. Предварительные бизнес-модели для аудита

Архитектура должна покрывать без создания отдельного приложения под профессию:

- услуга по предварительной записи;
- услуга без предварительной записи;
- розничная торговля;
- интернет-заказ / товар под заказ;
- индивидуальное изготовление;
- проектная работа;
- выездная работа;
- индивидуальное обучение;
- групповое обучение;
- регулярное обслуживание;
- абонемент / подписка;
- прокат;
- посуточная аренда;
- гостиница;
- долгосрочная аренда;
- серийное производство;
- еда/изготовление на заказ;
- доставка;
- агентская/посредническая работа;
- работа с учётом фактического времени;
- живая очередь.

Новая модель деятельности сначала проверяется против существующих F/E/capabilities. Новая F допускается только если существующий основной рабочий контур объективно не может её обслужить.

## 13. Матрица, обязательная перед регистрацией

До переработки регистрации для каждой модели деятельности необходимо заполнить:

| Поле | Смысл |
|---|---|
| Основной рабочий F | где человек проводит рабочий день |
| Старт операции | что запускает работу |
| Встроенные capabilities | что выполняется без ухода из основного F |
| Завершение операции | что означает «готово» |
| Автоматические последствия | Финансы / Склад / История / Контакты |
| Управляющие F | куда ходят смотреть/управлять |
| Конфигурационные F | что настраивают редко |
| Условные F | что появляется только при развитии бизнеса |
| Лишние F | что этому типу работы показывать запрещено |

Регистрация проектируется только после заполнения этой матрицы.

Регистрация не должна спрашивать пользователя названия наших внутренних F/E. Она должна спрашивать понятные действия бизнеса и по ответам выдавать минимальный набор рабочих поверхностей.

## 14. Правила, блокирующие возврат к CRM-перегрузке

1. Нельзя показывать сущность только потому, что она технически существует.
2. Нельзя создавать F для функции, которая естественно выполняется внутри основного рабочего контура.
3. Нельзя заставлять пользователя завершать одну операцию последовательным переходом через Журнал → Продажи → Склад → Финансы.
4. Нельзя создавать профессиональные копии одного F (`Журнал парикмахера`, `Журнал архитектора`, `Журнал педагога`). Меняется контракт данных/действий, а не владелец F.
5. Нельзя показывать управление множественностью до появления множественности: одно пространство, одна касса, один ресурсный набор и т. п. не должны порождать лишние селекторы.
6. Нельзя жёстко привязывать набор F к названию профессии. Профессия — пресет, не архитектура.
7. Нельзя делать скрытую возможность недоступной в будущем: пользователь должен иметь возможность развить бизнес без миграции в другой тип аккаунта.
8. Новый F/E требует проверки против этого реестра до реализации UI и кода.

## 15. Открытые решения

До реализации новых F отдельно определить:

1. Родительский F для Смет + Заказов и его пользовательское имя.
2. Архитектуру F/E для Бронирований + Ресурсов и контекстные названия (`Номера`, `Оборудование`, `Залы` и т. п.).
3. Когда Производство становится отдельным F, а когда остаётся этапом Заказа.
4. Где живут постоянные Группы и Посещения без создания лишней F.
5. Архитектуру Абонемента/Подписки как capability и критерий отдельной рабочей поверхности.
6. Полный контракт универсального События Журнала.
7. Полную матрицу моделей деятельности из раздела 13.

Пока эти пункты не закрыты, запрещено создавать новые корневые F «на глаз» под отдельную профессию.

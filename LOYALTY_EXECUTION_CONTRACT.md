# LOYALTY_EXECUTION_CONTRACT

Короткий обязательный контракт технического исполнения F `Лояльность`.

Он не перекладывает декомпозицию на заказчика. Заказчик определяет WHAT / WHY и утверждает пользовательскую логику. Исполнитель сам определяет HOW, порядок файлов, коммиты и проверки.

## 1. Нормативные источники

Перед изменением runtime исполнитель обязан читать совместно:
1. `LOYALTY_ARCHITECTURE.md`;
2. `LOYALTY_ASSIGNMENT_CONTRACT.md`;
3. `LOYALTY_FINANCE_CONTRACT.md`;
4. этот файл;
5. фактическое состояние `main` / `staging` и последние коммиты.

Если существующий runtime старше контракта, правильное уже работающее проявление сохраняется, а устаревшая внутренняя модель мигрируется к контракту.

### 1.1. Нормативный документ нельзя «упрощать» ценой потери решений

При исправлении контракта действует принцип минимального смыслового изменения:
- меняются только правила, которые были явно пересмотрены;
- все остальные утверждённые поля, сценарии, ограничения, Z-состояния, конструкторы и примеры сохраняются;
- нельзя заменять подробный утверждённый контракт кратким пересказом только потому, что новый исполнитель считает его понятнее;
- если новое правило конфликтует со старым, исправляется конфликтующий фрагмент и все прямые следствия, а не удаляются соседние утверждённые механики;
- перед сохранением новой версии исполнитель сравнивает её с предыдущей нормативной версией и убеждается, что несвязанные утверждённые детали не исчезли.

Краткий технический отчёт может быть коротким. Нормативный продуктовый контракт — нет, если сокращение уничтожает ранее утверждённые решения.

## 2. Обязательные фазы

Работа выполняется слоями. Исполнитель сам дробит каждую фазу на безопасные технические шаги.

### Фаза A — UI

Сначала фиксируется полный пользовательский контур F `Лояльность` и шести E на mock / adapter данных:
- F/E/Z;
- A/B/C/D;
- общие Q/X/S;
- общие списки / карты / селекторы;
- все необходимые пользовательские действия и состояния.

На этой фазе запрещено изобретать новую экономику только ради работы кнопки.

### Фаза B — доменные сущности

После стабилизации UI реализуются владельцы состояния:
- DepositProgram / DepositInstance;
- Personal Account;
- Certificate;
- Subscription;
- Referral Program;
- Bonus Program.

Одна сущность не подменяется операцией другого владельца.

### Фаза C — persistence / API

Доменные сущности получают каноническое серверное хранение и API. Временные mock / auxiliary adapters удаляются только после подтверждённой миграции данных и потребителей.

### Фаза D — интеграции

Только после владельцев состояния подключаются связи:
- Finance;
- Settlement;
- Contacts;
- Journal;
- Service;
- end-user runtime.

Интеграция выполняется ссылками и командами владельца, без копирования правил в место вызова.

## 3. Нельзя смешивать ответственность

Запрещено:
- одновременно менять UI, бизнес-модель и финансовую семантику без необходимости одной атомарной миграции;
- делать `FinanceOperation` сущностью Лояльности;
- создавать локальную копию правил Депозита / Сертификата / Абонемента в Журнале или Контактах;
- создавать локальные UI-компоненты вместо общих владельцев приложения;
- продолжать реализацию только по памяти предыдущего чата.

Если для одной атомарной миграции нужны изменения нескольких слоёв, исполнитель обязан сохранить границы владельцев и закрыть изменение одной проверяемой фиксацией.

## 4. Контрольная точка каждого технического шага

Шаг считается закрытым только если одновременно есть:
1. фактическое изменение в репозитории;
2. commit SHA;
3. локально доступные автоматические проверки либо CI;
4. отсутствие незакрытого красного результата, относящегося к изменению.

Красивый отчёт без этих четырёх пунктов не является завершением.

## 5. Восстановление после смены / обрыва чата

Новый исполнитель не имеет права писать «продолжаю с того же места» только по памяти разговора.

Сначала он обязан установить по репозиторию:
- текущий HEAD `main`;
- текущий HEAD `staging`;
- последние относящиеся к задаче коммиты;
- фактические файлы runtime;
- состояние CI / тестов;
- первый реально незавершённый пункт.

Только после этого продолжается работа.

## 6. Ветка и продвижение

Нормальный рабочий маршрут:

```text
staging
  ↓ автоматические проверки
  ↓ runtime / интеграционная проверка
main
```

`main` не считается проверочной площадкой для незавершённой технической гипотезы.

Если заказчик прямо требует результат в `main`, исполнитель обязан сначала получить доказанный зелёный результат и только затем продвинуть тот же проверенный commit.

## 7. Автоматические предохранители

Критические правила Лояльности должны быть представлены не только текстом, но и `scripts/check-loyalty-architecture.mjs`, который входит в `npm run check`.

Проверка как минимум блокирует:
- исчезновение F `Лояльность` или одного из шести E;
- возврат ручного открытия / C `+` и бонусного остатка в Личный счёт;
- использование FinanceOperation как единственного хранилища DepositInstance;
- прямой канонический browser-data маршрут Депозита через `/finance/deposits`;
- локальный CSS / native select / browser dialog внутри Loyalty UI;
- отсутствие канонического серверного владельца состояния Депозита после его миграции;
- потерю ключевых утверждённых деталей конструкторов Абонемента, Реферальной и Бонусной программ при будущем «упрощении» документа.

# ТЗ — Реестр технических заданий

## Назначение

Этот файл является живым реестром технических заданий проекта.

Он дополняется по мере разработки и не является одноразовым документом.

## Главное правило разработки

Проект создаётся и развивается **последовательно по ТЗ**.

Каждое ТЗ добавляет новую часть в уже существующую архитектурную ветку. Реализация следующего ТЗ не означает повторную реализацию предыдущих ТЗ.

**Предыдущие исполненные ТЗ являются частью текущего приложения и должны сохраняться.**

Ни одно последующее ТЗ не имеет права:

- создавать приложение заново;
- создавать новый корень приложения;
- создавать параллельную архитектуру;
- повторно реализовывать уже исполненное ТЗ без прямого указания;
- заменять или удалять ранее исполненную функциональность без прямого требования соответствующего ТЗ;
- создавать локальную копию общего UI или CSS;
- использовать старое приложение как источник кода или переносить из него код.

Если для нового ТЗ требуется изменение уже существующего общего компонента, изменение выполняется как изменение **общего компонента системы**, а не как локальная копия компонента внутри новой ветки.

## Как работает исполнение

Перед началом работы исполнитель обязан определить состояние реестра и проекта.

Если пользователь просит исполнить одно ТЗ, исполняется только указанное ТЗ.

Если пользователь просит исполнить несколько ТЗ, они исполняются последовательно в указанном порядке или в порядке их номеров.

Уже исполненные ТЗ не исполняются повторно.

Если ТЗ является правкой другого ТЗ, исполняется именно указанная правка; исходное исполненное ТЗ сохраняется.

После выполнения каждого ТЗ его статус должен быть обновлён в этом реестре.

## Статусы

### Статус реализации ТЗ

Показывает состояние самого технического задания как документа:

- `План` — ТЗ ещё не подготовлено.
- `ТЗ готово` — требования подготовлены и утверждены, реализация ещё не завершена.
- `Изменить` — требования требуют пересмотра.

### Статус исполнения ТЗ

Показывает состояние реализации ТЗ в приложении:

- `Не исполнено` — реализация по ТЗ не выполнялась.
- `В работе` — реализация начата, но ещё не завершена и не проверена.
- `Исполнено` — ТЗ реализовано в существующем приложении и результат проверен.

**«ТЗ готово» и «Исполнено» — разные состояния.**

`ТЗ готово` означает готовность документа.

`Исполнено` означает фактическое выполнение требований в приложении.

## Отдельные ТЗ сущностей

После определения конкретной сущности создаётся отдельный файл:

`ТЗ/ТЗ-<номер>-<сущность>.md`

Отдельное ТЗ сущности не заменяет архитектурное ТЗ. Оно добавляет конкретную сущность внутрь уже существующего владельца.

## Правило корректирующих ТЗ

Корректирующее ТЗ уточняет или изменяет конкретную часть уже существующего ТЗ/архитектуры.

Корректирующее ТЗ:

- не создаётся самовольно без запроса пользователя;
- не превращается в новое самостоятельное ТЗ;
- не отменяет исходное ТЗ;
- не удаляет ранее реализованные сущности;
- не переписывает приложение целиком;
- изменяет только область, прямо указанную в правке.

Если требуется новая корректировка, сначала согласовывается с пользователем, нужна ли новая правка и как она должна быть оформлена. Исполнитель не добавляет новые ТЗ в реестр по собственной инициативе.

## Синхронизация статусов

После подготовки отдельного ТЗ сущности:

- статус документа фиксируется здесь как `ТЗ готово`;
- статус сущности фиксируется в `сущностей.md` как `ТЗ готово`.

После фактической реализации и проверки:

- соответствующее ТЗ получает `Исполнено`;
- соответствующая сущность получает `Готово`.

Если реализация начата, но ещё не проверена:

- ТЗ получает `В работе`;
- сущность получает `В работе`.

Для корректирующих ТЗ применяется тот же принцип: сначала фиксируется документ, затем после фактической реализации и проверки статус исполнения переводится в `Исполнено`.

## Правило проверки перед исполнением

Перед изменением кода исполнитель обязан:

1. определить, какие ТЗ уже имеют статус `Исполнено`;
2. определить, какую ветку изменяет текущее ТЗ;
3. определить уже реализованные сущности внутри изменяемой области;
4. сохранить существующую реализацию предыдущих ТЗ;
5. проверить, существует ли необходимый общий UI-компонент;
6. использовать общий UI и общий CSS вместо локального дубля;
7. добавить только отсутствующую часть текущего ТЗ;
8. проверить, что ранее исполненная функциональность не исчезла и не сломана;
9. только после проверки поставить `Исполнено`.

## Правило последовательного добавления

Архитектура развивается как единое приложение:

```text
ТЗ-01
  ↓
архитектурный фундамент
  ↓
ТЗ-01-ПРАВКИ
  ↓
полное дерево + смартфонная архитектура + единый Modal System
  ↓
ТЗ-02
  ↓
существующая реализованная сущность Клиенты
  ↓
следующие ТЗ
```

Каждое следующее ТЗ расширяет приложение, а не заменяет его.

## Правило защиты ранее исполненного

Если новое ТЗ требует изменения поведения, которое уже было реализовано предыдущим ТЗ, исполнитель **не должен самостоятельно решать**, что старую реализацию нужно заменить.

Он должен:

- сохранить существующую архитектуру;
- определить конкретное требование нового ТЗ;
- изменить только то, что требуется новым ТЗ;
- не затрагивать несвязанные ветки;
- не переписывать приложение целиком.

## Правило общего UI и CSS

Все ветки используют одну общую систему UI и CSS.

Компоненты не копируются внутрь отдельных веток.

Если новый ТЗ требует отсутствующий компонент, он добавляется в общий UI и затем используется нужной веткой.

CSS остаётся единой системой стилей.

## Правило исходников

Старое или другое приложение не является исходником для реализации.

Код, архитектура и структура нового приложения создаются по действующим ТЗ.

Нельзя переносить старый код поверх новой архитектуры.

## Правило расширения

Реестр не является конечным.

Новые ТЗ могут добавляться в любую существующую ветку **только по запросу/решению пользователя**.

Если появляется новая подпапка, она создаётся внутри своего владельца.

Если появляется новая сущность, она добавляется в `сущностей.md` и получает отдельное ТЗ.

## Принцип разработки

```text
Архитектура
    ↓
Владелец ветки
    ↓
Список сущностей
    ↓
Отдельное ТЗ сущности
    ↓
Исполнение ТЗ
    ↓
Проверка
    ↓
Отметка «Исполнено»
```

Нельзя перескакивать через архитектуру и создавать сущность вне её владельца.

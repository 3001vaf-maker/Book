# UI Reference V2 — DRAFT

> **Статус:** второй эталонный контур, пока только проект.
>
> V1 остаётся действующим и не изменяется.  
> Этот документ не является разрешением переписывать рабочий UI до отдельного утверждения.

## 1. Общая идея

Приложение не обязано открываться на «Главную» и не обязан использовать нижнюю навигацию.

Базовая модель V2:

```text
Приложение
→ боковая колода разделов
→ активная карточка раздела
→ внутренняя рабочая область / вложенная колода
```

Навигация воспринимается как работа с карточками/листами, а не как набор кнопок.

## 2. Ширина приложения

- Единая максимальная ширина приложения: **390 px**.
- Правило действует для рабочего контура и контура конечного пользователя, карточек и модальных слоёв.
- Большой монитор не растягивает приложение до ширины браузера.
- Высота может меняться по сценарию.
- Локальный экран не имеет права задавать собственную ширину приложения.

## 3. Базовый фон

Основная пара V2:

- рабочий базовый фон приложения — **#2F3338**;
- белый — **#FFFFFF** для рабочих карточек и листов.

`#2F3338` принят как текущий рабочий эталон. При визуальной проверке допустимо сделать его немного темнее, не меняя общий принцип.

Требования к основному тёмному:
- не чистый чёрный;
- не тёплый коричнево-бежевый;
- не случайный «технический серый»;
- нейтральный, глубокий, чистый;
- должен хорошо держать белые поверхности и яркие акценты.

Базовая палитра намеренно ограничена. Новый яркий цвет не вводится без отдельной функции в интерфейсе.

## 4. Боковая колода

Нижняя навигация в V2 отсутствует.

Основные рабочие разделы находятся в боковой колоде.

### Вызов

Жест **от левого края вправо** показывает колоду.

Колода не выглядит как обычное sidebar-меню.  
Пользователь видит закруглённые края/ярлычки карточек, лежащих слоями под текущим экраном.

### Выбор

Пользователь тянет нужную карточку в рабочую область.

Карточка не появляется мгновенно: она **вытекает/раскрывается** из колоды.

### Возврат

Жест **от левого края вправо** возвращает текущую карточку к родительскому уровню.

Кнопка «Назад» не является основным механизмом навигации V2.

### Активная рабочая поверхность Z

Активный экран обозначается как **Z**.

Z не должен выглядеть как прямоугольная страница, жёстко закрывающая приложение от края до края. Он воспринимается как **рабочая карточка / лист**, который затекает справа поверх нижележащей навигационной колоды.

Обязательная визуальная подсказка:
- верхний левый угол Z остаётся заметно закруглённым;
- в **закрытом рабочем состоянии** слева виден только очень тонкий край нижележащего слоя — ориентировочно **10–15 px**;
- этот видимый край начинается **ниже верхней зоны A/B/C/D** и не поднимается до заголовка;
- глубина нужна только как подсказка, что под Z есть E- или F-колода; это не sidebar и не постоянное меню;
- Z остаётся основным рабочим экраном, но его форма подсказывает возможность свайпа вправо.

### Закрытое состояние Z

- Z почти полностью занимает рабочую ширину;
- справа Z доходит до рабочего края;
- слева остаётся только 10–15 px визуальной глубины нижнего слоя;
- верхняя зона A/B/C/D остаётся самостоятельной и не закрывается Z;
- точный радиус верхнего левого угла утверждается визуально отдельно.

### Открытое состояние Z

После свайпа вправо геометрия меняется существенно: Z не просто «чуть сдвигается», а освобождает заметную часть ширины для нижележащей колоды.

Размер открытого состояния **не один для всех разделов**:
- если боковому разделу нужно мало места, Z может оставаться примерно на **половине** рабочей ширины;
- если боковому разделу нужно больше места, Z может оставаться примерно на **треть** рабочей ширины;
- промежуточное положение между этими состояниями допустимо и определяется конкретной E- или F-колодой.

То есть открытый Z обычно занимает ориентировочно **1/3–1/2** рабочей ширины, а E/F — оставшуюся часть. Это не фиксированный глобальный процент: конкретная колода задаёт свою каноническую открытую глубину.

Поведение:
- открытие Z: рабочая поверхность затекает **справа налево**;
- закрытие / подъём на уровень выше: свайп **вправо** уводит Z вправо и раскрывает нижележащую колоду;
- какая колода открывается под Z, зависит от текущего уровня: **E** для длинной колоды или **F** для короткой карточной колоды;
- свайп должен физически двигать Z вместе с пальцем, а не переключать состояние скачком.

Это не полноэкранное перекрытие. Это слой, лежащий поверх другого слоя.

## 5. Вложенные колоды

Одинаковая механика работает на нескольких уровнях.

Пример:

```text
ПРИЛОЖЕНИЕ
→ Финансы
  → внутренняя колода Финансов
    → ДДС
    → Кассы
    → Статьи
    → Отчёты
```

Повторный жест вправо поднимает пользователя ещё на один уровень выше.

## 6. Высота рабочих карточек

Карточки используют одну механику, но раскрываются на разную высоту.

Пока фиксируется только приоритет, без точных пикселей:

1. **Журнал записей** — максимальная рабочая высота.
2. **График** — второй по требованию к площади.
3. **Чат** — большой рабочий экран.
4. Остальные разделы — высота определяется сценарием.

Журнал должен позволять увидеть рабочий день почти целиком; допустим максимум один дополнительный вертикальный шаг до конца дня.

## 7. Верхняя зона и три управляющих места

В верхней части V2 сохраняется структура с **тремя отдельными местами под управляющие элементы** вокруг/рядом с заголовком.

Пока фиксируется только наличие этих трёх мест.

Не утверждаются:
- назначение каждого места;
- обязательность заполнения;
- тип элемента;
- иконка или текст;
- ширина;
- высота;
- расстояния между элементами;
- поведение при отсутствии элемента.

То есть V2 пока сохраняет сам принцип:

```text
[ SLOT 1 ]   [ TITLE ]   [ SLOT 2 ] [ SLOT 3 ]
```

Это не означает возврат старых значений A/B/C. Значения и размеры будут утверждаться отдельно после визуального макета.

## 8. Верхняя постоянная зона

Чат не обязан быть отдельной карточкой корневой колоды.

Предварительный принцип:
- Чат доступен постоянно через иконку-облачко в верхней зоне.
- Системные настройки также могут быть вынесены из рабочей колоды.
- Профиль может открываться через аватар/имя, если это подтвердится в макете.

Эти пункты пока не считаются окончательно утверждёнными.

## 9. Чат

Чат V2 использует классическую модель переписки и остаётся полноценным рабочим экраном внутри общей оболочки.

### 9.1. Вход в Chat

Нажатие на D = облачко Chat из любого экрана, где эта кнопка доступна, переводит в Chat.

**Если Chat открыт из конкретного представителя / пространства:**
- сразу открывается диалог именно с этим представителем;
- **A** — круглая иконка / аватар / визуальный знак представителя;
- **B** — имя / название представителя;
- **C** — переключение на список представителей / контактов;
- **D** — скрепка / вложения.

**Если Chat открыт из общего профиля конечного пользователя:**
- сначала открывается общий список диалогов;
- **A** — неактивна;
- **B = «Чат»**;
- **C и D** не показываются, пока не выбран конкретный собеседник;
- **Z** — вертикальный список карточек представителей / пространств, с которыми доступна коммуникация.

После выбора карточки открывается конкретный диалог, и A/B/C/D переключаются в контекст выбранного представителя.

### 9.2. Переписка

- Z становится рабочей областью переписки;
- сообщения идут вертикальной лентой;
- при открытии клавиатуры рабочая область адаптируется;
- нижний composer остаётся доступным;
- многострочный текст растёт вверх до канонического предела, затем получает внутреннюю прокрутку.

### 9.3. Composer и вложения

Внизу находятся:
- поле сообщения;
- справа — тёмная кнопка отправки.

Постоянной кнопки вложений внизу нет.

**D в Header = скрепка** и открывает добавление фото, видео, PDF и других поддерживаемых файлов.

Внутри конкретного диалога главное действие отправки сообщения живёт в composer, а не в C Header.

### 9.4. Переключение собеседника

**C** открывает / перерисовывает Z в список представителей / контактов.

После выбора другого представителя:
- A — его иконка / аватар;
- B — его имя / название;
- Z — выбранный диалог;
- C снова остаётся кнопкой перехода к списку представителей;
- D — скрепка.

### 9.5. Настройки Chat

Отдельная постоянная шестерёнка в C/D не создаётся.

Настройки конкретного Chat-контекста доступны через **A/B** текущего собеседника. Там могут жить параметры уведомлений, Push, Telegram и другие настройки коммуникации.

Это сохраняет Header компактным: C = контакты, D = вложения.

### 9.6. Свайп из Chat

Свайп вправо из Chat поднимает пользователя на уровень боковой колоды **F** текущего общего интерфейса.

Chat не создаёт дополнительную скрытую навигационную систему поверх F.

Точный порог жеста, физика и easing утверждаются на интерактивном прототипе.

### 9.7. Геометрия

- Chat подчиняется общей ширине приложения: ориентир максимум 390 px;
- роль пользователя не меняет внешнюю геометрию Chat UI;
- на телефоне Chat использует почти всю доступную высоту;
- на desktop не растягивается в широкую панель;
- нижняя навигация не используется.

## 10. Конечный пользователь: карточки профилей

Контур конечного пользователя не создаёт отдельную новую ролевую сущность ради интерфейса.

Правила:
- существующая нейтральная сущность профиля остаётся как есть;
- ради V2 её не переименовывать;
- не создавать параллельную доменную модель только ради нового интерфейса;
- раздел конечного пользователя использует **существующую карточку профиля** как основной визуальный объект выбора;
- не создавать отдельную облегчённую копию карточки для списка;
- название профессии / роли на карточке приходит из данных самого профиля и не зашивается в интерфейс конечного пользователя;
- UI-раздел может называться «Специалисты» или иным пользовательским термином, но это не меняет имя сущности в коде.

При открытии карточки конечный пользователь переходит в контекст выбранного профиля:
- сам профиль становится верхним контекстом экрана;
- ниже показываются данные отношений конечного пользователя именно с этим профилем: история, программы, скидки, депозит, личный счёт и другие реально существующие сущности;
- отсутствующая сущность не рисуется пустой карточкой.

Точная композиция и размеры карточек будут утверждаться отдельно.

## 11. Модальные слои — только три канонических класса

V2 запрещает произвольные размеры и отдельную геометрию модалок для каждого экрана.

Есть только три базовых класса.

### QUICK — быстрая модалка

**Направление:** снизу вверх.

Используется для:
- короткого выбора;
- быстрого действия;
- небольшого подтверждения;
- компактного ввода;
- временного контекста, который не требует отдельной рабочей страницы.

QUICK не превращается в полноэкранную desktop-панель.

### STANDARD — стандартная рабочая модалка

**Направление:** справа налево.

Используется для:
- подробной карточки;
- редактирования;
- документа;
- настроек конкретного объекта;
- длинной формы;
- рабочего контента, который должен оставаться временным слоем над текущим разделом.

STANDARD по основной геометрии близка к **Z**: это большая белая рабочая карточка, которая заходит справа и перекрывает почти всю рабочую поверхность.

Ключевое отличие от Z:
- **Z — экран/рабочая поверхность и не имеет крестика закрытия**;
- **STANDARD — временный модальный слой и всегда имеет явный крестик закрытия**;
- крестик закрывает модалку и возвращает пользователя к нижележащему состоянию, не меняя навигационный уровень.

Большая STANDARD:
- остаётся внутри **390 px** ширины приложения;
- занимает почти всю доступную рабочую высоту/площадь, но не обязана закрывать буквально каждый пиксель оболочки;
- точные внешние отступы и радиусы утверждаются на реальном макете;
- если контента больше доступной высоты, **прокручивается содержимое самой модалки вниз**, а оболочка модалки остаётся в пределах экрана;
- прокрутка идёт до конца фактического контента;
- не растягивается до размера desktop viewport;
- использует одну каноническую геометрию для всех STANDARD-модалок, без локальных вариантов «почти такой же модалки».

### SYSTEM — системная модалка

**Направление:** сверху вниз.

Используется для:
- системного предупреждения;
- критичного состояния;
- сервисного уведомления;
- системного подтверждения;
- состояния, которое должно временно перекрыть текущий контекст.

SYSTEM не становится отдельным продуктовым экраном.

## 12. Главное правило модалок

```text
QUICK    → снизу
STANDARD → справа
SYSTEM   → сверху
```

Нельзя создавать:
- локальную «почти такую же» модалку;
- случайную ширину/высоту для одного экрана;
- модалку, растянутую на desktop viewport;
- новый четвёртый тип без изменения самого эталона V2.

## 13. Движение — часть интерфейса

Экран или модалка не должны просто «появляться».

Для каждого элемента заранее определяется:
- откуда он приходит;
- докуда раскрывается;
- какой слой остаётся виден;
- куда он уходит обратно.

Анимация и направление являются частью UI-контракта, а не декоративным эффектом после разработки.

## 14. Что ещё не утверждено

Пока намеренно не фиксируются:
- окончательная глубина основного тёмного фона (рабочий эталон сейчас #2F3338);
- точный оттенок нейтрального / вторичного серого текста;
- точные высоты карточек;
- точные размеры QUICK / STANDARD / SYSTEM;
- окончательный состав корневой колоды;
- окончательное положение Профиля и Настроек;
- скорость, easing и физика анимаций.

Это будет утверждаться отдельными визуальными макетами/стендом.

## 15. Защита V2 в будущем

Если V2 станет основным эталоном, его нельзя внедрять только документацией.

До production должны появиться автоматические guards:
- единая ширина 390 px;
- запрет локальных app-width;
- запрет произвольной модальной геометрии;
- только QUICK / STANDARD / SYSTEM;
- запрет локальных CSS-обходов;
- проверка направления и owner модальных слоёв;
- отдельный интерактивный reference-стенд V2.

До этого момента V1 остаётся действующим эталоном.


## 16. Цветовая система V2

Цветовая система является частью этого же UI-эталона. Отдельные документы «про цвета», «про кнопки» и «про модалки» не создаются.

### 16.1. База

- основной тёмный фон приложения: **#2F3338**;
- белые рабочие поверхности: **#FFFFFF**;
- основной системный текст: **#111111**;
- текст на тёмном или цветном фоне: **#FFFFFF**, когда этого требует контраст;
- нейтральный / вторичный текст: серый, точный оттенок будет утверждён отдельно.

### 16.2. Главная кнопка

Главная кнопка:
- фон **#111111**;
- текст **#FFFFFF**;
- используется для одного главного действия текущего экрана, шага или модалки.

Ключевое правило:

> В одном текущем действии не должно быть двух или более главных чёрных кнопок.

Если на экране несколько действий, только одно может быть главным. Остальные должны иметь другой визуальный приоритет.

### 16.3. Нейтральная активная кнопка

Нейтральная кнопка — это активная, доступная для нажатия кнопка, но не главное действие.

Рабочий принцип:
- фон **#FFFFFF**;
- текст **#111111**;
- тонкий чёрный контур.

Нейтральная кнопка не должна выглядеть как disabled-состояние.

### 16.4. Пассивная / disabled-кнопка

Пассивная кнопка — это действие, которое существует, но сейчас недоступно.

Например:
- `Продолжить` до заполнения обязательных данных — disabled;
- после выполнения условий та же кнопка становится активной главной чёрной.

Рабочий цвет disabled-фона:
- **#D8D3CF**.

Цвет должен восприниматься как мягкий, «вкусный» серый, а не технический системный grey.

### 16.5. Красный акцент

Эталонный красный:
- **#FF1111**.

Красный не привязан только к заливке. В зависимости от контекста он может использоваться как:
- заливка;
- цвет текста;
- контур;
- индикатор;
- уведомление;
- опасное / критическое действие.

Конкретный способ применения выбирается по контрасту и смыслу.

### 16.6. Жёлтый акцент

Эталонный жёлтый:
- **#FFFF00**.

Функция жёлтого пока намеренно не закреплена.

Он может использоваться как:
- заливка;
- контур;
- маркер;
- выбранное состояние;
- небольшой яркий акцент.

Жёлтый не должен автоматически становиться «главной кнопкой». Его роль определяется только конкретным сценарием.

### 16.7. Фиолетовый

Фиолетовый пока **не входит в базовую палитру V2**.

Он может появиться позже только если возникнет отдельная постоянная функция, которой действительно нужен собственный цветовой язык. До этого добавлять третий яркий акцент не нужно.

### 16.8. Статусные цвета записи

Цвета плашек записи сохраняются как отдельная спокойная информационная палитра и не смешиваются с иерархией кнопок.

Текущие эталонные цвета:

- активная запись: **#EFFFBB**;
- верхняя часть активной записи: **#E7FF99**;
- оплачено: **#DDE8D7**;
- верхняя часть оплаченной записи: **#B4D1B8**;
- не пришёл: **#F1DADA**;
- верхняя часть «не пришёл»: **#E3B5B5**;
- удалённая запись: **#FDD2D2**;
- перерыв: **#E6E4E1**.

Эти цвета описывают состояние записи. Они не являются цветами основных действий.

### 16.9. Общий принцип палитры

V2 строится на строгой базе:
- глубокий тёмный;
- белый;
- насыщенный чёрный текст;
- серый вторичный текст;
- один яркий красный;
- один яркий жёлтый;
- спокойная статусная палитра записей.

Цвет не добавляется «для красоты». Каждый новый цвет должен иметь понятную функцию.




## 18. Система координат интерфейса

Для обсуждения, макетов и дальнейшей реализации используется единая нейтральная система обозначений:

- **H** — верхняя зона / Header;
- **A** — левая системная / идентификационная позиция внутри H;
- **B** — заголовок внутри H;
- **C** — главное контекстное действие внутри H;
- **D** — Chat / входящие события внутри H;
- **S1…Sn** — опциональный слой заметок / news / reels / media;
- **E1…En** — длинная боковая колода, когда разделов или элементов много;
- **F1…Fn** — короткая перелистываемая колода крупных разделов;
- **Z** — активная рабочая поверхность / экран;
- **Z1, Z2…** — смысловые блоки внутри Z;
- **Z1.1, Z1.2…** — элементы внутри соответствующего блока.

**E и F — два режима одной боковой навигационной зоны.** Они не показываются одновременно как две разные системы.

E и F не являются постоянным открытым меню. Они находятся под Z и раскрываются свайпом вправо.

F — колода крупных карточек: карточки можно двигать пальцем влево/вправо, передняя позиция сохраняется, а активный раздел меняется. Нажатие на выбранную F-карточку открывает Z поверх неё.

Z всегда сохраняет визуальную связь с нижележащей колодой через закруглённый верхний левый угол и эффект слоёв.

H и S не обязаны присутствовать одинаково на каждом экране. В зависимости от сценария:
- H может быть видим;
- S может располагаться под H;
- S может занимать верхнюю роль, если H не нужен;
- Z может подниматься выше и частично или полностью перекрывать H/S.

Это определяется конкретным интерфейсным сценарием, а не отдельной новой оболочкой.


## 19. Опциональный слой Media / News / Reels

В интерфейсе может присутствовать отдельный медиа-слой с короткими публикациями / новостями / reels.

Это **не постоянный обязательный блок**.

Правила:
- слой располагается под верхней зоной A/B/C/D и над рабочей поверхностью Z, если он нужен в текущем контексте;
- если контента нет, слой не резервирует пустую высоту и визуально исчезает;
- если контент есть, он может показываться как горизонтальная лента компактных элементов;
- наличие Media / News / Reels не меняет базовую геометрию A/B/C/D, E/F и Z;
- слой не должен превращаться в отдельный постоянный раздел навигации, если для этого нет отдельного продуктового решения;
- конкретная высота, форма элементов и способ раскрытия утверждаются на реальном макете с фактическими данными.

Важно: размеры открытого состояния E/F и остаточной ширины Z не фиксируются абстрактно. Они определяются после того, как известны реальные элементы, подписи и плотность конкретного раздела.


### 19.1. Размеры открытого состояния

Размеры открытого состояния E/F и Z не утверждаются без реального содержимого.

Сначала определяется:
- сколько элементов в E/F;
- длина их названий;
- плотность данных;
- нужен ли Media / News / Reels слой;
- сколько места требуется Z для чтения и взаимодействия.

Только после этого на макете фиксируется конкретная открытая пропорция.


## 20. Header H: постоянные позиции и смысл A/B/C/D

Верхняя зона интерфейса обозначается как **H / Header**.

Её базовый фон — основной тёмный фон интерфейса. H не является белой карточкой.

Базовая координатная схема:

```text
A        B                 C        D
```

H может быть скрыт или перекрыт Z в отдельных сценариях, но когда H присутствует, смысл и порядок A/B/C/D сохраняются.

### A — левая системная / идентификационная позиция

A имеет две канонические визуальные формы.

**Форма 1 — идентификатор человека / профиля**
- фото;
- если фото нет — инициалы;
- визуально это круглая иконка;
- она крупнее обычной технической кнопки;
- используется там, где нужно показать текущий личный контекст, в первую очередь в интерфейсе конечного пользователя;
- нажатие ведёт в профиль / аккаунт / общие настройки соответствующего контекста.

**Форма 2 — системные настройки**
- маленькая техническая кнопка с иконкой шестерёнки;
- используется в рабочем приложении Пользователя 1/2/3, где постоянный аватар в Header не нужен;
- ведёт в системные / технические настройки приложения.

То есть A — постоянная координата, но её размер и визуальный тип зависят от функции: личная иконка крупнее, шестерёнка компактнее.

### B — заголовок

B — основной заголовок текущего контекста / раздела.

Правила:
- одна строка;
- не должен превращаться в 2–3 строки;
- C и D не имеют права вытеснять B в многострочный режим;
- если конкретному Z нужен собственный локальный заголовок, он живёт внутри Z и не отменяет смысл B как заголовка H.

### C — главное контекстное действие

C — место одного главного действия текущего контекста.

Примеры:
- `+`;
- «Добавить»;
- «Сохранить»;
- «Далее»;
- «Записаться»;
- другое одно конкретное действие.

Вид C зависит от содержимого:
- одна иконка / плюс — компактная кнопка;
- короткий текст — кнопка становится шире;
- размер меняется только настолько, насколько требует действие;
- C не должна ломать B или занимать произвольную ширину.

Если главного действия нет, C может отсутствовать.

Правило одной главной кнопки сохраняется: C не дублируется второй равнозначной главной кнопкой рядом.

### D — Chat / входящие события

D — каноническая кнопка Chat.

Визуально:
- всегда иконка **облачка сообщения**;
- нажатие открывает Chat;
- поверх/рядом с иконкой может появляться badge с количеством новых событий: 1, 2, 3, 10 и т. д.;
- отдельная постоянная кнопка уведомлений не создаётся: входящие коммуникационные события отображаются через badge D и соответствующую историю Chat.

Если конкретный сценарий действительно не имеет Chat, D может отсутствовать, но при наличии Chat его позиция и визуальный знак не меняются.

### Настройки конкретного раздела

Настройки конкретного раздела не занимают отдельную постоянную пятую позицию в H.

Они могут жить внутри Z, в локальном заголовке или локальных контролах соответствующего раздела.

Глобальные / системные настройки:
- для конечного пользователя доступны через A в форме личной иконки;
- для рабочего приложения доступны через A в форме маленькой шестерёнки.


## 21. Цветовая логика E/F: материал, а не техническая кодировка

Боковая навигационная зона E/F не использует яркую системную палитру по принципу «каждому разделу свой цвет».

Базовый принцип:

- **одинаковый тип сущности / один список → один материал / один цвет карточек**;
- разные карточки внутри такого списка отличаются содержимым, состоянием и данными, но не получают случайные разные цвета;
- если рядом представлены **разные типы разделов / разные смысловые классы**, им допустимо назначать разные спокойные оттенки;
- цвет должен помогать различать смысловые слои, а не превращаться в декоративную радугу;
- цвет не кодирует отдельный объект сам по себе без продуктовой причины.

Пример:
- список контактов / людей: все карточки одной цветовой семьи;
- несколько разных разделов в F-колоде: допустимы разные материалы / оттенки, если они действительно представляют разные классы содержания.

### Визуальное направление

Предпочтение — не яркий фиолетовый SaaS-акцент, а спокойная editorial / fashion палитра материалов:

- тёплый каменный — ориентир `#D8D1C8`;
- taupe / mushroom — ориентир `#B9AEA4`;
- дымчато-коричневый — ориентир `#8F8178`;
- глубокий сливово-чернильный может использоваться редко как особый акцент, но не как обязательный системный цвет.

Эти HEX пока считаются **направлением**, а не окончательным токеном: точные значения утверждаются на реальном макете рядом с BASE `#2F3338` и Z `#FFFFFF`.

### Роль цвета

- **BASE / H** — графит;
- **Z** — белая рабочая поверхность;
- **E/F** — спокойные тактильные «материалы»;
- **S** — жёлтый акцент используется дозированно;
- **критические состояния** — красный;
- **C** — канонически белая активная кнопка на тёмном H: фон `#FFFFFF`, текст/иконка `#111111`. Это фиксированный базовый вид главного действия. Другой цвет допускается только как отдельное осознанное исключение конкретного сценария.

Цвет E/F определяется прежде всего **типом содержания**, а не порядковым номером карточки.


## 22. Стартовый экран конечного пользователя

Это первый конкретный экран, собранный на основе общей системы H / S / E-F / Z.

### 22.1. Header H

На стартовом экране:

- **A** — аватар / инициалы конечного пользователя;
- **B** — имя конечного пользователя;
- **C** — отсутствует, если на стартовом экране нет одного главного действия;
- **D** — Chat; на кнопке может быть badge входящих событий.

### 22.2. Рабочая поверхность Z

В стартовом состоянии Z содержит как минимум два смысловых блока.

#### Z1 — Предстоящие визиты

- заголовок блока: «Предстоящие визиты»;
- заголовок спокойный, серый;
- ниже — карточки будущих визитов;
- визуальный принцип карточки: белая/нейтральная карточка с чёрной обводкой;
- внутренний состав данных карточки утверждается отдельно;
- карточки приходят / продолжаются **с правой стороны** и листаются горизонтально до конца доступных визитов.

#### Z2 — Представители / пространства

Рабочее название блока пока не считается финальным UI-термином.

Смысл блока широкий: люди, специалисты, компании, пространства, магазины, сервисы и другие стороны, услугами/предложениями которых пользуется конечный пользователь.

- заголовок блока спокойный, серый;
- карточка представителя/пространства формируется из соответствующего Profile-контекста;
- карточки имеют чёрную обводку;
- движение карточек — горизонтальное, с продолжением вправо до конца списка.

Не вводить в архитектуру отраслевой термин «мастер» как базовый тип.

### 22.3. Открытие боковой колоды F

Свайп Z вправо раскрывает короткую боковую колоду **F**.

Пока известно:
- в колоде ориентировочно до 5 разделов;
- **F1 — «Представители»**;
- отдельный раздел — **«История»**; его номер F пока не закрепляется;
- остальные разделы будут определяться по мере проектирования.

На стартовом Z пользователь видит только **будущую часть истории взаимодействий** через блок «Предстоящие визиты». Прошедшие визиты на стартовом экране не показываются.

### 22.4. Раздел «История»

При выборе «История» открывается отдельный Z, содержащий **хронологию визитов / взаимодействий**, а не список представителей.

Базовое состояние:
- при открытии в опорной точке показывается **ближайшая следующая запись**;
- список движется вертикально;
- движение в сторону будущего показывает последовательность следующих записей;
- движение в сторону прошлого показывает последовательность уже состоявшихся записей;
- таким образом, один экран истории позволяет пройти хронологию в обе стороны относительно ближайшей следующей записи.

Точная механика инерции, позиционирования и визуального разделения «будущее / прошлое» утверждается на макете.


Карточка события истории содержит данные о **конкретном взаимодействии** с представителем / пространством: что именно происходило в этом взаимодействии. Это может быть услуга, занятие, визит, работа, ремонт, покупка или другой тип взаимодействия в зависимости от сферы.

Примеры смысла данных: стрижка, окрашивание, маникюр, урок, визит специалиста, ремонт и т. п.

На этом этапе **не фиксируется внутренняя компоновка карточки**: какие поля где стоят, сколько строк, где цена, дата, статус и т. д. Фиксируется только смысл — карточка истории описывает конкретное событие / взаимодействие.

### 22.5. Раздел «Представители»

При выборе **F1 «Представители»** открывается отдельный Z только с представителями / пространствами, с которыми взаимодействует конечный пользователь.

Правила:
- список идёт **вертикально вниз**;
- каждая карточка представляет отдельный Profile-контекст / сторону взаимодействия;
- порядок карточек может меняться через сортировку;
- конкретное место и вид управления сортировкой пока не утверждены;
- термин «представители» — рабочий нейтральный термин интерфейсного проектирования и не вводит отраслевую роль в архитектуру.


Карточка представителя в этом разделе **не проектируется заново**. Она формируется из карточки / данных соответствующего **Profile** в приложении. Интерфейс конечного пользователя использует представление Profile как источник, а не создаёт отдельную независимую сущность карточки.

### 22.6. Переход в контекст конкретного представителя

После нажатия на карточку конкретного представителя / пространства меняется текущий контекст интерфейса.

Header H:
- **A** — аватар / визуальный идентификатор выбранного представителя;
- **B** — имя / название выбранного представителя;
- **C** — «Записаться» или другое каноническое действие начала взаимодействия, если запись применима в этом контексте;
- **D** — Chat именно с этим представителем.

Рабочая поверхность Z содержит:

1. верхний блок с основными данными взаимодействия / работы с этим представителем;
2. историю коммуникации именно с этим представителем;
3. бонусные, лояльностные или другие программы этого представителя.

Точный состав, порядок и визуальная форма этих внутренних блоков утверждаются при проектировании данного Z.


### 22.7. Контекстное действие C после открытия представителя или события

Кнопка **C** не имеет одного глобального текста для всех типов представителей. Она выражает **главное действие в текущем контексте**.

#### Если открыт представитель / пространство

После открытия карточки представителя C определяется его типом и доступным сценарием взаимодействия.

Примеры:
- для услуги / записи — **«Записаться»**;
- для будущего торгового сценария — действие покупки / корзины или другое соответствующее действие;
- для других типов взаимодействия — собственное главное действие.

Конкретные названия для ещё не спроектированных контуров заранее не придумываются.

Нажатие C переводит конечного пользователя из обзорного контекста представителя в **прикладной сервисный сценарий**, ради которого открыт этот представитель.

Для сценария записи это классическая цепочка:
**выбор услуги → календарь → время → дальнейшие шаги записи**.

#### Если открыто конкретное событие Истории

При открытии карточки уже состоявшегося взаимодействия C предлагает **снова войти в соответствующий прикладной сценарий**, а не просто перечитать историю.

Для сервисного сценария текст остаётся коротким и прямым — **«Записаться»**, а не «Повторить запись».

Смысл действия:
- пользователь видит, что именно делал раньше;
- нажимает C;
- система переводит его в контекст соответствующего представителя / сервиса;
- далее запускается актуальная цепочка действия, например выбор услуги → календарь → время.

Историческая карточка не должна жёстко копировать старую операцию один-в-один: она служит точкой входа в **новое актуальное действие** в том же смысловом контексте.

Для других будущих контуров (магазин, товары и т. п.) название C и следующая цепочка определяются соответствующей моделью, когда этот контур будет спроектирован.


### 22.8. Сценарий записи: последовательная перерисовка Z

После нажатия **C = «Записаться»** пользователь входит в прикладной сценарий записи. Внутри этого сценария не создаются отдельные нижние кнопки и не открываются новые независимые страницы оболочки: **одна и та же рабочая поверхность Z последовательно перерисовывается на каждом шаге**.

Для сервисного сценария типа записи:

1. **Z = рабочие места / пространства**  
   Пользователь выбирает, где именно хочет получить услугу. Даже если ранее использовалось известное пространство, выбор не должен считаться навсегда фиксированным.

2. **Z = услуги / процедуры**  
   Показываются карточки доступных услуг. Можно выбрать одну или несколько услуг, если сценарий это допускает.

3. **Z = календарь**  
   Пользователь выбирает дату.

4. **Z = доступные временные слоты**  
   После выбора даты Z перерисовывается в список доступного времени.

5. **Z = итог записи / подтверждение**  
   Формируется итоговая карточка записи с выбранным пространством, услугами, датой и временем.

### 22.8.1. Карточки услуг / процедур

На шаге выбора услуг / процедур Z использует не крупные hero-карточки, а **компактные прямоугольные бежевые sticker-карточки**.

Визуальный принцип:
- белая поверхность Z;
- каждая услуга — отдельный бежевый прямоугольный стикер;
- прямые углы;
- мягкая тень;
- небольшие равномерные промежутки между карточками;
- карточки визуально компактные, ориентир — примерно на три строки содержимого, а не на крупный рекламный блок;
- все карточки одного типа имеют одинаковую базовую геометрию;
- справа / в явной зоне карточки находится аккуратный selector / toggle выбора;
- допускается множественный выбор, если сценарий позволяет выбрать несколько услуг;
- выбранное состояние должно быть заметно, но не превращать карточку в яркий технический контрол.

По визуальному языку эти карточки родственны карточкам документов в юридическом sticker-слое, но живут уже внутри обычного Z-flow.

Карточки рабочих пространств / представителей не подменяются этими sticker-карточками: они используют представление Profile соответствующего пространства / представителя.

### 22.9. Кнопка C в сценарии записи

C остаётся **единственной главной кнопкой действия в Header H**.

Она меняется по текущему шагу, например:
- «Далее»;
- «Выбрать»;
- «Подтвердить»;
- другое короткое действие, соответствующее текущему шагу.

Нижняя фиксированная CTA-кнопка не появляется.

### 22.10. Назад внутри последовательного сценария

Внутри многошагового сценария записи **свайп вправо используется как возврат на предыдущий шаг**, а не как открытие E/F.

Пример:
- временные слоты → свайп вправо → календарь;
- календарь → свайп вправо → услуги;
- услуги → свайп вправо → рабочие места / пространства.

Это означает, что жест вправо имеет контекстный приоритет:
- **внутри активного многошагового flow** — назад на один шаг;
- **на корневом Z текущего раздела** — раскрытие E/F.

Таким образом, E/F не должны случайно открываться посреди сценария записи.

После выхода из flow пользователь снова возвращается к обычной навигационной механике Z ↔ E/F.

Точное поведение анимации, порог жеста и обработка частично выполненного свайпа утверждаются на реальном прототипе, но семантика жеста фиксируется уже сейчас.


### 22.11. Стек Z-карточек внутри flow

В многошаговом сценарии записи Z работает как **стек последовательно накладывающихся рабочих карточек**.

Правила:

- переход вперёд не является горизонтальным свайпом;
- следующий шаг открывается через **C** и накладывает новый Z-пласт поверх предыдущего;
- предыдущий шаг остаётся логически под текущим и может быть восстановлен;
- свайп **вправо** скидывает верхнюю Z-карточку и возвращает на предыдущий шаг;
- свайп влево не используется как способ пройти вперёд;
- пока активен этот стек, жест вправо не открывает E/F.

Пример:

```text
пространство
  → услуги
    → календарь
      → временные слоты
        → подтверждение
```

Каждый следующий шаг — новый верхний Z-пласт.

### 22.12. Постоянный Header и видимость C в flow

В сценарии записи **H остаётся доступным**, а C должна быть постоянно видна на каждом шаге.

Z не перекрывает Header в этом flow.

Если содержимое текущего Z длинное:
- прокручивается содержимое Z;
- локальный заголовок / данные внутри Z могут уходить вверх вместе с контентом;
- H и кнопка C остаются на месте;
- пользователь всегда видит текущее главное действие: «Далее», «Подтвердить» и т. п.

Это обязательное поведение: пользователь не должен прокручивать экран назад только для того, чтобы найти основную кнопку действия.


### 22.13. Завершение записи и возврат в контекст представителя

После подтверждения записи многошаговый Z-flow закрывается и пользователь возвращается в основной контекст выбранного представителя.

Header H возвращается к базовому состоянию этого представителя:
- **A** — аватар / визуальный идентификатор представителя;
- **B** — имя / название представителя;
- **C** — базовое главное действие данного контекста, например «Записаться»;
- **D** — Chat с представителем.

На основном Z представителя после успешной записи:
- новая запись появляется в блоке **предстоящих визитов / взаимодействий**;
- со временем, после наступления и завершения события, эта запись перестаёт быть будущей и становится частью прошлой истории;
- ниже могут отображаться бонусные, лояльностные или другие программы данного представителя;
- также могут появляться другие смысловые блоки, которые будут определяться по мере появления конкретных продуктовых сценариев.

### 22.14. Стабильность H во время многошагового flow

Во всём сценарии записи H остаётся стабильным по структуре.

- **A** сохраняет текущий контекст представителя;
- **B** сохраняет его имя / название и не меняется между шагами;
- **C** меняется по текущему шагу: «Далее», «Подтвердить» и т. п.;
- **D** остаётся Chat.

Пользователь может открыть Chat даже в середине записи.

Такой переход не должен разрушать или обнулять текущий стек Z-flow: после возврата из Chat пользователь должен продолжить с того шага, на котором остановился.


### 22.15. Локальные заголовки шагов остаются внутри Z

Заголовки шагов многошагового сценария записи **не переходят в Header H**.

Они являются частью текущей Z-карточки и прокручиваются вместе с её содержимым.

Примеры локальных заголовков Z:
- «Выбор рабочего пространства»;
- «Выбор процедур»;
- «Выбор даты»;
- «Выбор времени»;
- «Подтвердите запись».

Во время этих шагов Header H сохраняет стабильный контекст представителя:
- **A** — текущий представитель;
- **B** — имя / название представителя;
- **C** — текущее главное действие шага;
- **D** — Chat.

Таким образом, **B не используется как заголовок шага flow**. Название шага всегда остаётся внутри Z.


## 23. Контракт реализации V2

Этот раздел существует специально, чтобы согласованный интерфейс не остался только описанием и не был повторно переосмыслен другим чатом.

### Статусы

Для каждого крупного блока используются три независимых статуса:

- **DESIGN LOCKED** — поведение и визуальная логика согласованы;
- **IMPLEMENTED** — реализовано в коде;
- **VERIFIED** — проверено на реальном интерфейсе / сценарии.

Нельзя считать блок завершённым только потому, что он описан в документе.

### Текущее состояние

На момент этой фиксации:

- оболочка конечного пользователя H / A-B-C-D / S / E-F / Z — **DESIGN LOCKED**, не реализована как V2;
- стартовый экран конечного пользователя — **DESIGN LOCKED**, не реализован как V2;
- История и Представители — **DESIGN LOCKED на уровне структуры**, внутренние карточки ещё не спроектированы;
- контекст представителя — **DESIGN LOCKED на уровне структуры**;
- booking flow Z-stack — **DESIGN LOCKED**, не реализован как V2;
- модальные классы QUICK / STANDARD / SYSTEM — **DESIGN LOCKED**;
- цветовая логика BASE / Z / S / E-F / C — **DESIGN LOCKED на уровне принципов**, точные токены E/F ещё требуют визуального утверждения;
- входная / welcome / login / registration часть — **НЕ СПРОЕКТИРОВАНА V2** и должна быть разобрана отдельно до реализации всего конечного контура.

### Правило дальнейшей работы

После завершения входной части проектирование общего контура конечного пользователя прекращается и начинается реализация.

Реализация должна идти по одному контролируемому потоку:

1. feature-ветка от актуального **staging**;
2. реализация согласованного V2 без изменения продуктовой логики по ходу;
3. проверка каждого блока по этому документу;
4. merge feature → staging;
5. полная проверка staging;
6. только после этого staging → main.

Другой чат не должен заново «придумывать» интерфейс. Его задача — реализовать этот документ и фиксировать отклонения как отдельные вопросы, а не менять решения молча.

### Проверка реализации

Перед признанием V2 готовым отдельно проверяются:
- геометрия 390 px;
- стабильность H;
- A/B/C/D;
- наличие/отсутствие S;
- E/F и их свайпы;
- Z и его слои;
- booking Z-stack;
- Chat в середине flow без потери состояния;
- возврат после подтверждения;
- QUICK / STANDARD / SYSTEM;
- отсутствие старой bottom navigation;
- отсутствие старых back-кнопок в flow там, где возврат должен быть свайпом;
- отсутствие нижней primary CTA там, где действие должно жить в C.


## 24. Вход / регистрация после подтверждения действия

Этот контур относится к конечному пользователю и начинается **после того, как он уже прошёл прикладной flow и нажал C = «Подтвердить»**.

### 24.1. Удержание выбранного времени

Для сценария записи:

- пользователь проходит пространство → процедуры → дата → время → подтверждение;
- нажимает C = «Подтвердить»;
- если он ещё не авторизован, выбранный временной слот должен быть **временно удержан на период входа / регистрации**;
- временное удержание не равно окончательно созданной записи;
- если пользователь не завершает вход / регистрацию, удержание должно автоматически освобождаться;
- точный TTL удержания пока не утверждён.

Если пользователь уже авторизован, подтверждение сразу завершает действие и возвращает его в основной контекст представителя, где новая запись появляется среди предстоящих.

### 24.2. Auth Sticker — вход

Если пользователь не авторизован, вместо обычного H/Z показывается специальное входное состояние **Auth Sticker**.

Визуальная основа:
- тёмный BASE;
- по центру белый прямоугольный стикер / бумажка с прямыми углами и мягкой тенью;
- стикер может увеличиваться по высоте, если содержимого становится больше, но сохраняет тот же визуальный характер;
- основное действие на этом экране остаётся **внутри стикера**, а не переносится в C Header.

Содержимое входного стикера:
- Email;
- Пароль;
- внутри поля пароля — глаз / переключатель «показать / скрыть пароль»;
- основная кнопка входа внутри стикера;
- активная текстовая ссылка «Зарегистрироваться»;
- активная текстовая ссылка «Забыли пароль?».

Для белого стикера базовое направление главной кнопки — тёмная/чёрная кнопка с белым текстом; точная надпись утверждается на макете.

Если данные входа верны:
- пользователь попадает в свой уже существующий аккаунт;
- затем завершается удержанное прикладное действие и открывается соответствующий основной контекст.

### 24.3. Переход в регистрацию

Нажатие «Зарегистрироваться» выводит пользователя **из sticker-состояния** в обычную оболочку H + Z.

Регистрационный экран:
- **B** — заголовок регистрации;
- **C** — «Подтвердить»;
- **Z** — белая рабочая поверхность с формой;
- локальные поля живут внутри Z.

Поля регистрации:
- Имя — обязательно;
- Фамилия — необязательно;
- Телефон — обязательно;
- Email — обязательно;
- Пароль — обязательно;
- Повтор пароля — обязательно.

Пароль вводится дважды. Поля пароля используют переключатель «показать / скрыть» по той же логике, что и вход.

Нажатие C = «Подтвердить» валидирует форму и совпадение двух паролей, но регистрационный контур ещё не считается завершённым до обязательного принятия условий использования.

### 24.5. Восстановление пароля — пока только точка входа

На Auth Sticker присутствует ссылка «Забыли пароль?».

Сам flow восстановления пока не проектируется в этом разделе.

Безопасностное правило: существующий пароль пользователю **не высылается**. Восстановление должно идти через одноразовую ссылку / код и установку нового пароля.


### 24.6. Юридическое sticker-состояние перед финальным действием

Юридический checkpoint **не является обычным H/Z-экраном и не является SYSTEM-модалкой**. По визуальной логике он относится к тому же специальному техническому sticker-состоянию, что и приветствие / вход.

Внешний вид:
- основной фон остаётся тёмным;
- активного Header H с A/B/C/D нет: верхняя зона визуально чистая;
- по центру находится белый прямоугольный стикер / бумажка с прямыми углами и мягкой тенью;
- размер стикера зависит от количества документов и содержимого, но он сохраняет характер отдельного бумажного слоя.

На стикере показываются **2 или 3 короткие карточки документов**.

Для первого прохождения возможен состав:
1. **«Условия использования»** — обязательное, если актуальная версия платформенных условий ещё не принята;
2. **«Согласие на обработку персональных данных»** — обязательное согласие соответствующего представителя;
3. **«Согласие на получение рекламы»** — необязательное.

В пользовательском интерфейсе не использовать сокращение «ПДН» как самостоятельное название: оно непонятно обычному человеку. Для карточки используется полная, но короткая и общеупотребимая формулировка **«Согласие на обработку персональных данных»**.

Для рекламного согласия базовая короткая формулировка — **«Согласие на получение рекламы»**. Она остаётся отдельным добровольным пунктом и не блокирует основное действие.

Если «Условия использования» уже приняты и актуальны, они не показываются, и остаются два документа представителя.

Названия в списке должны быть короткими и понятными. Полное юридическое название документа живёт внутри раскрытого текста и не обязано занимать место в компактной карточке.

Карточки документов внутри юридического sticker-состояния имеют собственную фиксированную геометрию.

Вид каждой карточки:
- прямоугольный **бежевый стикер**;
- все карточки одинакового размера независимо от длины текста;
- между карточками есть явные равномерные промежутки;
- каждая карточка визуально отделена собственной мягкой тенью;
- карточки лежат поверх большого белого стикера как отдельные бумажные слои;
- заголовок документа — чёрный, более крупный и жирный;
- строка статуса — чёрная, обычного начертания, меньшего размера: **«обязательное»** или **«необязательное»**;
- справа — явный переключатель/toggle состояния «включено / выключено».

Статус не выделяется отдельным цветом: различие строится на размере и начертании текста, а не на серой подписи.

### 24.6.1. Открытие документа

Нажатие на сам бежевый стикер / карточку открывает полный документ.

Это **не модальное окно и не Z**. Это тот же отдельный технический юридический слой.

Поведение:
- большой белый sticker-layer расширяется почти на весь экран;
- по периметру остаётся тёмный ободок, чтобы сохранялось ощущение отдельного листа;
- внутри показывается полный читаемый текст документа;
- свайп вправо сбрасывает раскрытый документ;
- после свайпа пользователь всегда возвращается именно к исходному юридическому sticker-состоянию со списком 2–3 документов;
- юридический слой не превращается в H/Z-контекст и не использует обычную навигацию разделов;
- у конца длинного документа может появляться спокойная подсказка жеста возврата.

### 24.6.2. Условия продолжения

Основное действие находится **внутри sticker-состояния**, а не в C.

Переход дальше доступен только после принятия всех обязательных документов:
- «Условия использования» — если они показаны;
- «Согласие на обработку персональных данных».

«Согласие на получение рекламы» остаётся добровольным и не блокирует продолжение.

Юридически документы остаются независимыми, даже если визуально собраны на одном стикере.

Окончательное прикладное действие выполняется только после прохождения обязательных пунктов и повторной проверки доступности временно удержанного ресурса / слота.

### 24.7. Удержание временного слота

Удержание слота должно быть коротким и автоматически освобождаться, если пользователь бросил вход / регистрацию / обязательные согласия.

Точный TTL не фиксируется на этапе UI-проектирования. Он должен быть отдельным продуктовым параметром с учётом:
- среднего времени входа;
- среднего времени регистрации;
- среднего времени чтения обязательных условий;
- нагрузки и конкуренции за слоты.

Нельзя считать 15 минут обязательной нормой. UX и backend должны уметь показывать истечение удержания и корректно вернуть пользователя к выбору времени, если слот уже освобождён или занят.


## 25. End-to-end контур конечного пользователя

Этот раздел — контрольная карта всего согласованного пользовательского пути. Он не заменяет подробные правила выше, а связывает их в одну последовательность.

### 25.1. Вход по ссылке представителя

1. Конечный пользователь получает ссылку от конкретного представителя.
2. Открывается **Welcome Sticker**:
   - тёмный фон;
   - по центру белая прямоугольная бумажка с прямыми углами и мягкой тенью;
   - системно подставляется только «Приглашение от …»;
   - заголовок и приветственный текст создаёт сам представитель в своём интерфейсе;
   - свайп вправо или влево убирает welcome-слой.

### 25.2. Прикладной flow записи

После Welcome пользователь входит в контекст представителя.

Header H:
- A — визуальный идентификатор представителя;
- B — имя / название представителя;
- C — главное действие текущего шага;
- D — Chat.

Локальные заголовки шагов всегда остаются внутри Z и не перетекают в B.

Последовательность:
1. Z — выбор рабочего пространства;
2. Z — выбор одной или нескольких услуг / процедур;
3. Z — календарь / выбор даты;
4. Z — доступные временные слоты;
5. Z — итог / подтверждение.

Следующий шаг открывается через C и кладёт новый Z-пласт поверх предыдущего.

Свайп вправо внутри этого flow:
- снимает верхний Z-пласт;
- возвращает на предыдущий шаг;
- не открывает E/F.

C всегда видима в H.

### 25.3. Подтверждение и идентификация

Когда пользователь нажимает C = «Подтвердить»:

- если он уже авторизован и обязательные юридические состояния актуальны — прикладное действие завершается;
- если авторизация нужна — выбранный слот временно удерживается;
- открывается **Auth Sticker** на тёмном фоне.

Auth Sticker:
- Email;
- Пароль;
- глаз показать / скрыть пароль;
- основная кнопка входа внутри стикера;
- «Зарегистрироваться»;
- «Забыли пароль?».

Уже существующий пользователь после успешного входа возвращается к незавершённому действию.

### 25.4. Регистрация

Нажатие «Зарегистрироваться» переводит из sticker-состояния в обычный H + Z.

Форма Z:
- Имя — обязательно;
- Фамилия — необязательно;
- Телефон — обязательно;
- Email — обязательно;
- Пароль — обязательно;
- Повтор пароля — обязательно;
- в полях пароля есть показать / скрыть.

C = «Подтвердить».

### 25.5. Юридический технический слой

После идентификации / регистрации система показывает отдельный **LEGAL STICKER**, если есть неподтверждённые обязательные документы.

Это не H/Z и не модалка.

В большом белом стикере лежат 2–3 одинаковых бежевых стикера-документа:
- «Условия использования» — обязательное, только если ещё не принято;
- «Согласие на обработку персональных данных» — обязательное;
- «Согласие на получение рекламы» — необязательное.

У каждой карточки:
- одинаковый размер;
- прямые углы;
- мягкая тень;
- жирный чёрный заголовок;
- обычный чёрный текст «обязательное» / «необязательное»;
- toggle справа.

Нажатие на карточку открывает полный документ внутри расширенного белого sticker-layer. Свайп вправо возвращает к списку документов.

Продолжение возможно только после всех обязательных подтверждений.

### 25.6. Завершение действия

После юридической проверки:
- повторно проверяется доступность временно удержанного слота;
- действие окончательно фиксируется;
- пользователь возвращается в основной экран выбранного представителя;
- новая запись появляется среди предстоящих;
- после наступления события она переходит в историю;
- рядом могут жить бонусные / лояльностные / другие программы представителя.

### 25.7. Общий экран конечного пользователя

На корневом экране:
- A — аватар / инициалы пользователя;
- B — его имя;
- C — отсутствует, если нет одного главного действия;
- D — Chat с badge.

Z:
- «Предстоящие визиты» — серый локальный заголовок + горизонтальные карточки;
- «Представители / пространства» — серый локальный заголовок + горизонтальные карточки Profile-контекстов.

Свайп Z вправо открывает F.

F:
- F1 — «Представители»;
- отдельный F — «История»;
- остальные разделы добавляются только по реальным продуктовым сценариям.

### 25.8. История

Экран «История» — отдельный Z с вертикальной хронологией событий / взаимодействий.

- опорная точка — ближайшее следующее событие;
- движение в сторону будущего показывает следующие события;
- движение в сторону прошлого показывает уже состоявшиеся;
- карточка истории описывает конкретное взаимодействие;
- внутренняя компоновка карточки будет проектироваться отдельно.

Открытие события:
- C становится контекстным действием повторного входа в нужный сервис;
- для сценария услуг — «Записаться».

### 25.9. Представители

Экран «Представители»:
- отдельный Z;
- вертикальный список Profile-карточек;
- сортировка будет добавлена отдельно;
- карточка не создаётся заново, а берётся из Profile соответствующего представителя.

После открытия представителя:
- A — его визуальный идентификатор;
- B — его имя / название;
- C — главное действие этого типа представителя;
- D — Chat с ним;
- Z — данные взаимодействия, история коммуникации, бонусные / другие программы.

### 25.10. Chat

Нажатие D = Chat доступно в тех контекстах, где Chat существует.

Если D нажата в контексте конкретного представителя:
- сразу открывается его диалог;
- A — иконка / аватар представителя;
- B — имя / название;
- C — открыть список представителей / контактов;
- D — скрепка для вложений;
- Z — переписка;
- снизу composer и кнопка отправки.

Если Chat открыт из общего профиля:
- B = «Чат»;
- A неактивна;
- Z — вертикальный список карточек представителей;
- после выбора открывается конкретный диалог.

В конкретном диалоге:
- нажатие A/B открывает настройки / контекст собеседника;
- C переключает Z в список представителей;
- D = скрепка;
- отправка сообщения живёт в composer, а не в Header;
- свайп вправо выводит к F-уровню.

Chat, открытый посреди booking flow, не должен уничтожать текущий Z-stack: после возврата пользователь продолжает с прежнего шага.

### 25.11. Что остаётся специально не детализированным

Не считаются потерянными или забытыми — они сознательно отложены до реального макета / данных:
- точные внутренности карточки визита;
- точные внутренности карточки истории;
- финальные размеры и типографика карточек;
- точные оттенки E/F;
- место и вид сортировки «Представителей»;
- детали восстановления пароля;
- редкие состояния ошибок / пустых данных / истечения временного удержания.


## 26. Коррекции визуального эталона после PDF-просмотра

Этот раздел фиксирует обязательные поправки к визуальному PDF-эталону. При расхождении с ранними схемами приоритет имеет этот раздел.

### 26.1. Welcome Sticker

- белый прямоугольный стикер расположен **строго по центру экрана**;
- слева и справа от него остаётся только небольшой тёмный отступ — ориентир **10–15 px максимум**;
- сверху и снизу расстояние визуально равнозначное;
- стикер имеет мягкую теневую оболочку, чтобы не восприниматься как белая «дыра» на тёмном фоне;
- приветственный текст остаётся контентом представителя; системно подставляется только «Приглашение от …».

### 26.2. Календарь

В V2 **не проектируется новый календарь**.

Используется существующий канонический Calendar UI приложения:
- переключение месяца стрелками влево / вправо;
- заполнена вся календарная сетка, включая соседние даты предыдущего / следующего месяца;
- сохраняются существующие различия рабочих, выходных, текущей и выбранной даты;
- сохраняется действующая логика выбора даты;
- меняется только визуальная палитра: прежние коричневые акценты переводятся в чёрные, прежние бежевые — в новый утверждённый бежевый;
- геометрия и поведение календаря не переизобретаются.

### 26.3. Временные слоты

- временные слоты показываются **по три в ряд**, если ширина 390 px это позволяет;
- это не округлые карточки, а компактные sticker-контролы;
- прямые / острые углы;
- визуальный язык родственен карточкам услуг / процедур;
- одинаковая базовая геометрия;
- равномерные небольшие промежутки.

### 26.4. Подтверждение записи

В итоговом Z:
- представитель / пространство показывается первым;
- выбранные услуги / процедуры идут **вертикальным столбиком**, каждая отдельной строкой;
- не объединять их через «+» в одну строку;
- после даты / времени используется тонкая разделительная линия, не доходящая до боковых краёв;
- ниже: стоимость;
- затем скидка, если она есть;
- затем итог;
- кнопка C «Подтвердить» должна целиком помещаться в Header без многоточия и визуально быть центрирована внутри своей кнопки.

### 26.5. Экран конкретного представителя

Внутри Z представителя:
- если уже есть накопленная история взаимодействия, первым может идти верхний блок сводных данных / метрик по работе с этим представителем;
- если такой истории ещё нет, естественным первым содержательным блоком становятся предстоящие визиты;
- **предстоящие визиты идут горизонтальной лентой вправо**, несколько карточек не складываются вертикально;
- программы / бонусные / иные программы представителя также идут **горизонтальной лентой вправо**, а не вертикальным стеком;
- карточки представителя / пространства по-прежнему берутся из Profile и отдельно заново не проектируются.

### 26.6. Каноническая геометрия F-колоды

Предыдущие схемы с плитками, вертикальной лестницей и одинаковыми полноразмерными листами признаны неправильными.

**F и Z — зеркальные по направлению поверхности.**

Канонический принцип:
- **Z уходит вправо**;
- у Z закругление находится **с левой стороны**, то есть со стороны центра / зазора;
- **F уходит влево**;
- у F закругление находится **с правой стороны**, то есть также со стороны центра / зазора;
- между F и Z всегда есть видимый промежуток / воздух;
- F визуально собирается как вложенная стопка разного видимого размера;
- **самая большая F-карта лежит снизу / глубже всех и ближе всего к Z**;
- следующая карта визуально чуть меньше и смещена левее;
- верхняя / самая передняя по визуалу карта — самая маленькая и находится дальше всего слева;
- нижние карты видны как вложенные слои, а не как отдельные строки меню;
- надпись читается только у текущей выбранной / активной карты; подписи скрытых слоёв не должны торчать одновременно.

Схема принципа:

```text
ЛЕВО                                         ПРАВО

      F3
   ╭────────╮
   │        ╰╮
   │      F2 ╰╮
   │          ╰╮
   │        F1  ╰╮      GAP      ╭────────────── Z
   │             │                │
   │             │                │
   │             │                │
   ╰─────────────╯                │
                                  │
                                  ╰──────────────
                ↑                 ↑
        F закруглена справа   Z закруглена слева

F раскрывается / уходит влево.
Z раскрывается / уходит вправо.
```

Это именно зеркальная пара по направлению:
- внутренний край F смотрит вправо и закруглён;
- внутренний край Z смотрит влево и закруглён.

Точная разница размеров между F1/F2/F3, ширина видимых слоёв, GAP, радиусы и easing утверждаются на интерактивном прототипе. Но правило зеркальности и визуальной иерархии размеров является обязательным.

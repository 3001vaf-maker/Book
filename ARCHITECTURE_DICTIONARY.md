# Book — архитектурный словарь

## Назначение

Единый словарь архитектуры проекта Book. Используется вместе с `DESIGN_DICTIONARY.md`.

## 1. Структура приложения

| English | Русский | Значение |
|---|---|---|
| FOLDER | Папка | Структурный раздел приложения. Может содержать другие папки и данные. |
| DATA | Данные | Информация, принадлежащая конкретной папке. |
| FOLDER CONTROLLER | Управление папкой | Код, отвечающий за работу конкретной папки. |

**Важно:** `FOLDER` в архитектуре означает структурную сущность. Её визуальное представление — UI-компонент `FOLDER UI`.

Термин `MODULE / МОДУЛЬ` не используется как альтернативное название структурной папки.

## 7. Ответственность

```text
CORE
└── центральное управление приложением и навигацией

FOLDER
└── структурная единица приложения
    └── FOLDER CONTROLLER
        └── управление этой папкой

UI
└── единые визуальные компоненты

DESIGN DICTIONARY
└── утверждённые визуальные правила

styles.css
└── единый источник CSS-реализации
```

## 8. Единый поток

Для открытия верхнеуровневой папки поток должен быть однозначным:

```text
CORE
  ↓
команда / действие
  ↓
FOLDER CONTROLLER
  ↓
данные + состояние
  ↓
UI COMPONENT
  ↓
отображение
```

UI не определяет структуру приложения. Контроллер папки не создаёт собственную визуальную систему.

## 9. Правило единственного источника

Одна сущность — одно имя — одно место ответственности.

Один UI-компонент имеет одну реализацию во всём приложении. Функциональные папки используют общий UI и не создают собственные копии компонентов.

Варианты одного компонента реализуются через вариант (`variant`), а не через дубликат компонента.

Пример:

```text
FOLDER UI
├── default — обычная папка
└── feature — большая папка
```

## 10. Единый дизайн

Все UI-компоненты используют правила из `DESIGN_DICTIONARY.md`.

Цвета, типографика, отступы, радиусы, размеры, иконки и состояния реализуются через общий `styles.css`. Функциональные папки не получают собственные CSS-файлы.


```text

```

`MODULE / МОДУЛЬ` не используется как второе название папки.

## 12. Реестр UI-функций — с 1 сентября 2026

С 1 сентября 2026 года в проекте Book введён отдельный живой реестр UI-функций:

`UI_FUNCTIONS_DICTIONARY.md`

Этот документ не заменяет архитектурный словарь и не переписывает архитектуру. Он дополняет её практическим реестром существующих UI-функций и их единственных реализаций.

### Правило при новых ТЗ

При каждом новом исполнении ТЗ, если затрагивается UI, перед созданием новой UI-функции необходимо проверить `UI_FUNCTIONS_DICTIONARY.md`.

Порядок:

```text
Новое ТЗ
  ↓
проверка UI_FUNCTIONS_DICTIONARY.md
  ↓
если функция уже существует → использовать существующую
  ↓
если функции нет → определить место новой реализации
  ↓
создать функцию только при необходимости
  ↓
одновременно внести её в UI_FUNCTIONS_DICTIONARY.md
```

Нельзя создавать новую UI-функцию только потому, что текущая функция находится в другой папке или имеет другое локальное название, если по назначению это один и тот же компонент.

### Разделение ответственности документов

```text
ARCHITECTURE_DICTIONARY.md
└── что является частью архитектуры и кто за что отвечает

UI_FUNCTIONS_DICTIONARY.md
└── какие UI-функции уже существуют, где находится их реализация и где они используются

DESIGN_DICTIONARY.md
└── как UI-компоненты должны выглядеть и взаимодействовать визуально

ТЗ
└── что необходимо реализовать в рамках конкретной задачи
```

Конкретное ТЗ не должно самовольно создавать новую глобальную UI-архитектуру или дублировать существующий UI-компонент. Если для выполнения ТЗ требуется новое общее UI-решение, оно должно быть согласовано с действующей архитектурой и внесено в `UI_FUNCTIONS_DICTIONARY.md`.

## 13. Workplace → Day → Calendar → Header

### 13.1. Цвет рабочего места

Цвет принадлежит сущности `Workplace` и хранится вместе с данными рабочего места.

При создании и редактировании рабочего места используется общий `colorPicker()` и общая палитра `ui/colors/`, та же система цветов, которая используется Ярлыками.

Для новых и редактируемых рабочих мест выбор цвета является обязательным. Для старых или неполных данных, где цвет ещё отсутствует, применяется единый системный fallback: **чёрный индикатор `#212529`**. Fallback используется только для проявления и не создаёт отдельную палитру или локальный цвет Графика.

### 13.2. Рабочий день не хранит цвет

`Day` хранит факт работы в конкретную дату и ссылку `workplaceId`.

Цвет не копируется в `Day`. При подготовке календарных данных цвет определяется через соответствующий `Workplace`.

```text
Workplace
├── id
└── color
     │
Day ─┴── workplaceId + date + time
     │
     ▼
Calendar data
```

### 13.3. Индикатор даты принадлежит Calendar UI

Цветная точка является общим **индикатором даты Calendar**, а не локальным элементом Графика или Журнала.

`Calendar` владеет:

- местом индикаторов внутри кнопки даты;
- размером точки;
- расстоянием между точками;
- отображением нескольких индикаторов;
- CSS индикаторов.

`Calendar` не знает, что индикатор означает рабочее место. Контроллер передаёт массив готовых метаданных `indicators`, а Calendar только проявляет их.

Полноценный Calendar используется Графиком и `Журнал → Месяц`, поэтому индикаторы рабочих мест проходят через один и тот же Calendar UI. `MonthDayPicker` для выбора дня рождения остаётся отдельным режимом и эти индикаторы не показывает.

### 13.4. Конкретное рабочее место и Общий график

В режиме конкретного рабочего места Calendar показывает рабочие дни и интервалы только выбранного рабочего места. Индикаторы на датах показывают другие рабочие места, использующие эту дату.

В режиме `Общий график` Calendar показывает объединение всех рабочих дат. Интервал `от–до` не показывается, потому что несколько рабочих мест могут иметь разрывы во времени. Вместо интервала отображается сумма фактической продолжительности работы за дату.

Пример:

```text
12:00–15:00 + 17:00–20:00 = 6 ч
```

а не ложный интервал `12:00–20:00`.

Количество дней в общем показателе считается по уникальным календарным датам. Часы суммируются по фактической продолжительности рабочих интервалов.

### 13.5. Header Control и Workplace List

`Header Control` остаётся универсальной оболочкой заголовка и не имеет собственного названия или сущности.

Рабочие места внутри его стандартного Modal проявляются через общий `list()`, а не через отдельную кнопку `Рабочее место → Select → Выбрать`.

Workplace-композиция передаёт в общий List:

- `Общий график` как агрегированную строку там, где агрегированный режим разрешён;
- название рабочего места;
- цветовой индикатор;
- количество дней;
- количество часов;
- выбранное состояние строки.

Нажатие непосредственно на строку является выбором. Выбранная строка использует общее активное/бежевое состояние List.

`Graph`, `Journal` и другие папки не создают собственный визуал Header Control, List или календарных индикаторов. Они только подготавливают данные и передают их общим UI-компонентам.

## 14. Journal → WorkPlan → Availability → TimeGrid → UI

Это каноническая архитектура расписания. Она не переопределяется локальным ТЗ.

### 14.1. Два разных Day

`core/day.js` и `journal/день.js` имеют разные роли и не являются взаимозаменяемыми.

```text
core/day.js
└── WORKPLAN / рабочий план
    ├── хранит рабочие дни
    ├── создаёт / изменяет / удаляет рабочий день
    ├── определяет интервалы работы
    ├── определяет пересечения рабочих интервалов
    └── проверяет, помещаются ли существующие usage после изменения графика

journal/день.js
└── JOURNAL DAY CONTROLLER / экран «День»
    ├── получает готовый WorkPlan
    ├── получает готовые usages
    ├── передаёт их Timeline UI
    └── маршрутизирует нажатия в Record / Break
```

Экран `journal/день.js` не рассчитывает интервалы, пересечения, свободное время или владельца занятости самостоятельно.

### 14.2. Time

`core/time.js` — только техническая математика времени.

Разрешено:
- нормализовать `HH:MM`;
- переводить время в минуты и обратно;
- проверять валидность диапазона;
- проверять техническое пересечение двух диапазонов.

Запрещено:
- знать о Record;
- знать о Break;
- знать о Workplace;
- знать о Journal;
- принимать решение «свободно / занято» для приложения.

### 14.3. Time Usage

`core/time-usage.js` — нейтральный контракт занятости между бизнес-сущностями и Core.

Он владеет:
- нормализованным форматом usage;
- получением usages для `date + workplaceId` через подключённый source;
- проверкой, помещаются ли существующие usages внутрь изменённого рабочего времени;
- освобождением soft usage при удалении рабочего дня через подключённый source.

Он **не владеет Availability** и не содержит второго способа расчёта свободного времени.

Единственный адаптер бизнес-сущностей в usages:

`journal/time-usage-source.js`

```text
Record → hard usage
Break  → soft usage
```

### 14.4. TimeGrid

`core/time-grid.js` — единственная нейтральная сетка занятости времени.

Она получает уже готовые:
- `plan { from, to }`;
- `usages[]`.

И только она вычисляет:
- состояние минуты;
- состояние диапазона;
- доступные начала;
- доступные окончания.

TimeGrid не читает Record, Break, Day, Workplace, Journal и ничего не хранит.

### 14.5. Availability

`core/availability.js` — **единственная публичная точка ответа на вопрос «можно ли занять это время?»**.

Availability собирает:

```text
WorkPlan (core/day.js)
        +
Workplace
        +
Time Usage source
        ↓
TimeGrid
        ↓
Availability API
```

Record, Break и Journal не создают собственные алгоритмы занятости.

Канонические запросы:
- `checkTimeAvailability()`;
- `getTimeAvailabilityAt()`;
- `listAvailableStartTimes()`;
- `listAvailableEndTimes()`.

### 14.6. Record

Record разделён по ответственности:

```text
record-data.js    → физическое хранение Record и Record Events
record-read.js    → собрать Record для чтения
record-service.js → создать / изменить / перенести / отменить
record-events.js  → неизменяемые lifecycle-факты
record-state.js   → проекция текущего lifecycle-состояния
record.js         → UI-процесс создания
record-view.js    → UI-процесс просмотра / редактирования
```

`record.js` и `record-view.js` могут управлять последовательностью экранов, но не рассчитывают занятость. Для времени они обращаются к Availability.

### 14.7. Break

Break использует ту же модель ответственности:

```text
break-data.js    → только физическое хранение
break-read.js    → чтение Break
break-service.js → создать / перенести / удалить Break
break-view.js    → только UI-процесс просмотра / редактирования
```

`break-service.js` проверяет время только через Availability.
`break-view.js` получает варианты времени только через Availability.

### 14.8. Workplace Time

`core/workplace-time.js` — read-model рабочего места и рабочего плана.

Он может:
- получить Workplace;
- получить рабочие даты Workplace;
- получить статистику рабочего графика;
- подготовить индикаторы Calendar;
- прочитать фактический интервал рабочего дня.

Он не является вторым владельцем мутаций Day и не является вторым Availability.

### 14.9. Timetable Day Editor

`timetable/day-editor.js` — UI-контроллер редактирования WorkPlan.

Он:
- показывает поля;
- читает ввод пользователя;
- показывает сообщения об ошибках;
- вызывает `core/day.js` для правил рабочего графика;
- вызывает `core/time-usage.js` только для проверки влияния нового рабочего времени на существующие usages.

Он не реализует свой алгоритм пересечения рабочих интервалов.

### 14.10. Time UI

`ui/time/index.js` владеет только общими визуальными элементами выбора времени:
- `timePicker()`;
- `timeSlots()`;
- wheel UI.

`ui/time/journal-day.js` владеет только визуальной временной шкалой Журнала:
- геометрией шкалы;
- размещением уже готовых usages;
- визуальными слотами;
- событиями нажатия.

Time UI не определяет, свободен ли слот, и не решает, какой бизнес-объект владеет занятостью.

### 14.11. Journal

`journal/journal.js` — контроллер папки Журнал.

Он владеет:
- активным представлением `День / Месяц / Список`;
- выбранной датой;
- выбранным Workplace;
- маршрутизацией между представлениями.

Он не владеет:
- TimeGrid;
- Availability;
- WorkPlan-правилами;
- Record lifecycle;
- Break persistence.

### 14.12. Composition Root

`core.js` — единственное место, где инфраструктурные источники подключаются к нейтральному Core:

```text
Workplace source → configureWorkplaceSource()
Journal usages   → configureTimeUsageSource()
soft release     → configureSoftTimeUsageReleaseSource()
```

Feature-файлы не переподключают эти источники локально.

### 14.13. Жёсткое правило для будущих ТЗ

Обычное продуктовое ТЗ не является разрешением менять эту архитектуру.

Если задача звучит как:
- поменять кнопку;
- добавить поле;
- изменить карточку;
- изменить цепочку экранов;
- добавить действие Record / Break;
- изменить внешний вид Journal;

то существующие владельцы остаются неизменными.

Изменение архитектурной границы допускается только как отдельная архитектурная задача с явным изменением этого словаря и CI-проверок.

# Book — архитектурный словарь

## Назначение

Единый словарь архитектуры проекта Book. Используется вместе с `DESIGN_DICTIONARY.md`.

## 1. Структура приложения

| English | Русский | Значение |
|---|---|---|
| FOLDER | Папка | Структурный раздел приложения. Может содержать другие папки и данные. |
| DATA | Данные | Информация, принадлежащая конкретной папке. |
| FOLDER CONTROLLER | Управление папкой | Код, отвечающий за работу конкретной папки. |

**Важно:** `FOLDER` в архитектуре означает структурную сущность. Её визуальное представление — UI-компонент `FOLDER UI`.

Термин `MODULE / МОДУЛЬ` не используется как альтернативное название структурной папки.

| English | Русский | Значение |
|---|---|---|
| NAVIGATION | Навигация | Перемещение между разделами. |
| BOTTOM NAVIGATION | Нижняя навигация | Нижнее меню приложения. |

## 7. Ответственность

```text
CORE
└── центральное управление приложением и навигацией

FOLDER
└── структурная единица приложения
    └── FOLDER CONTROLLER
        └── управление этой папкой

UI
└── единые визуальные компоненты

DESIGN DICTIONARY
└── утверждённые визуальные правила

styles.css
└── единый источник CSS-реализации
```

## 8. Единый поток

Для открытия верхнеуровневой папки поток должен быть однозначным:

```text
CORE
  ↓
команда / действие
  ↓
FOLDER CONTROLLER
  ↓
данные + состояние
  ↓
UI COMPONENT
  ↓
отображение
```

UI не определяет структуру приложения. Контроллер папки не создаёт собственную визуальную систему.

## 9. Правило единственного источника

Одна сущность — одно имя — одно место ответственности.

Один UI-компонент имеет одну реализацию во всём приложении. Функциональные папки используют общий UI и не создают собственные копии компонентов.

Варианты одного компонента реализуются через вариант (`variant`), а не через дубликат компонента.

Пример:

```text
FOLDER UI
├── default — обычная папка
└── feature — большая папка
```

## 10. Единый дизайн

Все UI-компоненты используют правила из `DESIGN_DICTIONARY.md`.

Цвета, типографика, отступы, радиусы, размеры, иконки и состояния реализуются через общий `styles.css`. Функциональные папки не получают собственные CSS-файлы.

## 11. Терминология

Если речь идёт о структуре приложения:

```text
Папка Сервис
Папка Профиль
Папка Настройки
```

Если речь идёт о визуальном элементе, используется:

```text
FOLDER UI
```

`MODULE / МОДУЛЬ` не используется как второе название папки.

## 12. Реестр UI-функций — с 1 сентября 2026

С 1 сентября 2026 года в проекте Book введён отдельный живой реестр UI-функций:

`UI_FUNCTIONS_DICTIONARY.md`

Этот документ не заменяет архитектурный словарь и не переписывает архитектуру. Он дополняет её практическим реестром существующих UI-функций и их единственных реализаций.

### Правило при новых ТЗ

При каждом новом исполнении ТЗ, если затрагивается UI, перед созданием новой UI-функции необходимо проверить `UI_FUNCTIONS_DICTIONARY.md`.

Порядок:

```text
Новое ТЗ
  ↓
проверка UI_FUNCTIONS_DICTIONARY.md
  ↓
если функция уже существует → использовать существующую
  ↓
если функции нет → определить место новой реализации
  ↓
создать функцию только при необходимости
  ↓
одновременно внести её в UI_FUNCTIONS_DICTIONARY.md
```

Нельзя создавать новую UI-функцию только потому, что текущая функция находится в другой папке или имеет другое локальное название, если по назначению это один и тот же компонент.

### Разделение ответственности документов

```text
ARCHITECTURE_DICTIONARY.md
└── что является частью архитектуры и кто за что отвечает

UI_FUNCTIONS_DICTIONARY.md
└── какие UI-функции уже существуют, где находится их реализация и где они используются

DESIGN_DICTIONARY.md
└── как UI-компоненты должны выглядеть и взаимодействовать визуально

ТЗ
└── что необходимо реализовать в рамках конкретной задачи
```

Конкретное ТЗ не должно самовольно создавать новую глобальную UI-архитектуру или дублировать существующий UI-компонент. Если для выполнения ТЗ требуется новое общее UI-решение, оно должно быть согласовано с действующей архитектурой и внесено в `UI_FUNCTIONS_DICTIONARY.md`.

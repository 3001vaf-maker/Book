# ТЗ-07 — График / сущность «Дата»

## 1. Обязательное правило дополнения существующего приложения

ТЗ-07 реализуется **в уже существующем приложении Book и в его текущем состоянии**.

ТЗ-07 **не создаёт новое приложение и не переписывает существующее приложение**.

ТЗ-07 является очередным расширением уже существующей архитектуры Book и добавляет в неё новую бизнес-сущность:

**E-08 — Дата**

В рамках ТЗ-07 необходимо:

- сохранить существующий архитектурный фундамент Book;
- сохранить все ранее реализованные сущности;
- сохранить ранее реализованную функциональность;
- сохранить существующий UI Core;
- использовать существующий общий CSS;
- использовать уже существующие общие UI-компоненты;
- добавить ветку и функциональность Графика в существующую архитектуру;
- добавить E-08 «Дата» как новую сущность владельца «График»;
- добавить только те общие UI-компоненты или изменения общих компонентов, которые действительно необходимы для реализации ТЗ-07.

### Запрещено

ТЗ-07 не даёт права:

- переписывать приложение целиком;
- создавать новый корень приложения;
- создавать параллельную архитектуру;
- удалять ранее реализованные сущности;
- заменять ранее реализованную функциональность;
- создавать локальные копии существующего UI;
- переносить код из другого приложения;
- изменять несвязанные с ТЗ-07 ветки.

Если для реализации Графика требуется изменение уже существующего общего компонента, изменяется **сам общий компонент Book**, после чего он используется Графиком вместе с остальными ветками приложения.

Таким образом:

```text
СУЩЕСТВУЮЩИЙ BOOK
       │
       ├── существующие сущности
       ├── существующий UI Core
       ├── существующий CSS
       └── существующая функциональность
              │
              ↓
          ТЗ-07
              │
              ↓
       добавляется ГРАФИК
              │
              ↓
        E-08 «Дата»
```

**ТЗ-07 дополняет Book. Оно не заменяет Book.**

---

## 2. Назначение

Реализовать ветку **График** как владельца сущности **E-08 «Дата»**.

Главная задача Графика — сформировать, сохранить и предоставлять бизнес-логике доступный рабочий временной ресурс конкретной даты.

График определяет:

- календарную дату;
- является ли дата рабочей или выходной;
- рабочий временной диапазон рабочей даты;
- доступность временного ресурса даты для последующего использования другими бизнес-сущностями.

График **не создаёт и не управляет сущностью «Запись»**.

Сущность «Запись» будет определена отдельным ТЗ в ветке Журнала.

## 3. Место в архитектуре

```text
BOOK
│
├── Общий UI / UI Core
│   └── Calendar UI Core
│
├── ГРАФИК
│   └── E-08 Дата
│       ├── рабочий / выходной
│       ├── рабочее время
│       └── доступный временной ресурс
│
└── ЖУРНАЛ
    └── будущая сущность «Запись»
```

График является владельцем E-08 «Дата».

Calendar UI Core не является владельцем E-08.

---

## 4. Архитектурная граница Calendar UI Core и Графика

### 4.1. Calendar UI Core

Calendar UI Core является общей системой календарного интерфейса Book.

Он предоставляет:

- переключение месяца и года;
- навигацию `← месяц год →`;
- дни недели;
- календарную сетку;
- даты текущего и соседних месяцев;
- геометрию ячеек;
- общую типографику;
- общие визуальные правила календаря;
- календарное отображение Сб/Вс;
- общие UI-механизмы;
- общие кнопки;
- общие заголовки и подзаголовки;
- общий механизм выбора;
- общее модальное окно выбора времени;
- общий CSS.

Calendar UI Core **не хранит бизнес-состояние Графика**.

Он не определяет самостоятельно:

- рабочая дата или выходная;
- рабочий интервал даты;
- доступно ли время для записи;
- можно ли изменить состояние даты;
- можно ли другому бизнес-модулю воздействовать на дату.

Эти решения принадлежат Графику.

### 4.2. Передача состояния

Направление данных:

```text
ГРАФИК
   ↓
Calendar UI Core
   ↓
визуальное отображение
```

Не допускается обратная бизнес-зависимость:

```text
Calendar UI Core
   ↓
График
```

Calendar UI Core не должен самостоятельно получать, хранить или изменять состояние E-08.

График передаёт календарю только те данные и визуальные состояния, которые разрешены его собственной бизнес-логикой.

---

## 5. Сущность E-08 «Дата»

E-08 является самостоятельной бизнес-сущностью.

### 5.1. Состояния

У даты существует только два состояния:

```text
Рабочий день
Выходной день
```

Третьего состояния нет.

Изначально все даты являются **выходными**.

### 5.2. Структура

```text
E-08 Дата
│
├── календарная дата
├── состояние
│   ├── рабочий
│   └── выходной
│
└── если состояние = рабочий
    ├── начало рабочего времени
    └── окончание рабочего времени
```

Рабочий интервал не является отдельной сущностью.

Он является частью состояния E-08 «Дата».

---

## 6. Рабочий временной ресурс

Рабочий диапазон даты является ресурсом времени, который График предоставляет другим бизнес-процессам.

Например:

```text
03.09.2026
Рабочий день

10:00 — 18:30
```

Это означает, что дата предоставляет рабочий временной ресурс в данном диапазоне.

График не создаёт запись внутри этого ресурса.

Он только определяет и предоставляет ресурс.

---

## 7. Будущее взаимодействие с Журналом

Журнал будет владельцем отдельной сущности «Запись».

```text
ГРАФИК
  │
  │ предоставляет
  ↓
рабочий временной ресурс Даты
  │
  ↓
ЖУРНАЛ
  │
  └── создаёт «Запись»
```

Журнал не получает прямого права изменять внутреннее состояние E-08.

Если Журналу потребуется воздействовать на рабочий ресурс Даты, он обращается к Графику через предусмотренный бизнес-механизм запроса.

График самостоятельно:

1. получает запрос;
2. проверяет допустимость изменения;
3. изменяет принадлежащее ему состояние;
4. возвращает результат.

Таким образом:

**График владеет Датой и временем.**

**Журнал владеет Записью.**

**Журнал не владеет временем.**

---

## 8. Критическое бизнес-правило доступности времени

Сущность «Запись» не может занимать время, которое не предоставлено Графиком как доступный рабочий ресурс.

Запрещено создавать запись:

- на выходной день;
- вне рабочего диапазона;
- поверх уже занятого времени другой записью;
- поверх недоступного времени;
- поверх перерыва или другого ограничения рабочего ресурса;
- с пересечением другой записи.

Это ограничение должно обеспечиваться **бизнес-логикой**, а не только интерфейсом.

Нельзя рассчитывать только на то, что UI скроет недоступное время.

Даже при прямом бизнес-запросе создание записи на недоступное время должно быть отклонено.

---

## 9. Изменение рабочего дня

### 9.1. Перевод выходного в рабочий

Пользователь выбирает одну или несколько выходных дат.

Задаёт:

```text
Начало
Окончание
```

После применения выбранные даты становятся рабочими и получают указанный рабочий диапазон.

Например:

```text
03
04
05
```

получают:

```text
10:00 — 18:00
```

После этого каждая дата хранит собственный результат.

Позднее другой набор дат может получить другой диапазон:

```text
06
07
08

12:00 — 21:00
```

Рабочий диапазон является свойством конкретной даты.

### 9.2. Перевод рабочего дня в выходной

Если выбранная дата является рабочей, основная операция позволяет сделать её выходной.

При переводе даты в состояние «выходной» её рабочий диапазон удаляется.

То есть:

```text
Рабочая дата
10:00 — 18:30
       ↓
Выходной
```

После этого у даты больше нет рабочего начала и окончания.

---

## 10. Однородный выбор дат

При выборе нескольких дат первая выбранная дата определяет тип операции.

### Если первая дата рабочая

Система переходит в режим:

```text
Сделать выходным
```

Можно выбирать только рабочие даты.

Кнопка:

**Применить выходной**

### Если первая дата выходная

Система переходит в режим:

```text
Сделать рабочим
```

Можно выбирать только выходные даты.

Кнопка:

**Применить рабочий день**

Смешанный выбор рабочих и выходных дат в одной операции не допускается.

### 10.1. Снятие выбора

Повторное нажатие на выбранную дату снимает её с выбора.

Если выбор полностью пуст:

```text
выбрано 0 дат
```

система возвращается в нейтральное состояние.

Следующая выбранная дата снова становится первой и определяет тип операции.

---

## 11. Рабочий интервал

В интерфейсе Графика используется общий UI-блок:

```text
Рабочий интервал

Начало        Окончание
10:00         18:30
```

Выбор времени осуществляется через общий механизм выбора времени.

Рабочий интервал:

- не является отдельной сущностью;
- не хранится отдельно от даты;
- используется как инструмент назначения времени выбранным датам.

После применения значения становятся частью состояния соответствующих дат.

---

## 12. Корректировка рабочего дня

Для уже рабочей даты допускается отдельный механизм **«Корректировка дня»**.

Он не заменяет основную операцию перевода рабочего дня в выходной.

Предназначение механизма:

- изменить параметры уже рабочего дня;
- не переводить его автоматически в выходной;
- работать через принадлежащий Графику механизм изменения даты.

Конкретный состав корректировки определяется отдельно, если потребуется расширение этой функции.

---

## 13. Calendar UI

### 13.1. Верхняя часть

Используется общий календарный контрол:

```text
← Сентябрь 2026 →
```

Отдельный «заголовок календаря» не создаётся.

Это общий механизм выбора месяца и года.

### 13.2. Дни недели

```text
Пн Вт Ср Чт Пт Сб Вс
```

Суббота и воскресенье отображаются красным как **календарные выходные**.

Это не означает, что дата автоматически является выходной в Графике.

Суббота или воскресенье могут быть рабочими.

---

## 14. Календарная сетка

Calendar UI Core предоставляет одну общую календарную сетку.

Она используется разными ветками Book.

Один экземпляр календаря может использоваться Графиком, другой — Месяцем.

Текущий месяц каждого экземпляра независим.

Например:

```text
График → Сентябрь 2026
Месяц  → Август 2026
```

Работа с сентябрём в Графике не переключает календарь Месяца на сентябрь.

Каждый владелец передаёт своему экземпляру календаря собственное состояние и бизнес-логику.

---

## 15. Даты соседних месяцев

Даты соседних месяцев являются полноценными активными датами.

Например, в сетке сентября:

```text
31 августа
1–30 сентября
1–4 октября
```

31 августа и 1–4 октября:

- полностью активны;
- доступны для выбора;
- могут быть сделаны рабочими;
- могут быть сделаны выходными;
- сохраняют своё собственное состояние.

Визуально они приглушены относительно дат активного месяца.

Серый цвет означает только принадлежность к соседнему месяцу.

Он не означает недоступность.

---

## 16. Визуальное отображение рабочего статуса

Правило отображения рабочего статуса передаётся через бизнес-логику владельца данных в календарный UI.

Сам Calendar UI Core не определяет, какие даты являются рабочими.

Для рабочей даты:

- номер становится немного крупнее;
- номер становится немного жирнее.

Это правило применяется во всех календарях данного класса **только тогда, когда соответствующий владелец календаря передал состояние рабочей даты для отображения**.

### 16.1. Календарные выходные

Суббота и воскресенье сохраняют красный цвет номера.

Если суббота или воскресенье являются рабочими:

```text
красный
+
немного крупнее
+
немного жирнее
```

Таким образом:

```text
красный → календарный выходной
жирность + размер → рабочее состояние
```

Эти признаки не должны конфликтовать.

---

## 17. Отображение рабочего времени

Для рабочей даты активного месяца внутри ячейки отображается:

```text
┌──────────────────┐
│                  │
│        3         │
│                  │
│                  │
│ 10:00            │
│ 18:30            │
└──────────────────┘
```

Правила:

- номер даты находится в центре ячейки;
- рабочее время находится в нижней левой части;
- `10:00` — начало;
- `18:30` — окончание;
- время отображается мелким шрифтом;
- номер даты отображается обычным размером, если дата не является рабочей;
- рабочая дата получает увеличенный и более жирный номер.

Рабочее время отображается **только у дат активного месяца**.

Для дат соседних месяцев:

- их рабочий статус может отображаться;
- их рабочее время в ячейке не отображается.

---

## 18. Состояния выбора

### Рабочая дата

При выборе рабочей даты:

```text
бежевая заливка
тёмно-коричневый текст
```

### Выходная дата

При выборе выходной даты:

```text
тёмно-коричневая заливка
белый текст
```

Цвета соответствуют существующей системе CSS Book.

Выбор является отдельным визуальным состоянием и не заменяет бизнес-состояние даты.

---

## 19. Независимость календарных выходных и состояния Графика

Нельзя приравнивать:

```text
Суббота / воскресенье
```

к:

```text
Выходной день Графика
```

Это разные понятия.

Пример:

```text
Суббота
→ календарный выходной
→ красный номер

Но если График сделал дату рабочей:
→ номер жирнее
→ номер немного крупнее
→ дата имеет рабочий диапазон
```

---

## 20. Хранение данных

Состояние E-08 должно сохраняться таким образом, чтобы после повторного открытия приложения сохранялись:

- календарная дата;
- состояние рабочий/выходной;
- рабочее начало;
- рабочее окончание, если дата рабочая.

При состоянии «выходной» рабочее начало и окончание не сохраняются как активный рабочий ресурс.

Физическая технология хранения определяется архитектурой приложения.

ТЗ фиксирует бизнес-структуру и требования к сохранности данных, а не конкретную технологию базы данных.

---

## 21. Требования к данным для будущего Журнала

График должен предоставлять бизнес-логике Журнала возможность получить для конкретной даты:

1. существует ли рабочий день;
2. является ли дата рабочей или выходной;
3. какой рабочий ресурс доступен;
4. какие интервалы недоступны, если такие ограничения будут добавлены в будущем;
5. можно ли использовать запрошенное время для создания записи.

Журнал не должен самостоятельно реконструировать рабочее время Графика.

---

## 22. Запрет прямого изменения Даты другими сущностями

E-08 принадлежит Графику.

Другие бизнес-сущности не должны напрямую изменять:

- статус даты;
- начало рабочего дня;
- окончание рабочего дня;
- доступный временной ресурс.

Изменение выполняется только через предоставленный Графиком бизнес-механизм.

Это необходимо для сохранения единственного владельца состояния и предотвращения петель и конфликтов данных.

---

## 23. Не входит в ТЗ-07

В ТЗ-07 не реализуются:

- сущность «Запись»;
- клиент внутри записи;
- услуга внутри записи;
- Журнал;
- представления «День / Месяц / Список» как отдельная бизнес-логика;
- создание записи;
- перенос записи;
- отмена записи;
- бизнес-логика клиента и услуги;
- конкретная реализация перерыва как отдельной сущности;
- другие бизнес-сущности Журнала.

Они реализуются своими ТЗ и взаимодействуют с Графиком через его бизнес-контракт.

---

## 24. Использование общего UI

График не создаёт собственную систему UI.

Используются существующие общие компоненты Book.

Если необходимый компонент отсутствует:

1. компонент создаётся в общем UI;
2. компонент не копируется внутрь Графика;
3. после создания График использует общий компонент.

---

## 25. Использование общего CSS

График не создаёт отдельную систему CSS.

Используется существующий CSS Book.

Все цвета, типографика, размеры, состояния и общие визуальные правила должны соответствовать общей системе.

Локальный дубль CSS не допускается.

## 26. Мобильные требования

Календарь должен оставаться полноценным рабочим календарём, а не превращаться в маленький date-picker.

Ячейки должны иметь достаточный размер для одновременного отображения:

- номера даты;
- визуального состояния;
- рабочего времени;
- будущих календарных данных, которые будут добавляться бизнес-логикой.

Сетка должна быть пригодна для дальнейшего расширения без изменения фундаментальной модели календаря.

## 27. Критерии готовности

ТЗ-07 считается выполненным, если:

- существует E-08 «Дата» внутри владельца График;
- ТЗ реализовано как дополнение существующего приложения Book, без переписывания или замены существующей архитектуры;
- у даты существуют только два состояния: рабочая и выходная;
- первоначальное состояние даты — выходной;
- рабочая дата имеет начало и окончание рабочего времени;
- выходная дата не имеет рабочего временного диапазона;
- рабочий диапазон хранится как часть Даты, а не как отдельная сущность;
- несколько дат могут получить один диапазон;
- разные даты могут иметь разные диапазоны;
- соседние месяцы полностью активны;
- состояние соседних дат может изменяться;
- рабочее время соседних дат не отображается в сетке активного месяца;
- календарные Сб/Вс остаются красными независимо от рабочего статуса;
- рабочий статус отображается увеличением и утолщением номера;
- выбор рабочей даты использует бежевую заливку и тёмно-коричневый текст;
- выбор выходной даты использует тёмно-коричневую заливку и белый текст;
- однородный выбор не позволяет смешивать рабочие и выходные даты;
- перевод рабочей даты в выходную удаляет её рабочий диапазон;
- Calendar UI Core не хранит состояние Графика;
- График является единственным владельцем состояния E-08;
- будущий Журнал не сможет создать Запись вне предоставленного Графиком рабочего ресурса;
- ранее исполненная функциональность Book не удалена, не заменена и не переписана;
- общий UI и общий CSS не дублируются и не заменяются локальной реализацией Графика.

# ТЗ-02 — Сущность «Человек / профиль клиента»

## 1. Назначение

Добавить содержимое сущности «Человек / профиль клиента» внутрь уже существующей ветки:

```text
APP
└── Главная
    └── Клиенты
        └── Человек / профиль клиента
```

Это ТЗ описывает только сущность и её пользовательский интерфейс внутри владельца «Клиенты».

ТЗ-02 не изменяет корневую архитектуру, пять разделов нижней навигации, систему владения, общий UI, общий CSS или другие ветки приложения.

## 2. Модель сущности

Базовый объект — сущность человека.

Она может существовать:

- без ID;
- с ID.

Наличие ID не превращает сущность в другой тип объекта.

```text
Сущность без ID
Сущность с ID
```

Название «Клиенты» является названием ветки пользовательского интерфейса. Внутри ветки работают сущности людей.

## 3. ID — связующий якорь

ID является постоянным уникальным якорем, предназначенным в том числе для будущего связывания сущностей.

ID всегда отображается в формате ровно 4 символа.

```text
1      → 0001
12     → 0012
345    → 0345
9999   → 9999
A      → 000A
DS     → 00DS
SFH    → 0SFH
DJFG   → DJFG
A1     → 00A1
```

Допустимы буквы и цифры. Введённое значение приводится к четырёхсимвольному виду.

Один ID не может одновременно принадлежать двум независимым профилям.

После присвоения и сохранения ID не редактируется как обычное поле.

Если ID был удалён из профиля, он не должен автоматически становиться доступным для повторного использования.

Полный механизм назначения, связывания, переноса и отвязки реализуется отдельным ТЗ. Данное ТЗ только фиксирует модель и требования к UI.

## 4. Связывание сущностей

Несколько отдельных сущностей могут в будущем быть связаны в один профиль человека.

```text
Сущность A
Сущность B
Сущность C
      ↓ связывание
Один профиль человека
├── данные A
├── данные B
└── данные C
```

После связывания в списке отображается одна строка профиля, а связанные данные живут внутри этого профиля.

Связанные телефоны, Telegram-аккаунты, email и другие данные не становятся отдельными строками списка.

Если сущность не связана, она остаётся отдельной строкой.

## 5. Главная → Клиенты

Владелец «Главная» содержит большую папку «Клиенты».

Внутри «Клиентов» управляющие действия находятся сверху, список — ниже.

```text
Клиенты

[ + ]    [ Excel ]    [ Сортировка ▼ ]

────────────────────────

список профилей
```

Список растёт вниз. Управляющие элементы не должны перемещаться в конец списка.

## 6. Счётчик

Большая папка «Клиенты» на Главной отображает количество строк, представленных в списке.

Одна отображаемая строка = один профиль человека.

Количество вложенных Telegram, телефонов, email и других данных счётчик не увеличивает.

Пример:

```text
0012 — Александр
├── Telegram 1
└── Telegram 2

0002 — Анна

Антон
```

Счётчик = 3.

## 7. Добавление

Кнопка `[ + ]` открывает общий механизм добавления.

```text
[ Создать ]
[ Добавить из контактов ]
```

Используются только общие UI-компоненты приложения.

## 8. Малая форма создания

Ручное создание выполняется через компактную форму.

Обязательные данные:

- Имя;
- Телефон.

Дополнительные данные:

- Фамилия;
- ID.

```text
Имя
[________________]

Фамилия
[________________]

Телефон
[________________]

ID
[____]

[ Сохранить ]
```

После сохранения профиль появляется в списке.

## 9. Список

Если ID указан:

```text
0012 — Александр
+7-934-567-34-45
```

Если ID отсутствует:

```text
Александр
+7-934-567-34-45
```

Правила:

- ID и имя находятся в одной строке;
- ID стоит первым;
- телефон находится под именем;
- телефон отображается слабее основного имени;
- Telegram username в списке не показывается;
- Telegram ID в списке не показывается;
- список рассчитан на смартфонную ширину.

## 10. Сортировка

Сверху списка находится один общий механизм сортировки.

```text
[ Сортировка ▼ ]
```

Доступны:

- Имя ↑;
- Имя ↓;
- Последнее посещение ↑;
- Последнее посещение ↓.

Сортировка является функцией списка, а не отдельной сущностью.

## 11. Excel

Excel находится сверху, рядом с добавлением и сортировкой.

```text
[ Excel ]
```

Внутри:

```text
[ Выгрузить ]
[ Загрузить ]
[ Шаблон ]
```

Кнопки не должны находиться после списка.

Формат импорта и экспорта может быть уточнён отдельным ТЗ, но архитектура должна поддерживать будущие связанные данные.

## 12. Открытие профиля

Нажатие на имя или строку списка открывает страницу данных выбранного человека.

Не использовать заголовок «Карточка клиента».

Верхняя информационная область сама является визуальным заголовком.

## 13. Верхняя информационная плашка

Фото является частью плашки и используется как визуальная заливка/фон, а не как маленький круглый аватар.

На плашке отображаются:

- ID, если существует;
- имя;
- телефон;
- три компактных показателя в одну строку.

Три показателя:

1. количество записей/посещений;
2. сумма;
3. последнее посещение либо компактный показатель давности.

Пример:

```text
┌─────────────────────────────┐
│            фото             │
│                             │
│  0012                       │
│  Александр                  │
│  +7-934-567-34-45           │
│                             │
│  12       48 000 ₽     12.08│
└─────────────────────────────┘
```

Композиция должна помещаться на экране смартфона без горизонтального скролла.

## 14. Один Accordion

Вся редактируемая часть профиля собирается одним общим Accordion-компонентом.

Не создавать отдельный Accordion для «Клиентов».

Блоки принадлежат одной сущности:

```text
ID                         ▼
Личные данные              ▼
Контактные данные          ▼
Программа лояльности       ▼
Ссылки                     ▼
Ярлыки                     ▼
```

Разбиение данных на блоки не создаёт новых сущностей внутри профиля.

## 15. Личные данные

Содержат:

- Имя;
- Фамилия;
- Пол;
- Дата рождения.

## 16. Контактные данные

Содержат:

- Телефон;
- Telegram;
- Email.

Каждый тип поддерживает несколько значений.

```text
Телефон
+7...
+7...
[ + ]

Telegram
аккаунт 1
аккаунт 2
[ + ]

Email
email 1
email 2
[ + ]
```

Telegram находится только внутри «Контактных данных». Он не является отдельным Accordion-блоком.

Telegram ID хранится как техническое значение и не показывается в обычном пользовательском интерфейсе.

## 17. Ссылки

Используется один механизм добавления:

```text
[ + Добавить ссылку ]
```

Тип и URL выбираются в одной строке:

```text
[ Instagram ▼ ] [ URL____________ ]
```

Типы:

- Instagram;
- ВКонтакте;
- YouTube;
- Facebook;
- Сайт;
- Другое.

После добавления:

```text
Instagram   instagram.com/...   ×
ВКонтакте   vk.com/...          ×
YouTube     youtube.com/...     ×
Сайт        example.com         ×
```

Удаляется конкретная ссылка через `×` либо единый согласованный UI-компонент удаления.

Telegram в этот блок не входит.

## 18. Программа лояльности

Название блока — «Программа лояльности».

Скидка является первым элементом блока.

Если скидка назначена, процент виден прямо в закрытой строке Accordion:

```text
Программа лояльности       10% ▼
```

Если скидки нет, `0%` не отображается.

Выбор скидки — мобильный Number/Wheel Picker от 0 до 100%.

Не использовать слайдер или `+ / −`.

Ниже располагается список назначенных программ:

```text
Скидка                 10%

Программа 1
Программа 2
Программа 3

[ + Программа ]
```

Шесть направлений Программы лояльности являются отдельными дочерними ветками владельца в Настройках. Их собственные сущности реализуются отдельными ТЗ.

## 19. Ярлыки

Название блока — «Ярлыки».

Ярлыки назначаются из общей системы Настроек.

Не создавать отдельную систему ярлыков внутри Клиентов.

## 20. Соглашения

Состояния соглашений должны быть видны при закрытом Accordion.

```text
Согласие ПДН          Дано / Не дано
Согласие на рассылки  Дано / Не дано
```

Они не должны исчезать только из-за сворачивания редактируемых блоков.

## 21. Сохранение

Используется одна общая кнопка:

```text
[ Сохранить ]
```

Она сохраняет изменения всей страницы данных.

Не создавать отдельные кнопки сохранения внутри каждого блока.

## 22. Назад

В конце страницы:

```text
[ Назад ]
```

Возвращает в список «Клиенты».

## 23. Мобильные требования

Интерфейс проектируется прежде всего под смартфон.

Обязательно:

- отсутствие горизонтального скролла;
- отсутствие выхода текста за границы;
- корректная работа Accordion;
- корректное отображение модальных окон;
- корректное отображение длинных имён, телефонов и URL;
- три показателя в верхней плашке должны помещаться в одну строку;
- управляющие действия остаются доступными при большом количестве записей.

## 24. Общий UI и CSS

Все элементы используют общий UI и общий CSS приложения.

Допускаются варианты общих компонентов, если конкретной ветке требуется другой размер или композиция.

Например, «Клиенты» может использовать крупный вариант общей папки/контейнера со счётчиком, не создавая собственного UI-компонента.

Не допускается:

- локальный Accordion;
- локальные кнопки;
- локальные поля;
- локальный CSS;
- дублирование общих компонентов;
- отдельная система цветов;
- отдельная система типографики.

## 25. Граница ТЗ

Это ТЗ не создаёт и не изменяет:

- корневую архитектуру;
- пять разделов нижней навигации;
- другие ветки приложения;
- сущности Журнала;
- сущность Графика;
- сущности Программы лояльности;
- сущность Ярлыков;
- сущность Кошельков;
- полный механизм связывания сущностей.

Оно только добавляет сущность человека/профиль клиента внутрь уже существующей ветки «Главная → Клиенты».

## 26. Критерии готовности

ТЗ считается реализованным только при выполнении всех условий:

1. «Клиенты» находится внутри ветки «Главная».
2. На Главной отображается крупный контейнер «Клиенты» со счётчиком.
3. Счётчик считает отображаемые профили, а не вложенные контакты.
4. Добавление, Excel и сортировка находятся сверху.
5. Список растёт вниз.
6. Создание выполняется через компактную форму.
7. В списке ID, если существует, стоит перед именем в одной строке.
8. Телефон находится под именем.
9. Открывается страница данных без заголовка «Карточка клиента».
10. Фото используется как часть верхней информационной плашки.
11. Три показателя находятся в одной строке.
12. Редактируемые данные собраны одним общим Accordion.
13. Telegram находится внутри «Контактных данных».
14. Ссылки добавляются через один общий механизм.
15. Скидка является первым элементом «Программы лояльности» и видна в закрытом состоянии, если назначена.
16. Соглашения видны при закрытом Accordion.
17. Сохранение выполняется одной общей кнопкой.
18. Есть кнопка «Назад» в список.
19. ID всегда имеет ровно 4 символа и проверяется на уникальность.
20. Архитектура оставляет возможность будущего связывания сущностей.
21. Не создаётся локальный UI или локальный CSS.
22. Интерфейс проверен на смартфонной ширине.

# ТЗ-01-ПРАВКИ-2 — Архитектура представлений Журнала и View Navigation

## 1. НАЗНАЧЕНИЕ

Данное ТЗ является **второй точечной правкой ТЗ-01**.

Цель ТЗ — не переделать Журнал и не реализовать его бизнес-функциональность.

Цель — **достроить отсутствующую архитектурную цепочку представлений Журнала**:

```text
ЖУРНАЛ
└── journal.js
    └── View Navigation
        ├── День
        │   └── день.js
        ├── Месяц
        │   └── месяц.js
        └── Список
            └── список.js
```

В текущем состоянии Журнал содержит `journal.js` и визуальный переключатель:

```text
[ День ] [ Месяц ] [ Список ]
```

но полноценной архитектурной цепочки представлений и рабочего перехода между ними нет.

Данное ТЗ должно **дополнить существующую архитектуру Book отсутствующим звеном**, а не заменять существующую архитектуру.

# 4. АРХИТЕКТУРА, КОТОРУЮ НЕОБХОДИМО ДОСТРОИТЬ

Архитектурный принцип данного ТЗ **не является предложением для свободной интерпретации исполнителем**.

Обязательная логическая структура:

```text
ЖУРНАЛ
│
└── journal.js
    │
    └── View Navigation
        │
        ├── День
        │   └── день.js
        │
        ├── Месяц
        │   └── месяц.js
        │
        └── Список
            └── список.js
```

### Смысл уровней:

**Журнал**

Одна самостоятельная сущность/ветка Book.

**journal.js**

Главная точка входа Журнала.

Он не должен становиться контейнером для реализации всех трёх представлений.

**View Navigation**

Отдельный архитектурный механизм выбора представления Журнала.

Он отвечает за переход между:

- День;
- Месяц;
- Список.

**День / Месяц / Список**

Отдельные представления одной сущности Журнал.

Каждое представление должно иметь собственную точку входа / JS-модуль.

# 5. ВАЖНО: НЕ ПРИДУМЫВАТЬ ДРУГУЮ АРХИТЕКТУРУ

Исполнитель **не имеет права самостоятельно заменять указанную модель другой архитектурной моделью**.

Запрещено решать задачу только следующим способом:

```text
journal.js
 ├── if День
 ├── if Месяц
 └── if Список
```

если это приводит к тому, что все три представления остаются частью одного `journal.js`.

Также запрещено:

- оставлять День / Месяц / Список только визуальными кнопками;
- делать фиктивное переключение без отдельных представлений;
- создавать три визуальных состояния одного и того же DOM вместо архитектурных представлений;
- объединять три представления обратно в один файл;
- создавать новый независимый навигационный механизм, если в Book уже существует подходящий общий механизм;
- создавать параллельную UI/Core-систему только для Журнала.

### При этом

Конкретный физический путь файлов должен соответствовать **реальной архитектуре Book**.

Исполнитель не обязан буквально создавать каталог с названием `View Navigation`, если существующая архитектура Book организует такие слои иначе.

Но логическое разделение ответственности должно сохраниться:

```text
Журнал
→ journal.js
→ View Navigation
→ День / Месяц / Список
→ отдельный JS-модуль каждого представления
```

# 8. VIEW NAVIGATION ДОЛЖЕН БЫТЬ РАБОЧИМ

Существующий визуальный элемент:

```text
[ День ] [ Месяц ] [ Список ]
```

должен стать настоящим механизмом View Navigation.

Требования:

1. При открытии Журнала по умолчанию открывается **День**.
2. `[ День ]` имеет активное состояние.
3. Нажатие `[ Месяц ]` открывает `месяц.js`.
4. Нажатие `[ Список ]` открывает `список.js`.
5. Повторное нажатие `[ День ]` возвращает к `день.js`.
6. Одновременно активно только одно представление.
7. Визуальное активное состояние всегда соответствует реально открытому представлению.
8. Переключение не должно открывать новый независимый Журнал.
9. Пользователь остаётся внутри одной сущности **Журнал**.

Логика:

```text
Журнал
   ↓
View Navigation
   ↓
выбранное представление
   ↓
содержимое выбранного JS-модуля
```

# 9. ОБЩИЙ UI/CORE

View Navigation должен использовать существующую общую систему UI/Core Book.

Перед созданием нового компонента исполнитель обязан проверить, существует ли уже подходящий общий компонент:

- tabs;
- segmented control;
- view switcher;
- navigation;
- selector;
- аналогичный механизм.

### Если подходящий компонент существует:

Использовать его.

Не создавать второй аналогичный компонент.

### Если существующего компонента недостаточно:

Дополнить **существующий UI/Core** минимальным универсальным механизмом.

Новый механизм должен быть пригоден не только для Журнала.

Запрещено создавать отдельную параллельную UI-систему внутри Журнала.

# 10. ОБЩИЙ CSS

Переключатель View Navigation должен использовать существующую единую CSS-систему Book.

До добавления CSS исполнитель обязан проверить:

- существующие классы;
- CSS-переменные;
- размеры;
- состояния active/inactive;
- правила мобильного интерфейса;
- существующие стили кнопок/tabs/navigation.

Запрещено создавать отдельную CSS-систему Журнала.

Если требуется изменение общего CSS:

- изменение должно быть минимальным;
- изменение должно быть обратно совместимым;
- существующие потребители CSS не должны ломаться;
- изменение должно быть непосредственно связано с View Navigation.

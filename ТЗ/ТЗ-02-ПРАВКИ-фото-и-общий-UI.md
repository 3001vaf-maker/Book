# ТЗ-02-ПРАВКИ
## Фото клиента и унификация UI сущности Client

### Статус документа

Это отдельная правка к ТЗ-02 «Человек / профиль клиента».

Настоящий документ не заменяет и не переписывает ТЗ-02.
Все требования ТЗ-02, которые настоящей правкой не затронуты, остаются без изменений.
Правка применяется к существующей реализации Client.

---

# 1. Главный принцип правки

При реализации правки сначала анализируется существующая реализация ТЗ-02. Изменения вносятся минимально необходимым образом в существующую архитектуру.

Переписывание существующей сущности или создание параллельной реализации допускается только при обнаружении архитектурного конфликта, который невозможно устранить точечным изменением; в таком случае реализация останавливается и требуется отдельное согласование.

---

# 2. Запрет самовольных изменений

В рамках настоящей правки запрещено самостоятельно создавать:

- новые сущности;
- новые ТЗ;
- новые архитектурные ветки;
- новые документы;
- параллельные UI-компоненты;
- параллельные CSS-компоненты;
- отдельную систему карточек;
- отдельную систему Select;
- отдельную систему загрузки фотографий;
- локальные CSS-костыли.

Если для реализации обнаруживается необходимость изменения, которое не предусмотрено настоящей правкой, реализация останавливается и требуется отдельное согласование.

---

# 3. Личные данные — существующий Accordion

В Client уже существует раздел **«Личные данные»**. Это кнопка Accordion.

Настоящая правка не создаёт новый Accordion и не изменяет сам принцип его работы.

Внутрь существующего Accordion «Личные данные» добавляется новое поле **«Фото»**.

Фото является полем данных сущности Client, а не отдельной сущностью или отдельным разделом.

---

# 4. Порядок полей в «Личных данных»

Внутри Accordion «Личные данные» поле «Фото» располагается первым.

Структура:

```text
Личные данные
    ↓
Фото
Имя *
Фамилия
Телефон *
...
```

После поля «Фото» сохраняются существующие поля и их существующий порядок, если иное прямо не предусмотрено ТЗ-02.

Фраза «остальные существующие данные» не является отдельным полем интерфейса. В реализации должны использоваться фактически существующие поля Accordion «Личные данные».

---

# 5. Поле «Фото»

Внутри Accordion «Личные данные» должно существовать визуально единообразное поле для добавления фотографии.

Поле должно использовать существующую общую UI/CSS-систему Book.

Не создавать отдельный Client-specific компонент загрузки фотографии, если в проекте уже существует подходящий общий механизм.

Фото сохраняется как данные сущности Client.

---

# 6. Отображение фотографии в карточке Client

Существующая карточка Client должна использовать сохранённое фото следующим образом.

### Если фото загружено

Фото используется как **background / заливка Entity Card**.

Фотография не должна превращаться в отдельную круглую аватарку или отдельный самостоятельный блок внутри карточки.

### Если фото отсутствует

Сохраняется существующее поведение карточки: **заливка с первыми буквами клиента**.

Это состояние не удаляется и не заменяется новым placeholder.

```text
Фото есть
    ↓
Фото как background карточки

Фото нет
    ↓
Существующая заливка + первые буквы
```

---

# 7. Единая Entity Card

Client должен использовать существующий общий компонент **Entity Card**.

Не создавать отдельную карточку специально для Client.

Различается содержание карточки, но не базовая UI/CSS-модель.

---

# 8. Кнопка `[ + ]`

`[ + ]` является общим UI-компонентом Book.

В списке Client кнопка `[ + ]` должна находиться **в правом нижнем углу блока заголовка**.

Используется существующий общий компонент `[ + ]`.

Не создавать новый вариант кнопки.

Если текущая реализация Client содержит `[ + ]` в другом месте или визуально отличается, необходимо исправить общий компонент или общее правило его расположения, чтобы изменение распространялось на все места использования.

---

# 9. Кнопка `[ EX ]`

`[ EX ]` является общим UI-компонентом работы с Excel.

Если `[ EX ]` используется в Client:

- использовать существующий общий компонент;
- не создавать новый вариант;
- сохранить единую высоту, размер и оформление;
- использовать общее позиционирование.

Настоящая правка не добавляет новую Excel-функциональность.

---

# 10. Сортировка

Сортировка является общим UI-компонентом.

В Client элемент сортировки должен находиться **в нижней левой части блока заголовка**.

Он должен иметь:

- единый размер;
- единое оформление;
- единое выравнивание;
- единое положение относительно своего блока.

Не создавать отдельный Client-specific компонент сортировки.

---

# 11. Точное расположение управляющих элементов Client

В блоке заголовка Client управляющие элементы располагаются следующим образом:

```text
[ Сортировка ]                              [ Excel ] [ + ]
```

Правила:

- `[ Сортировка ]` — внизу слева;
- `[ Excel ]` — внизу справа, левее `[ + ]`;
- `[ + ]` — внизу справа, в крайней правой позиции;
- все три элемента имеют одинаковый визуальный размер и единый UI-паттерн;
- каждый элемент сохраняет своё функциональное назначение.

Не менять это расположение самовольно при реализации.

---

# 12. Поля формы

Существующие поля Client сохраняют:

- данные;
- назначение;
- логику;
- валидацию;
- существующее поведение.

Изменяется только визуальное представление там, где оно не соответствует общей UI-системе Book.

Не создавать новые формы вместо существующих.

---

# 13. Select / выпадающие списки

Текущие технически выглядящие системные выпадающие списки Client необходимо привести к единому визуальному компоненту Select Book.

Например, поле **«Пол»** не должно выглядеть как узкий стандартный системный `<select>`, если общая UI-система Book предусматривает стилизованный Select.

### Требования к Select

Select должен иметь единый:

- размер;
- высоту;
- ширину в рамках контейнера;
- шрифт;
- размер текста;
- скругление;
- внутренние отступы;
- стрелку;
- визуальные состояния;
- внешний вид раскрывающегося меню.

Select должен выглядеть как полноценный элемент интерфейса Book, а не как стандартный технический HTML-контрол.

При этом существующая логика и данные поля не изменяются.

---

# 14. Общий Select

Если общий Select уже существует, Client должен использовать именно его.

Не создавать Client-specific Select или отдельные варианты Select для отдельных полей.

Если существующий общий Select реализован неправильно, исправляется общий Select, а не создаётся второй вариант.

---

# 15. Общий UI/Core/CSS

Все изменения настоящей правки должны использовать существующие:

- UI;
- Core;
- CSS;
- компоненты;
- дизайн-токены;
- типографику;
- размеры;
- отступы;
- состояния.

Главный принцип:

> **Один общий компонент — одно поведение и один визуальный стандарт во всех местах его использования.**

---

# 16. Исправление существующего UI

Если визуальная проблема Client вызвана общим компонентом, исправляется общий компонент или общее правило его использования.

```text
Общий компонент
        ↓
     исправление
        ↓
существующие места использования
```

Не создавать локальный исправленный компонент только для Client.

Цель — исправить первопричину на уровне общей системы.

---

# 17. Проверка существующей архитектуры

Перед изменениями необходимо проверить фактическую реализацию Client и определить:

- как реализован Accordion «Личные данные»;
- как реализованы существующие поля;
- как реализована Entity Card;
- как реализованы `[ + ]`, `[ EX ]` и сортировка;
- какой Select используется;
- какие общие UI/Core/CSS-компоненты уже существуют.

Реализация должна опираться на фактическую архитектуру проекта, а не на предположения.

---

# 18. Проверка уже реализованного

При реализации необходимо проверить, что правка не нарушает уже реализованные:

- ТЗ-01;
- ТЗ-01-ПРАВКИ;
- ТЗ-02;
- существующую архитектуру Book;
- существующий UI/Core/CSS;
- существующие сущности и их связи.

Настоящая правка не должна становиться причиной разрушения или переписывания уже работающих частей приложения.

---

# 19. Мобильная реализация

Все изменения должны корректно работать на смартфонной ширине.

Не допускаются:

- горизонтальный скролл;
- отдельная desktop-версия;
- отдельная мобильная копия компонентов;
- локальные CSS-костыли для отдельных размеров экрана.

---

# 20. Что настоящая правка НЕ меняет

Настоящая правка не изменяет:

- сущность E-01 Client;
- владельца Client;
- идентификатор Client;
- существующую бизнес-логику Client, кроме явно указанных изменений;
- нижнюю навигацию;
- другие сущности;
- ТЗ-01;
- ТЗ-01-ПРАВКИ;
- ТЗ-02 как основной документ требований.

Настоящий документ является только дополнением к ТЗ-02.

---

# 21. Критерии готовности

### Personal Data

- [ ] «Личные данные» остаётся существующим Accordion.
- [ ] Фото добавлено внутрь Accordion.
- [ ] Фото является первым полем Accordion.
- [ ] После фото идут фактически существующие поля Client.
- [ ] Новый отдельный Accordion не создан.

### Фото

- [ ] Фото можно добавить через «Личные данные».
- [ ] Фото сохраняется вместе с Client.
- [ ] При наличии фото оно используется как background Entity Card.
- [ ] При отсутствии фото сохраняется существующая заливка с первыми буквами.
- [ ] Отдельная avatar-модель не создана.

### Entity Card

- [ ] Client использует общий Entity Card.
- [ ] Отдельный Client Card не создан.
- [ ] CSS карточки не продублирован.

### Управляющие элементы

- [ ] Сортировка находится внизу слева блока заголовка.
- [ ] Excel находится внизу справа, левее `[ + ]`.
- [ ] `[ + ]` находится внизу справа, в крайней правой позиции.
- [ ] Все три элемента имеют одинаковый визуальный размер.
- [ ] Используются общие компоненты.
- [ ] Новые варианты компонентов не созданы.

### Select

- [ ] Пол и другие существующие выпадающие поля используют общий визуальный Select.
- [ ] Узкий системный технический вид устранён.
- [ ] Логика существующего поля сохранена.
- [ ] Новый Client-specific Select не создан.

### Архитектура

- [ ] ТЗ-02 не переписано.
- [ ] Настоящий документ используется только как правка к ТЗ-02.
- [ ] Новая сущность не создана.
- [ ] Новый документ, кроме настоящей правки, не создан.
- [ ] Параллельная UI/CSS-система не создана.
- [ ] Самовольные архитектурные изменения не внесены.
- [ ] Уже реализованные части приложения не нарушены.
- [ ] При невозможности точечной реализации выполнение останавливается для отдельного согласования.

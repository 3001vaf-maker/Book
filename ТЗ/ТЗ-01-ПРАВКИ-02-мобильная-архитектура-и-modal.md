# ТЗ-01-ПРАВКИ-02 — Мобильная архитектура смартфона и глобальная система модальных окон

## 1. Назначение

Это корректирующее архитектурное ТЗ к ТЗ-01 и ТЗ-01-ПРАВКИ.

Оно фиксирует два обязательных свойства общего фундамента приложения:

1. приложение проектируется как **mobile-first приложение для смартфонов**;
2. все модальные окна являются частью **единой глобальной UI-системы** и центрируются относительно видимой области экрана.

Это не два локальных исправления отдельных экранов. Оба правила относятся ко всему приложению и должны быть реализованы на уровне общей архитектуры UI/CSS.

---

## 2. Смартфон — базовая платформа

Приложение предназначено прежде всего для смартфона.

Смартфон не является «сжатой desktop-версией». Базовые размеры, сетка, навигация, формы, карточки, списки, кнопки, модальные окна и другие компоненты проектируются от доступного мобильного viewport.

### Обязательные правила

- не использовать фиксированную desktop-ширину;
- не проектировать интерфейс под одну конкретную модель телефона;
- использовать адаптивную ширину контейнера;
- исключить горизонтальный overflow;
- учитывать реальную ширину и высоту viewport;
- учитывать safe area устройства;
- учитывать появление экранной клавиатуры;
- не привязывать критические элементы к фиксированной высоте устройства;
- общие мобильные правила должны находиться в общей системе UI/CSS.

---

## 3. Viewport и safe area

Мобильный фундамент должен использовать корректный viewport для смартфонов.

Для полноэкранных областей нельзя безусловно полагаться на `100vh`, если это приводит к перекрытию браузерными или системными областями. Использовать современные viewport units (`dvh`, `svh`, `lvh`) там, где это необходимо, с корректным fallback.

Общий layout должен учитывать:

```text
env(safe-area-inset-top)
env(safe-area-inset-right)
env(safe-area-inset-bottom)
env(safe-area-inset-left)
```

Особенно это относится к верхней области, нижней навигации, закреплённым действиям и модальным окнам.

---

## 4. Нижняя навигация

Нижняя навигация является общим UI-компонентом приложения.

Она должна:

- работать на узких и широких смартфонах;
- учитывать `safe-area-inset-bottom`;
- не перекрывать основной контент;
- не зависеть от фиксированной высоты конкретного устройства.

---

## 5. Touch-first

Интерактивные элементы рассчитываются для управления пальцем.

Область нажатия не должна быть чрезмерно маленькой. Размеры и отступы должны быть частью общей системы UI, а не задаваться заново в каждой ветке.

---

## 6. Экранная клавиатура

При открытии экранной клавиатуры доступная высота viewport изменяется.

Общий мобильный layout должен корректно реагировать на это изменение.

Поля ввода и основные действия не должны оказываться скрыты клавиатурой.

---

## 7. Глобальная система Modal

Modal — обязательный общий UI-компонент архитектуры.

Все модальные окна приложения должны использовать **один общий Modal system**.

Запрещены отдельные реализации модальных окон внутри:

- Клиентов;
- Профиля;
- Сервиса;
- Программы лояльности;
- других веток приложения.

Если конкретной ветке требуется особый вид модального окна, это должен быть вариант общего компонента, а не новый компонент с собственной системой позиционирования.

---

## 8. Центрирование Modal

Каждое модальное окно должно позиционироваться относительно **видимой области viewport**, а не относительно элемента, из которого оно было вызвано.

Правильная архитектура:

```text
APP VIEWPORT
┌──────────────────────────────┐
│                              │
│           OVERLAY            │
│                              │
│       ┌──────────────┐       │
│       │    MODAL     │       │
│       │              │       │
│       └──────────────┘       │
│                              │
└──────────────────────────────┘
```

Центр Modal Container должен совпадать с центром доступной видимой области с учётом safe area.

Модальное окно нельзя центрировать относительно:

- кнопки;
- карточки;
- Accordion;
- списка;
- локального контейнера;
- страницы конкретной ветки;
- любого другого родительского блока.

---

## 9. Modal Layer

Архитектурно Modal состоит из общего слоя:

```text
Modal Layer
├── Overlay
└── Modal Container
    └── Modal Content
```

Overlay покрывает доступную область приложения.

Modal Container центрируется внутри Modal Layer.

После открытия Modal становится частью глобального слоя приложения и перестаёт зависеть от layout родительской ветки.

---

## 10. Поведение Modal на смартфоне

Модальное окно должно:

- помещаться в доступный viewport;
- учитывать safe area;
- не создавать горизонтальный scroll;
- корректно изменять доступную высоту при появлении клавиатуры;
- иметь внутреннюю прокрутку при большом объёме содержимого;
- сохранять доступность основных действий.

Если содержимое выше доступной области, ограничивается высота Modal Content и прокручивается именно содержимое, а не весь основной экран приложения.

---

## 11. Общий CSS

Правила мобильного контейнера и Modal должны находиться в общей системе `style.css` и/или в централизованном общем UI-механизме проекта.

Нельзя исправлять отдельное модальное окно локальным CSS, если проблема относится к общему позиционированию.

Если одно из модальных окон центрируется неправильно, сначала исправляется общий Modal system.

Аналогично, если несколько экранов имеют одинаковую мобильную проблему, исправляется общий mobile layout/component, а не создаются одинаковые локальные костыли.

---

## 12. Архитектурное расположение общего UI

В существующей архитектуре должен сохраняться единый `UI`.

Функционально в нём должна присутствовать единая система:

```text
UI
├── navigation
├── buttons
├── inputs
├── forms
├── lists
├── cards
├── accordion
├── modals
├── mobile layout
└── ...
```

Фактическое количество файлов и их физическая структура может соответствовать уже существующей реализации, если сохраняется принцип единого владельца компонентов.

---

## 13. Сохранение существующего приложения

Это корректировка фундамента существующего Book.

Нельзя:

- создавать новый корень приложения;
- переписывать приложение с нуля;
- создавать вторую UI-систему;
- создавать второй CSS;
- удалять функциональность ТЗ-02;
- менять `Главная` на `Dashboard`;
- копировать код старого приложения.

Существующая функциональность должна остаться рабочей.

---

## 14. Связь с ТЗ-01-ПРАВКИ

ТЗ-01-ПРАВКИ уже требует полного архитектурного дерева.

Настоящая правка **не изменяет это дерево**.

Она добавляет к нему два глобальных архитектурных ограничения:

```text
Архитектурное дерево
        +
Mobile-first система смартфона
        +
Единая система Modal
```

---

## 15. Критерии готовности

ТЗ считается исполненным только после проверки:

### Смартфон

- [ ] приложение корректно отображается на типичных смартфонных ширинах;
- [ ] отсутствует горизонтальный overflow;
- [ ] нет зависимости от одной фиксированной ширины;
- [ ] viewport настроен корректно;
- [ ] учитывается safe area;
- [ ] нижняя навигация учитывает safe area;
- [ ] интерфейс реагирует на изменение высоты viewport;
- [ ] поля и действия не перекрываются экранной клавиатурой.

### Modal

- [ ] существует единая система Modal;
- [ ] все модальные окна используют её;
- [ ] Overlay покрывает доступный viewport;
- [ ] Modal Container центрируется относительно видимой области экрана;
- [ ] Modal не зависит от родительского элемента;
- [ ] safe area учитывается;
- [ ] при появлении клавиатуры доступная область пересчитывается;
- [ ] большое содержимое прокручивается внутри Modal;
- [ ] нет локальных копий Modal.

### Архитектура

- [ ] используется существующий общий UI;
- [ ] используется единая система CSS;
- [ ] не создан второй корень;
- [ ] ТЗ-02 сохранено;
- [ ] `Главная` не переименована в `Dashboard`.

---

## 16. Порядок исполнения

Исполнять последовательно:

1. проверить фактическое состояние `main`;
2. проверить исполнение ТЗ-01;
3. проверить ТЗ-01-ПРАВКИ и полное архитектурное дерево;
4. проверить существующий UI и CSS;
5. найти фактическую реализацию всех Modal;
6. объединить их под единым Modal system;
7. исправить позиционирование Modal на уровне общего компонента;
8. привести общий layout к mobile-first архитектуре;
9. проверить safe area, viewport, нижнюю навигацию и клавиатуру;
10. проверить ТЗ-02;
11. проверить приложение на нескольких типичных смартфонных viewport;
12. только после проверки отметить ТЗ как `Исполнено`.

**Ключевой принцип:** исправления выполняются на уровне архитектуры общего UI/CSS. Нельзя закрывать проблему набором локальных CSS-костылей в отдельных экранах.

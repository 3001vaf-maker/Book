# ТЗ-03 — Сущность «Человек / профиль клиента»

## 1. Назначение

Добавить сущность «Человек / профиль клиента» внутрь уже существующей ветки:

```text
Главная
└── Клиенты
    └── Человек / профиль клиента
```

Это ТЗ описывает только содержимое и поведение сущности в ветке «Клиенты».

ТЗ не изменяет корневую архитектуру приложения, нижнюю навигацию, владельцев веток, общий UI, общий CSS или другие разделы.

## 2. Модель сущности

Базовый объект — сущность человека.

Сущность может существовать:

- без ID;
- с ID.

ID не является отдельной сущностью и не меняет тип сущности.

```text
Сущность без ID
Сущность с ID
```

В интерфейсе ветка называется «Клиенты», но внутри неё система работает с сущностями людей.

## 3. Связь сущностей

Сущности могут быть связаны в один профиль человека.

Механизм связывания полностью реализуется отдельным этапом. В этом ТЗ необходимо только сохранить правильную модель данных и UI-структуру для будущей связи.

Правило результата связи:

```text
Сущность A
Сущность B
Сущность C
       ↓ связь
Один профиль человека
├── данные A
├── данные B
└── данные C
```

После связи отдельные исходные сущности не должны отображаться как несколько строк списка. В списке остаётся одна строка профиля человека, внутри которой доступны связанные данные.

Например, если два Telegram-аккаунта были отдельными сущностями и затем связаны, список показывает один профиль, а внутри него находятся два Telegram-аккаунта.

Если сущность не связана — она остаётся отдельной строкой списка.

## 4. ID как якорь

ID — постоянный уникальный якорь профиля.

Формат всегда ровно 4 символа.

Правила дополнения нулями:

```text
1      → 0001
12     → 0012
345    → 0345
9999   → 9999
A      → 000A
DS     → 00DS
SFH    → 0SFH
DJFG   → DJFG
A1     → 00A1
```

Допустимы цифры и буквы. Значение, введённое пользователем, приводится к четырёхсимвольному виду по этим правилам.

Один и тот же ID не может одновременно принадлежать двум независимым профилям.

После сохранения присвоенный ID не редактируется как обычное поле.

Полная логика назначения, переноса, объединения и отвязки по ID не входит в текущую реализацию и должна быть предусмотрена архитектурно для последующего ТЗ.

## 5. Главная → Клиенты

В ветке «Клиенты» сверху находятся управляющие действия, а ниже — растущий список профилей.

```text
Клиенты

[ + ]    [ Excel ]    [ Сортировка ▼ ]

────────────────────────

список профилей
```

Управляющие элементы всегда остаются сверху и не должны перемещаться в конец списка при росте количества профилей.

## 6. Счётчик Клиентов

Папка «Клиенты» на экране Главной отображает количество строк, представленных в списке профилей.

Одна строка списка = один отображаемый профиль человека.

Связанные аккаунты, телефоны, Telegram и другие вложенные данные не увеличивают счётчик.

Пример:

```text
0012 — Александр
└── 2 Telegram

0002 — Анна

Антон — без ID
```

Счётчик = 3 отображаемых профиля.

## 7. Добавление

Кнопка `[ + ]` запускает добавление сущности.

Первый экран добавления предоставляет варианты:

```text
[ Создать ]
[ Добавить из контактов ]
```

Варианты используют общий UI приложения.

## 8. Малая форма создания

При ручном создании открывается компактная форма.

Обязательные данные:

- Имя;
- Телефон.

Дополнительно:

- Фамилия;
- ID — если пользователь указывает его при создании.

Пример:

```text
Имя
[________________]

Фамилия
[________________]

Телефон
[________________]

ID
[____]

[ Сохранить ]
```

После сохранения сущность появляется в списке.

## 9. Список профилей

Каждая строка списка имеет компактный мобильный вид.

Если ID существует:

```text
0012 — Александр
+7-934-567-34-45
```

Если ID отсутствует:

```text
Александр
+7-934-567-34-45
```

Правила:

- ID находится в первой строке перед именем;
- ID и имя находятся в одной строке;
- телефон находится под именем;
- телефон отображается более слабым/серым текстом;
- Telegram username не показывается в списке;
- Telegram ID не показывается в списке;
- если имени нет, отображение должно использовать доступные данные без нарушения структуры строки.

Фото может использоваться в строке как визуальный элемент, но не является обязательным вводным полем списка.

## 10. Сортировка

Сортировка находится сверху списка.

Варианты:

```text
Имя ↑
Имя ↓
Последнее посещение ↑
Последнее посещение ↓
```

Сортировка является функцией списка, а не отдельной сущностью.

## 11. Excel

В верхней части списка доступно действие Excel.

Оно предоставляет:

```text
[ Выгрузить ]
[ Загрузить ]
[ Шаблон ]
```

Excel не должен находиться после списка и не должен требовать прокрутки большого количества профилей.

Экспорт и импорт должны учитывать структуру сущности и будущие связанные данные, но конкретный формат импорта/экспорта может быть определён отдельным техническим уточнением.

## 12. Открытие профиля

Нажатие на строку открывает страницу данных выбранного профиля.

Не использовать заголовок «Карточка клиента».

Верх страницы является самостоятельной визуальной информационной плашкой и одновременно визуальным заголовком профиля.

## 13. Верхняя информационная плашка

Фото является фоновой заливкой/частью визуальной области, а не маленьким круглым аватаром.

Внутри плашки отображаются:

- ID, если существует;
- имя;
- телефон;
- три компактных показателя в одну строку.

Три показателя:

1. количество записей/посещений;
2. сумма;
3. последнее посещение либо компактный показатель давности посещения.

Пример композиции:

```text
┌─────────────────────────────┐
│            фото             │
│                             │
│  0012                       │
│  Александр                  │
│  +7-934-567-34-45           │
│                             │
│  12       48 000 ₽     12.08│
└─────────────────────────────┘
```

Плашка должна быть рассчитана на ширину смартфона.

## 14. Один общий Accordion

Вся редактируемая часть профиля собирается одним общим Accordion-компонентом.

Accordion является единым компонентом приложения. Это ТЗ не создаёт отдельную версию Accordion.

Блоки относятся к одной сущности человека:

```text
ID                         ▼
Личные данные              ▼
Контактные данные          ▼
Программа лояльности       ▼
Ссылки                     ▼
Ярлыки                     ▼
```

Внутри профиля нет отдельных самостоятельных сущностей только потому, что данные разбиты на блоки.

## 15. ID

Блок ID содержит поле четырёхсимвольного ID.

После сохранения ID нельзя редактировать обычным вводом.

Связывание нескольких сущностей по ID не реализуется полностью в этом ТЗ, но структура должна позволять в будущем объединить связанные данные в один отображаемый профиль.

## 16. Личные данные

Блок «Личные данные» содержит:

- Имя;
- Фамилия;
- Пол;
- Дата рождения.

## 17. Контактные данные

Блок «Контактные данные» содержит:

- Телефон;
- Telegram;
- Email.

Каждый тип контакта может иметь несколько значений.

Принцип:

```text
Телефон
+7...
+7...
[ + ]

Telegram
аккаунт 1
аккаунт 2
[ + ]

Email
email 1
email 2
[ + ]
```

Telegram является частью «Контактных данных» и не является отдельным Accordion-блоком.

Telegram ID хранится как техническое значение, но не показывается пользователю в обычном интерфейсе.

## 18. Ссылки

Блок «Ссылки» использует один механизм добавления.

Не создавать отдельные кнопки для каждого типа.

```text
[ + Добавить ссылку ]
```

При добавлении в одной строке выбираются тип и значение:

```text
[ Instagram ▼ ] [ URL____________ ]
```

Типы могут включать:

- Instagram;
- ВКонтакте;
- YouTube;
- Facebook;
- Сайт;
- Другое.

После добавления:

```text
Instagram   instagram.com/...   ×
ВКонтакте   vk.com/...          ×
YouTube     youtube.com/...     ×
Сайт        example.com         ×
```

Удаление выполняется для конкретной строки через `×` или единый согласованный компонент удаления.

Telegram в этот блок не входит.

## 19. Программа лояльности

Блок называется «Программа лояльности».

Скидка является первым элементом этого блока.

Если скидка назначена, её процент отображается непосредственно на строке Accordion в закрытом состоянии:

```text
Программа лояльности       10% ▼
```

Если скидки нет, `0%` не показывается.

Выбор скидки выполняется через мобильный Number/Wheel Picker со значениями от 0 до 100%.

Не использовать слайдер или отдельные кнопки `+ / −`.

Ниже скидки находится список назначенных программ:

```text
Скидка                 10%

Программа 1
Программа 2
Программа 3

[ + Программа ]
```

Сами шесть направлений Программы лояльности и их сущности не реализуются этим ТЗ. Здесь предусматривается только место и UI для назначения программ человеку.

## 20. Ярлыки

Блок называется «Ярлыки».

Доступные ярлыки должны поступать из общей системы Настроек, а не создаваться отдельной системой внутри Клиентов.

Этот блок предусматривает назначение существующих ярлыков профилю.

## 21. Соглашения

Соглашения должны быть видны даже при закрытых блоках Accordion.

Отображать:

```text
Согласие ПДН       Дано / Не дано
Согласие на рассылки Дано / Не дано
```

Эти состояния не должны исчезать при сворачивании Accordion.

## 22. Сохранение

Одна общая кнопка:

```text
[ Сохранить ]
```

Она сохраняет изменения всей страницы профиля.

Не создавать отдельные кнопки «Сохранить» внутри каждого блока.

## 23. Назад

В конце страницы:

```text
[ Назад ]
```

Кнопка возвращает в список «Клиенты».

## 24. Мобильные требования

Сущность проектируется для смартфонного экрана.

Обязательно:

- отсутствие горизонтального скролла;
- отсутствие выхода текста за границы;
- корректное отображение длинных имён;
- корректное отображение телефонов;
- компактное отображение трёх показателей;
- корректное отображение Accordion;
- корректное отображение модальных окон;
- корректное отображение списков из нескольких телефонов, Telegram и email;
- корректное отображение длинных URL;
- корректная работа при большом количестве профилей.

## 25. Общий UI и CSS

Сущность использует только общий UI и общую систему CSS приложения.

Не создавать внутри ветки «Клиенты»:

- отдельную систему кнопок;
- отдельный Accordion;
- отдельные локальные цвета;
- отдельную типографику;
- отдельный CSS-файл для решения тех же задач;
- копии существующих UI-компонентов.

Если для этой сущности требуется новый универсальный компонент, он добавляется в общий UI приложения и становится доступным другим веткам.

Особый вид списка или крупной папки «Клиенты» должен реализовываться через вариант/композицию общего UI, чтобы изменение этого варианта не изменяло другие ветки.

## 26. Граница ТЗ

Это ТЗ добавляет одну сущность в существующую ветку «Главная → Клиенты».

Оно не должно:

- создавать новый корень приложения;
- менять пять разделов нижней навигации;
- менять владельцев веток;
- менять структуру других веток;
- создавать собственную UI-систему;
- создавать собственную CSS-систему;
- реализовывать сущности Журнала, Графика, Настроек или Чата;
- реализовывать полноценный механизм объединения и разъединения сущностей.

## 27. Критерии готовности

ТЗ считается реализованным после проверки следующих условий:

1. Ветка «Клиенты» остаётся внутри своего владельца.
2. Счётчик показывает количество отображаемых профилей, а не количество вложенных аккаунтов.
3. Добавление создаёт одну сущность человека.
4. Сущность может существовать без ID.
5. ID имеет ровно 4 символа.
6. ID отображается перед именем в списке.
7. Телефон находится под именем.
8. Управление добавлением, Excel и сортировкой находится сверху списка.
9. Список растёт вниз.
10. Открывается страница данных без заголовка «Карточка клиента».
11. Верхняя область является информационной фото-плашкой.
12. В ней помещаются три показателя в одну строку.
13. Все редактируемые блоки собраны одним Accordion.
14. Telegram находится внутри «Контактных данных».
15. Телефоны, Telegram и email поддерживают несколько значений.
16. Ссылки добавляются через один общий механизм выбора типа.
17. Скидка находится первой в «Программе лояльности» и может отображаться на строке блока.
18. Ярлыки назначаются из общей системы ярлыков.
19. Соглашения видны при закрытом Accordion.
20. Сохранение выполняется одной общей кнопкой.
21. Есть возврат в список.
22. Будущая связь нескольких сущностей в один профиль не требует изменения основной модели списка.
23. Никаких локальных копий общего UI/CSS не создано.
24. Интерфейс корректен на мобильной ширине.

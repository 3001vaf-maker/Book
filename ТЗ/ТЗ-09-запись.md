# ТЗ-09 — Главная сущность «Запись»

## 1. Статус

- Реализация ТЗ: `ТЗ готово`
- Исполнение: `Не исполнено`

Это ТЗ фиксирует согласованную модель и UI основной бизнес-сущности Book — **Записи**. На этом этапе ТЗ является источником требований. Реализация начинается только после отдельного аудита существующего кода и подтверждения, что найдено правильное место интеграции.

## 2. Назначение

**Запись — главная рабочая бизнес-сущность Book.**

График, Журнал, Клиенты, Процедуры/Прайс и другие ранее реализованные части приложения являются подготовкой и инфраструктурой для работы Записи.

Запись связывает:

- дату;
- место работы;
- время;
- клиента;
- одну или несколько процедур;
- параметры процедур, применённые именно к данной записи.

ТЗ не заменяет ранее реализованные сущности и не меняет их владельцев.

## 3. Архитектурный принцип

Book остаётся единым существующим приложением.

Запись добавляется в существующую архитектуру и должна использовать:

- существующий Core;
- существующий общий UI;
- существующий общий Modal;
- существующий переключатель;
- существующий Time Picker;
- существующий UI списка/карточки;
- существующий общий CSS.

Запрещается:

- создавать параллельный Core;
- создавать локальный UI или локальный CSS для Записи;
- дублировать существующие компоненты;
- переписывать Клиентов, Процедуры, График или Журнал ради Записи;
- ломать или заменять существующую корректировку рабочего дня из Журнала.

Перед реализацией обязателен аудит текущего репозитория.

## 4. Владельцы исходных данных

Запись не дублирует исходные сущности как самостоятельные копии.

### Клиент

Клиенты берутся из существующей сущности **Клиенты**.

Из неё для отображения Записи используются необходимые данные карточки клиента:

- собственный ID клиента, если он существует;
- имя и фамилия;
- телефон;
- другие данные карточки при необходимости отображения.

ID клиента — это именно внутренний идентификатор клиента в клиентской базе мастера, а не Telegram ID.

### Процедуры

Процедуры берутся из существующего **Прайса / Процедур**.

Для выбора доступны существующие данные процедуры, прежде всего:

- название;
- стандартная длительность;
- стоимость.

При формировании конкретной Записи параметры процедуры могут быть скорректированы только для этой Записи. Изменение самой процедуры в Прайсе при этом не происходит.

## 5. Запуск создания Записи

Создание Записи начинается из временного поля Журнала.

Пользователь нажимает на конкретное время рабочего дня.

Первое модальное окно содержит два режима:

```text
┌─────────────────────────────────┐
│ Создать запись              [X] │
├─────────────────────────────────┤
│ [ Создать запись ] [ Занять время ]
├─────────────────────────────────┤
│              15:00              │
│              15:05              │
│              15:10              │
│              15:15              │
│              15:20              │
│              15:25              │
│              15:30              │
│              15:35              │
│              15:40              │
│              15:45              │
│              15:50              │
│              15:55              │
└─────────────────────────────────┘
```

### 5.1. Заголовок модалки

Используется стандартная существующая модальная система Book.

В заголовке:

- название `Создать запись`;
- стандартная кнопка `[X]` справа.

Кнопки `Отмена` снизу нет.

`X` полностью закрывает текущую модалку.

### 5.2. Переключатель

Под заголовком используется существующий общий переключатель Book.

Это тот же UI-механизм, который уже используется в приложении, в том числе для переключения режимов стоимости в Процедурах.

Два режима:

- `Создать запись` — выбран по умолчанию;
- `Занять время` — альтернативный режим.

Эти режимы являются двумя путями одного процесса.

В данном ТЗ основной подробно определённый путь — **Создать запись**.

Режим `Занять время` должен оставаться отдельным путём и не смешиваться с Записью. Его дальнейшая детализация фиксируется отдельно.

### 5.3. Временной блок

После переключателя располагается список времени от выбранной пользователем точки до конца текущего часа.

Шаг выбора — **5 минут**.

Например, если пользователь нажал на `15:00`, доступны:

`15:00, 15:05, 15:10, 15:15, 15:20, 15:25, 15:30, 15:35, 15:40, 15:45, 15:50, 15:55`.

Визуально:

- `:00`, `:15`, `:30`, `:45` — основные точки сетки, более активный/коричневый цвет;
- остальные пятиминутные значения — светлые, серые/прозрачные.

Светлые значения не запрещены для выбора. Они лишь визуально показывают, что предпочтительными точками являются четверти часа.

Нажатие на конкретное время **сразу закрывает текущую модалку и открывает следующую**. Кнопки `Далее` для выбора времени нет.

## 6. Экран «Процедуры»

После выбора времени открывается новая стандартная модалка только для выбора процедур.

Переключатель `Создать запись / Занять время` здесь больше не отображается.

Структура:

```text
┌────────────────────────────────────────┐
│ Процедуры                    [ + ] [X]│
├────────────────────────────────────────┤
│ ☐ Стрижка                         ⚙   │
│   60 мин                               │
│                                        │
│ ☐ Окрашивание                     ⚙   │
│   120 мин                              │
│                                        │
│ ☐ Укладка                         ⚙   │
│   30 мин                               │
│                                        │
│                         [ Далее → ]    │
└────────────────────────────────────────┘
```

### 6.1. Верхняя часть

Используется стандартная модальная система Book.

Справа находятся стандартные действия:

- `[ + ]` — добавить/создать новую процедуру;
- `[X]` — закрыть модалку.

Отдельной нижней кнопки `Отмена` нет.

Функционал создания новой процедуры через `[+]` в этом ТЗ не проектируется. Он относится к отдельному процессу сущности Процедура.

### 6.2. Список процедур

Список берётся из существующего Прайса/сущности Процедур.

Каждая процедура отображается:

- слева — чекбокс множественного выбора;
- название — одной строкой;
- под названием — длительность;
- справа — `[⚙]` настройки конкретной процедуры для текущей Записи.

Выбор процедур является **множественным**.

### 6.3. Кнопка «Далее»

`Далее` находится в верхней части модалки согласно существующему общему UI, если этого требует конкретный общий компонент. Нижняя часть длинного списка не должна использоваться как единственная точка навигации.

При отсутствии выбранной процедуры переход далее невозможен.

После выбора одной или нескольких процедур становится доступен переход `Далее`.

### 6.4. Сброс выбора

После появления выбранных процедур доступно действие `Сброс выбора`.

Оно сбрасывает текущий выбор процедур.

Это не является закрытием модалки.

## 7. Настройки процедуры внутри Записи

Нажатие на `[⚙]` открывает отдельную небольшую стандартную модалку для корректировки выбранной процедуры **только в рамках текущей Записи**.

Структура:

```text
┌───────────────────────────────────┐
│ Стрижка                       [X] │
├───────────────────────────────────┤
│ установите необходимые параметры  │
│ услуги для данной записи          │
│                                   │
│ Стоимость             [ 4000 ₽ ]  │
│                                   │
│ Длительность           [ 01:00 ] │
│                                   │
│ [ Отмена ]          [ Сохранить ] │
└───────────────────────────────────┘
```

### 7.1. Выравнивание

Для параметров обязательно используется единая структура одной строки:

```text
Стоимость                 [ значение ]
Длительность              [ значение ]
```

- название параметра — слева;
- поле со значением — справа;
- строки выровнены одинаково;
- никаких разрозненных блоков или иной структуры.

Нижние действия также располагаются **на одной линии**:

- `Отмена` — слева;
- `Сохранить` — справа.

Это маленькая корректирующая модалка. Её визуал должен использовать существующий общий Modal/UI Book.

### 7.2. Длительность

Нажатие на поле длительности открывает существующий классический общий Time Picker.

Новый Time Picker для Записи не создаётся.

### 7.3. Перерыв процедуры

Поле `Перерыв после записи` в эту модалку **не входит**.

Перерыв является отдельным путём занятого времени и не является параметром процедуры конкретной Записи.

После `Сохранить` или `Отмена` пользователь возвращается к экрану Процедур текущей Записи.

## 8. Экран «Клиенты»

После `Далее` на экране Процедур открывается новая стандартная модалка выбора клиента.

Здесь также используется существующая модальная система Book.

Структура верхней части:

```text
┌────────────────────────────────────────┐
│                                [ + ] [X]│
├────────────────────────────────────────┤
│ 🔍  Найти клиента...                  │
├────────────────────────────────────────┤
│ Маша Иванова                           │
│ Маша Петрова                           │
│ Даша Иванова                           │
│ Даша Петрова                           │
└────────────────────────────────────────┘
```

### 8.1. Заголовочная часть

В стандартной верхней части модалки:

- `[+]` — создать нового клиента;
- `[X]` — закрыть модалку.

Слова `Клиенты` как отдельного заголовка в верхней строке нет.

Функционал создания нового клиента через `[+]` в этом ТЗ не проектируется.

### 8.2. Поиск

Первый блок содержимого модалки — компактное поле поиска:

- иконка лупы;
- поле/подсказка `Найти клиента...`.

При вводе текста список клиентов фильтруется.

Например, поиск `Маша` показывает только соответствующие варианты.

### 8.3. Выбор клиента

Из списка выбирается **один клиент**.

После выбора отображается существующая карточка выбранного клиента.

Карточка берётся из существующей сущности/механизма Клиентов, а не создаётся отдельная карточка специально для Записи.

Пример информационной структуры:

```text
┌────────────────────────────────────┐
│ Маша Иванова                       │
│ телефон                            │
│ основные данные карточки клиента   │
│ ...                                │
└────────────────────────────────────┘
```

После выбора клиента `[+]` больше не является действием текущего выбора. Пользователь продолжает через `Далее`.

### 8.4. Завершение выбора клиента

После появления карточки клиента доступно `Далее`.

`Далее` завершает последовательность создания Записи.

Отдельной кнопки `Записать` не создаётся.

## 9. Формирование Записи

После нажатия `Далее` на экране Клиенты создаётся одна сущность **Запись**.

Она должна сохранить фактически выбранные данные, необходимые для исторической корректности записи.

Минимальная логическая структура:

```text
Запись
├── дата
├── место работы
├── время начала
├── время окончания
├── клиент
│   ├── ID клиента, если существует
│   ├── имя
│   ├── фамилия
│   └── телефон
└── процедуры[]
    ├── процедура
    ├── стоимость для данной Записи
    └── длительность для данной Записи
```

Точная структура хранения и идентификаторы определяются после обязательного аудита существующего Core и сущностей Book.

## 10. Отображение созданной Записи во временном листе

После создания Записи занятое ей время в Журнале должно отображаться как единый цветной занятый блок поверх временной шкалы.

Пример:

```text
┌──────────────────────────────┐
│ 0042 Маша Иванова            │
│ +7 999 123-45-67             │
│ Стрижка                      │
│ Окрашивание                  │
└──────────────────────────────┘
```

### 10.1. Первая строка

Если у клиента существует собственный ID:

```text
0042 Маша Иванова
```

Используется только сам код. Не выводятся слова `ID`, `КЛ` или другие обозначения.

Если ID отсутствует:

```text
Маша Иванова
```

### 10.2. Вторая строка

Телефон занимает отдельную строку:

```text
+7 999 123-45-67
```

### 10.3. Процедуры

Каждая выбранная процедура занимает **собственную строку**:

```text
Стрижка
Окрашивание
```

Таким образом:

1. ID + имя и фамилия;
2. телефон;
3. первая процедура;
4. вторая процедура;
5. и далее по одной строке на каждую процедуру.

Информация не должна искусственно объединяться в одну строку, если это ухудшает размещение на мобильном экране.

## 11. Время Записи и занятие временного листа

Выбранное время становится временем Записи.

После создания Записи соответствующий интервал Журнала становится занятым.

Запись не изменяет границы рабочего дня.

Это принципиально отличается от существующей **Корректировки рабочего дня**:

```text
Корректировка рабочего дня
→ изменяет WorkTime / границы рабочего дня
→ принадлежит модели Графика

Запись
→ занимает время внутри рабочего дня
→ принадлежит Журналу как рабочая бизнес-сущность
```

Корректировка рабочего дня из Журнала не должна быть удалена, заменена или смешана с созданием Записи.

## 12. Перерыв / «Занять время»

В первом модальном окне существует второй путь:

`Занять время`.

Он означает не создание Записи, а занятие части рабочего времени без клиента и процедуры.

Это отдельная модель занятого времени и не является параметром Записи.

Ранее созданная техническая основа `core/journal-breaks.js` может быть использована только после аудита и проверки соответствия этой окончательной модели. Сам факт её существования не определяет окончательную архитектуру.

Детальное ТЗ для пути `Занять время` создаётся/уточняется отдельно после завершения определения Записи, если потребуется отдельная фиксация требований.

## 13. Связи с существующими сущностями

```text
График / Date
      │
      │ предоставляет рабочий временной ресурс
      ↓
Журнал
      │
      │ пользователь выбирает время
      ↓
   Запись
   ├── Клиент
   └── Процедуры
```

Запись использует рабочий временной ресурс Графика, но не получает права напрямую менять владельца этого ресурса.

Изменение границ рабочего дня выполняется существующим бизнес-механизмом корректировки WorkTime.

## 14. Аудит перед реализацией

Перед изменением кода исполнитель обязан провести аудит текущего состояния `main` и определить:

1. где реально реализована сущность Клиент;
2. где хранится её внутренний ID;
3. как получить список клиентов;
4. как получить карточку клиента;
5. где реально реализована сущность Процедура/Прайс;
6. как получить список процедур;
7. какие поля процедуры являются источником названия, стоимости и длительности;
8. какой общий Modal используется сейчас;
9. какой общий переключатель используется сейчас;
10. какой общий Time Picker используется сейчас;
11. какой общий UI списка/карточки уже существует;
12. где правильно разместить Core сущности Запись;
13. как подключить Запись к Журналу без нарушения существующей архитектуры;
14. как занять временной интервал Записью без изменения WorkTime;
15. какие существующие файлы потребуется изменить;
16. какие новые файлы действительно необходимы.

**До завершения аудита реализация Записи не начинается.**

## 15. Ограничения

- Запись — одна центральная бизнес-сущность, а не набор независимых UI-сущностей.
- День, Процедура, Клиент и другие существующие сущности не копируются внутрь Записи без необходимости.
- Выбор процедур — множественный.
- Выбор клиента — одиночный.
- Время выбирается с шагом 5 минут.
- Предпочтительные четверти часа визуально выделяются сильнее.
- Нажатие времени автоматически переводит на следующий экран.
- Нажатие `Далее` переводит на следующий экран.
- Запись занимает время, но не изменяет границы рабочего дня.
- Перерыв не является частью процедуры Записи.
- Все модальные окна используют общий Modal Book.
- Все переключатели используют существующий общий переключатель Book.
- Все временные пикеры используют существующий общий Time Picker.
- Общий CSS не дублируется.
- Мобильная ширина учитывается при формировании блока Записи.

## 16. Критерии готовности

ТЗ считается исполненным только после проверки полного сценария:

```text
Журнал → временной слот
        ↓
Создать запись
        ↓
выбор времени
        ↓
Процедуры
        ↓
настройка процедуры при необходимости
        ↓
Клиенты
        ↓
выбор существующего клиента / создание нового клиента
        ↓
карточка клиента
        ↓
Далее
        ↓
создание Записи
        ↓
занятый блок в Журнале
```

При этом необходимо отдельно проверить:

- одна процедура;

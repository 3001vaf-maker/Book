# ТЗ-01 — Архитектурный фундамент нового мобильного приложения

## 1. Цель

Создать чистый архитектурный фундамент приложения, рассчитанного прежде всего на работу на смартфоне.

ТЗ-01 создаёт только фундамент:

- корневое управление;
- пять разделов нижней навигации;
- первоначальную структуру всех известных веток;
- единую систему UI;
- единую систему CSS;
- мобильную систему размеров и адаптации;
- систему вариантов общих компонентов;
- правила владения ветками и будущего расширения.

Бизнес-сущности и их функциональность в ТЗ-01 не реализуются. Они добавляются последующими отдельными ТЗ.

## 2. Главный принцип

Архитектура приложения единая.

```text
APP
│
├── MAIN
├── TIMETABLE
├── JOURNAL
├── CHAT
└── SETTINGS
```

Каждая из пяти веток является равноправным разделом приложения. Ни одна ветка не считается «главной» относительно остальных.

Название `main` означает только раздел «Главная» в нижней навигации.

## 3. Корневое управление

Создать `core.js`.

`core.js` является корневым уровнем приложения и отвечает за:

- запуск приложения;
- подключение пяти основных веток;
- общую навигацию;
- общий UI;
- общий CSS;
- общий мобильный контейнер;
- маршрутизацию между разделами;
- общие состояния приложения.

`core.js` не должен содержать бизнес-логику конкретных сущностей.

## 4. Пять разделов нижней навигации

```text
Главная
График
Журнал
Чат
Настройки
```

Нижняя навигация является частью общего UI. Каждая ветка получает собственный модуль и собственное владение.

## 6. Архитектура не является конечной

Данная структура является начальной архитектурой, а не окончательным списком всех будущих возможностей приложения.

В дальнейшем новые подпапки могут появляться внутри существующих веток. Новая ветка всегда добавляется внутрь своего владельца и не требует перестройки всего приложения.

## 7. Правило владения

Каждый модуль владеет своим непосредственным содержимым.

```text
APP
 ↓
Настройки
 ↓
Программа лояльности
 ↓
Депозит
```

Владелец отвечает за свою ветку. Соседняя ветка не получает права напрямую управлять внутренним содержимым другой ветки.

## 8. Журнал

`journal.js` владеет единой сущностью записи.

У записи есть три представления:

```text
День | Месяц | Список
```

Это единый переключатель представления, а не три отдельные папки.

Не создавать `day.js`, `month.js`, `list.js` и не создавать отдельные папки для этих представлений.

Все три представления принадлежат Журналу.

## 9. Главная

```text
main/
├── main.js
└── clients/
    └── clients.js
```

`main.js` владеет содержимым Главной. `clients.js` является отдельной дочерней веткой.

Правила сущностей Клиентов не реализуются в ТЗ-01.

## 10. График

```text
timetable/
└── timetable.js
```

График владеет будущей сущностью рабочего времени. Сама сущность реализуется отдельным ТЗ.

## 11. Чат

```text
chat/
└── chat.js
```

Чат является самостоятельной веткой. На этапе ТЗ-01 внутренняя сущность Чата не определяется.

## 12. Настройки

```text
settings/
├── profile/
├── service/
├── warehouse/
├── documents/
├── loyalty/
├── tags/
└── wallets/
```

Этот список является начальным и может расширяться.

## 13. Профиль

```text
profile/
├── profile.js
├── personal/
│   └── personal.js
└── workplaces/
    └── workplaces.js
```

Профиль владеет Личными данными и Местами работы.

## 14. Сервис

```text
service/
├── service.js
├── procedures/
│   └── procedures.js
└── products/
    └── products.js
```

Сервис владеет Процедурами и Продуктами. Сами сущности будут добавлены отдельными ТЗ.

## 15. Склад

Использовать техническое название `warehouse/`. Пользовательское название раздела — **Склад**.

Не использовать `work` или `works`.

## 16. Документы

```text
documents/
└── documents.js
```

Документы являются отдельной веткой Настроек. Будущая сущность определяется отдельным ТЗ.

## 17. Программа лояльности

Техническая ветка — `loyalty/`. Пользовательское название — **Программа лояльности**.

Сейчас она является владельцем шести направлений:

```text
loyalty/
├── deposit/
├── personal-account/
├── referral-program/
├── bonus-program/
├── certificates/
└── subscriptions/
```

Это шесть текущих дочерних веток. В будущем новые направления могут быть добавлены.

## 18. Личный счёт

Пользовательское название — **Личный счёт**.

Техническое название:

```text
personal-account/
└── personal-account.js
```

Личный счёт является отдельным финансовым балансом и не объединяется автоматически с Депозитом или Реферальной программой.

## 19. Ярлыки

```text
tags/
└── tags.js
```

Пользовательское название — **Ярлыки**. Ярлыки предназначены для последующей фильтрации. Сущность Ярлыка будет реализована отдельным ТЗ.

## 20. Кошельки

```text
wallets/
└── wallets.js
```

Кошельки являются отдельной веткой и не объединяются автоматически с Программой лояльности.

## 21. Единый UI

Создать `ui/` как общий UI приложения.

Минимальный набор:

```text
ui/
├── buttons/
├── inputs/
├── forms/
├── lists/
├── rows/
├── cards/
├── accordion/
├── selectors/
├── dropdowns/
├── pickers/
├── tabs/
├── navigation/
├── modals/
├── avatar/
├── badges/
├── toggles/
├── counters/
├── dividers/
├── states/
└── ...
```

Список расширяемый.

## 22. Accordion

Accordion является обязательным компонентом общего UI и создаётся один раз в `ui/accordion/`.

Все ветки используют этот компонент.

Если разные разделы требуют разного вида Accordion, используются варианты одного общего компонента.

Не создавать локальные копии Accordion внутри отдельных веток.

## 23. Система вариантов UI

Общий UI должен поддерживать варианты одного компонента:

- стандартный;
- компактный;
- крупный;
- со счётчиком;
- с дополнительной информацией;
- для определённого состояния.

Уникальность конкретной ветки достигается композицией и вариантами общего UI, а не созданием отдельной UI-системы.

## 24. Особенность раздела Клиенты

Раздел Клиенты может иметь особую композицию:

- крупный визуальный блок;
- счётчик;
- особое размещение;
- собственную информационную структуру.

Это не означает создание собственного CSS или собственного UI. Используется общий UI с необходимым вариантом компонента.

Изменение внешнего вида Клиентов не должно автоматически менять другие разделы.

## 25. Единый CSS

Создать:

```text
css/
└── style.css
```

Это единая система стилей приложения.

В ней находятся общие:

- цвета;
- типографика;
- размеры;
- отступы;
- радиусы;
- состояния;
- кнопки;
- поля;
- списки;
- карточки;
- Accordion;
- навигация;
- мобильные правила.

Не создавать параллельные CSS-файлы для отдельных веток без отдельного архитектурного решения.

## 26. Визуальная основа

В новую систему переносятся только утверждённые визуальные параметры как исходная визуальная база. Поведение, размеры и адаптивность проектируются заново для мобильного приложения.

### Цвета

```text
Основной текст / основной акцент  #3B302B
Вторичный текст                   #7A6F69
Вспомогательный текст             #B8AEA8
Граница                           #E5DED9
Основной светлый фон              #F4F1EA
Фон приложения                    #F5F5F3
Белый UI-фон                      #FFFFFF
Фон вторичной кнопки              #E7E1DB
Активное состояние                #E8E1DC
Опасное действие                  #9A6258
```

Значения хранятся централизованно и не должны дублироваться в отдельных модулях.

## 27. Типографика

Использовать системный шрифт:

```text
-apple-system,
BlinkMacSystemFont,
"Segoe UI",
Roboto,
Arial,
sans-serif
```

Типографическая система должна централизованно предусматривать:

- крупный заголовок;
- заголовок раздела;
- подзаголовок;
- основной текст;
- вторичный текст;
- подпись;
- служебный текст;
- цифровые показатели.

## 28. Размеры компонентов

Визуальные размеры не переносятся механически. Они должны быть проверены и рассчитаны для мобильного интерфейса.

Базовые значения:

```text
Высота стандартного управляющего элемента: 48 px
Базовый gap: 12 px
Основной горизонтальный отступ: 18 px
Радиус стандартного элемента: 14 px
Радиус крупного элемента/папки: 16 px
Радиус панели: 18 px
Радиус нижнего листа: 20 px
```

Это базовые значения, допускающие варианты общего UI.

## 29. Mobile-first

Приложение проектируется mobile-first.

Нельзя строить desktop-интерфейс и затем просто уменьшать его.

Необходимо учитывать:

- ширину экрана смартфона;
- safe-area;
- нижнюю область экрана;
- высоту нижней навигации;
- сенсорные зоны;
- читаемость;
- вертикальный скролл;
- отсутствие горизонтального скролла;
- компактное размещение информации;
- устройства с разной шириной экрана.

Компоненты не должны иметь жёсткую ширину, рассчитанную на один телефон.

## 30. Адаптивность

Использовать:

- responsive layout;
- относительные размеры;
- ограничения максимальной ширины;
- flex/grid;
- адаптивные отступы;
- safe-area;
- управление переполнением.

Особенно контролировать длинные имена, номера телефонов, большие суммы, счётчики и несколько элементов в одной строке.

## 31. Три информативные точки

Компактные элементы должны позволять размещать несколько ключевых показателей в одной строке:

```text
показатель 1 | показатель 2 | показатель 3
```

При недостатке ширины компонент должен иметь заранее предусмотренное адаптивное поведение.

## 32. Нижняя навигация

Общий компонент находится в `ui/navigation/`.

Содержит:

```text
Главная
График
Журнал
Чат
Настройки
```

Навигация должна:

- быть доступной большим пальцем;
- учитывать safe-area;
- не перекрывать содержимое;
- сохранять активное состояние;
- иметь единый визуальный стиль;
- использовать общий CSS.

## 33. Изоляция веток

Каждая ветка может иметь уникальную структуру и функциональность.

Но:

```text
уникальная структура ≠ отдельный UI
уникальная структура ≠ отдельный CSS
```

Если требуется специальный вид, используется вариант общего компонента.

Если требуется новый общий компонент, он добавляется в `ui/` и затем используется необходимыми ветками.

## 34. Запрет дублирования

Не создавать независимые CSS-файлы или копии одинаковых UI-компонентов для разных веток.

Не копировать CSS между ветками.

## 35. Сущности

ТЗ-01 только создаёт архитектурные точки, в которых впоследствии будут находиться сущности.

Сами модели, поля, действия и бизнес-правила сущностей здесь не реализуются.

Каждая сущность разрабатывается отдельным ТЗ.

## 36. Правило последовательного строительства

Каждое новое ТЗ должно определить, в какую уже существующую ветку добавляется содержимое.

После определения ветки:

1. используется существующий владелец;
2. используется существующий UI;
3. используется существующий CSS;
4. добавляется только необходимая логика;
5. при необходимости добавляется новая подпапка внутри существующей ветки;
6. при необходимости добавляется новая сущность;
7. существующая архитектура не переписывается.

## 37. Главное правило будущих ТЗ

Новое ТЗ **добавляет**, а не пересобирает приложение.

Запрещено без отдельного архитектурного решения:

- менять корневую архитектуру;
- создавать второй `core`;
- создавать второй `ui`;
- создавать второй `style.css`;
- создавать локальную UI-систему;
- копировать существующие компоненты;
- переносить сущность в другую ветку;
- переписывать соседние ветки без необходимости.

## 38. Критерий завершения

После выполнения ТЗ-01 должен существовать чистый мобильный фундамент:

```text
                    CORE
                      │
       ┌──────────────┼──────────────┐
       │              │              │
    NAVIGATION      COMMON UI     COMMON CSS
       │
 ┌─────┼─────┬──────┬──────┐
 │     │     │      │      │
Главная График Журнал Чат Настройки
 │                         │
Клиенты                существующие
                       подпапки
```

Должны существовать:

- пять разделов;
- определённые владельцы;
- все известные начальные подпапки;
- Программа лояльности с шестью текущими направлениями;
- возможность будущего расширения;
- единый UI;
- Accordion;
- система вариантов UI;
- единый CSS;
- mobile-first система;
- централизованная палитра и типографика;
- отсутствие дублирования UI/CSS;
- отсутствие реализации бизнес-сущностей в фундаменте.

## 39. Итоговый принцип

```text
ОДНА АРХИТЕКТУРА
        │
        ├── 5 основных веток
        │
        ├── каждая ветка владеет своим содержимым
        │
        ├── ветки могут расширяться
        │
        ├── сущности добавляются отдельными ТЗ
        │
        ├── ОДИН ОБЩИЙ UI
        │
        ├── ОДИН ОБЩИЙ CSS
        │
        └── MOBILE-FIRST
```

Архитектура является расширяемой. UI является единым. CSS является единым. Ветки независимы по содержимому, но используют общий фундамент.

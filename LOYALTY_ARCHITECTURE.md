# LOYALTY_ARCHITECTURE

Нормативный продуктовый контракт F `Лояльность`.

Этот файл фиксирует утверждённую бизнес-модель и обязательные UI-проявления. Порядок технического исполнения определён отдельно в `LOYALTY_EXECUTION_CONTRACT.md`.

## 1. Главное архитектурное правило

**Сущность владеет своим состоянием. Операция владеет фактом действия. Место вызова механики не становится её владельцем.**

Следствия:
- Журнал, Контакты, расчёт и другие рабочие контуры могут вызвать готовую механику Лояльности, но не получают собственной копии её правил;
- Финансы хранят факты реального движения денег, но не подменяют собой сущности Лояльности;
- расчёт / Settlement использует доступные источники оплаты, но не объединяет их данные в одну сущность;
- один факт не должен существовать как несколько независимых операций в разных владельцах; связь выполняется ссылками;
- исторические факты не переписываются бесследно.

Общая схема:

```text
СУЩНОСТЬ (состояние)
    ↕ ссылки
ОПЕРАЦИЯ-ВЛАДЕЛЕЦ (факт/действие)
    ↕ ссылки
РАСЧЁТ / место использования
```

## 2. Состав F `Лояльность`

Внутри F `Лояльность` существуют E строго в таком порядке:

1. `Депозит`
2. `Личный счёт`
3. `Сертификат`
4. `Абонемент`
5. `Реферальная программа`
6. `Бонусная программа`

Для каждого E действует общий верхний контракт:
- A — фото / настройки только там, где есть доказанное действие;
- B — заголовок текущего E/Z;
- C — одно контекстное действие только по смыслу текущего состояния;
- D — отдельный общий контур Чата;
- Z1 — рабочий вид E;
- Z2/Z3/Q/X/S используются только по смыслу сущности и только через общие UI-владельцы приложения.

Настройки не являются отдельными E.

## 3. E `Депозит`

### 3.1. Две разные сущности

`DepositProgram` — шаблон правил депозитной программы.

`DepositInstance` — конкретный оформленный депозит конкретного человека.

Их нельзя подменять финансовой операцией.

### 3.2. DepositProgram

Профессионал задаёт:
- название;
- сумму или правило свободной суммы;
- срок / бессрочность;
- выгоду;
- текст условий;
- другие подтверждённые правила использования.

После запуска экономические условия программы не редактируются. Для новых условий создаётся новая программа / версия. Допустимо менять только жизненный статус программы: активна, приостановлена, возобновлена, закрыта и иные подтверждённые состояния. История существующих экземпляров сохраняется.

Z1 показывает список программ.

A Z1:
- `Вид карты`.

C Z1:
- `+` — создать программу в Q.

Z2 показывает паспорт программы и список оформленных экземпляров.

C Z2:
- `Оформить` — создать `DepositInstance` выбранному человеку.

### 3.3. DepositInstance

Конкретный депозит владеет собственным состоянием минимум:
- `depositId`;
- профессионал / tenant;
- человек;
- ссылка на программу и зафиксированный снимок её условий;
- первоначальный объём права / внесённая сумма;
- текущий доступный остаток;
- состояние;
- срок / даты действия;
- дата оформления;
- ссылки на связанные факты использования и финансовые факты.

Z3 показывает именно этот экземпляр и его историю.

**DepositInstance не должен реконструироваться как сущность исключительно из `FinanceOperation`.**

### 3.4. Связь с Финансами и расчётом

При внесении реальных денег:
- Deposit создаёт / изменяет собственную сущность;
- Finance фиксирует факт поступления денег;
- FinanceOperation содержит ссылку на `DepositInstance`.

При возврате реальных денег:
- Deposit изменяет собственное состояние;
- Finance фиксирует денежный возврат;
- оба факта связаны ссылкой на один `DepositInstance`.

При использовании в оплате:
- Settlement использует `DepositInstance` как источник расчёта;
- Deposit меняет доступный остаток;
- нового физического прихода денег в этот момент нет.

При возврате оплаты соответствующая часть права Депозита восстанавливается по связанной операции.

Вызвать готовую механику Депозита можно из Журнала, Контактов, самого E `Депозит` и других подтверждённых мест расчёта. Эти места не владеют правилами Депозита.

## 4. E `Личный счёт`

### 4.1. Смысл

Личный счёт — **автоматически существующая денежная связь между конкретным профессионалом и конкретным конечным пользователем**.

Как только между ними существует контакт / отношение, Личный счёт существует.

Он может иметь:
- `0` — если профессионал не хранит деньги этого человека;
- положительный денежный остаток — если у профессионала находятся реальные деньги этого человека для будущего расчёта.

Пример: работа стоит `4 500 ₽`, человек передал `5 000 ₽` и явно попросил оставить `500 ₽` на своём счёте. Личный счёт отражает обязательство профессионала перед этим человеком на `500 ₽`.

### 4.2. Чего у Личного счёта нет

Личный счёт:
- не создаётся вручную;
- не назначается;
- не подключается и не отключается;
- не имеет действия `Открыть счёт`;
- не имеет C `+` для создания;
- не хранит бонусный баланс;
- не владеет сроком жизни бонусов;
- не является Депозитом, Сертификатом или Абонементом.

### 4.3. Состояние и история

Личный счёт владеет person-specific денежным обязательством / остатком.

Факты физического поступления или возврата денег принадлежат Finance. Использование уже оставленных денег в расчёте принадлежит Settlement как факту расчёта. Личный счёт отражает связанное изменение своего состояния без создания независимого дубля того же финансового факта.

История должна быть проверяемой: сохраняются ссылки на источник изменения, рабочая дата и аудитная дата там, где они различаются, а корректировки не уничтожают цепочку аудита.

Z1 показывает людей и их **денежный** остаток.

Z2 показывает конкретный Личный счёт и связанную историю изменений остатка.

Отдельного Z3 «бонусной операции Личного счёта» не существует.

## 5. E `Сертификат`

### 5.1. Модель

Профессионал создаёт виды сертификатов, затем оформляет конкретные экземпляры.

Поддерживаемые типы:
- на сумму;
- на конкретную позицию Сервиса;
- на набор позиций.

Покупатель и владелец сертификата могут быть разными людьми.

### 5.2. Владение

Сертификат сам владеет:
- исходным правом / номиналом;
- остатком;
- сроком;
- правилом частичного использования, если оно разрешено;
- состоянием;
- историей использования.

Факт продажи за реальные деньги принадлежит Finance. Использование в расчёте вызывается Settlement, но изменение права принадлежит Сертификату.

Z1 — виды сертификатов. C `+` создаёт новый вид в Q.

Z2 — выбранный вид и его оформленные экземпляры. C `Оформить` / `Продать` создаёт экземпляр.

Z3 — конкретный сертификат конкретного владельца.

---

## 6. E `Абонемент`

Профессионал создаёт программы из позиций собственного Сервиса.

Поддерживаются:
- одна позиция с количеством;
- набор нескольких позиций с отдельными лимитами;
- общий лимит на несколько позиций;
- безлимит по выбранным позициям;
- срок действия / бессрочность;
- начало срока с оформления, первого использования или конкретной даты;
- ограничения частоты по дню / неделе / месяцу;
- допустимость нескольких единиц за одно событие.

После запуска условия программы не редактируются; изменение условий создаёт новую программу / версию.

Абонемент сам владеет остатками, лимитами, сроком, допустимостью очередного использования и историей.

Факт продажи за реальные деньги принадлежит Finance. Журнал, Контакты и расчёт могут вызвать использование, но не содержат собственной реализации правил Абонемента.

Z1 — программы, C `+` создаёт программу в Q.

Z2 — выбранная программа и люди с оформленными экземплярами.

Z3 — конкретный экземпляр человека.

---

## 7. E `Реферальная программа`

Реферальная программа владеет:
- своими условиями;
- персональной ссылкой / кодом;
- связью `пригласивший → приглашённый`;
- квалифицирующим событием;
- уровнями;
- расчётом награды;
- повторяемостью и ограничениями;
- **собственным per-person бонусным балансом / журналом наград и сроками их действия**.

Результат Реферальной программы **не записывается в Личный счёт**.

Программа может назначаться:
- всем контактам;
- выбранным контактам.

Персональное назначение / исключение принадлежит Контактам. Экономические правила и награды остаются владельцу `Реферальная программа`.

Обязательные ограничения:
- нельзя пригласить самого себя;
- нельзя создавать циклическую цепочку;
- одно квалифицирующее событие не создаёт одно и то же вознаграждение повторно;
- отмена / возврат квалифицирующего события корректно связывается с наградой;
- исторические связи и награды не уничтожаются бесследно.

Z1 — программы; C `+` создаёт программу в Q.

Z2 — сеть / список реферальных связей выбранной программы.

Z3 — конкретная связь / цепочка и награды в рамках этой программы.

---

## 8. E `Бонусная программа`

Бонусная программа определяет награду за собственные действия человека и не создаёт реферальные связи.

Она владеет:
- условиями начисления;
- правилами размера награды;
- повторяемостью;
- назначением общего режима `всем / выбранным` как свойством программы;
- **собственным per-person бонусным балансом / журналом начислений, списаний и сроками действия наград**.

Результат Бонусной программы **не записывается в Личный счёт**.

Назначение / персональное отключение конкретному человеку выполняется через Контакты и не копирует экономику программы в Контакты.

Z1 — программы; C `+` создаёт программу в Q.

Z2 — выбранная программа и её участники / результат по каждому.

Z3 — конкретный участник и история внутри этой программы.

---

## 9. Общий расчёт

Settlement может в одном интерфейсе показать доступные человеку источники, например:

```text
Личный счёт: 1 250 ₽
Депозит: 18 500 ₽
Бонусная программа «VIP»: 750 бонусов
Сертификат: 1 000 ₽
Абонемент: доступно 3 использования
```

Это только агрегированное представление выбора источников. Данные не сливаются:
- Личный счёт владеет реальными деньгами человека;
- Депозит — своим остатком и условиями;
- конкретная Бонусная программа — собственными бонусами;
- конкретная Реферальная программа — собственными наградами;
- Сертификат — своим правом / остатком;
- Абонемент — своими лимитами.

Settlement владеет фактом расчёта и ссылками на использованные источники.

---

## 10. Статус контракта

Продуктовая архитектура шести E зафиксирована.

Связанные нормативные документы:
- `LOYALTY_ASSIGNMENT_CONTRACT.md` — назначение и появление сущностей у конкретного человека;
- `LOYALTY_FINANCE_CONTRACT.md` — граница реальных денег, обязательств, бонусов и расчёта;
- `LOYALTY_EXECUTION_CONTRACT.md` — обязательный порядок технической реализации и восстановления работы после смены исполнителя.

Runtime не имеет права вводить модель, противоречащую этим контрактам. Уже существующий код, который старше текущего контракта, должен мигрироваться к нему без уничтожения корректных пользовательских проявлений и исторических фактов.

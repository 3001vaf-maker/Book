# SETTLEMENT_OPERATION_CONTRACT

Нормативный контракт единой операции расчёта / оплаты.

Этот файл определяет владельца операции и границу между операцией, Финансами и Лояльностью. Он обязателен для Журнала, Продажи, Заказа и любых будущих рабочих контуров, где возникает расчёт.

## 1. Операция одна

Одна продажа / запись / заказ не разбивается на отдельные независимые операции по способам погашения.

Владелец факта расчёта — единая операция расчёта.

Она хранит минимум:
- `operationId`;
- источник: тип рабочего события и его id;
- рабочую дату/время;
- расчёт / сумму к погашению;
- человека, если он есть;
- четыре канала погашения;
- чаевые отдельно;
- состояние;
- связи с возвратами, отменой и корректировками;
- аудитную дату.

Журнал, Продажа, Заказ и другие рабочие контуры вызывают эту операцию, но не реализуют собственную финансовую механику.

## 2. Четыре канала погашения

У операции существуют четыре независимых канала:

1. `money` — Деньги: новые реальные деньги, физически поступающие сейчас;
2. `deposit` — Депозит: использование ранее внесённого остатка конкретного депозита;
3. `personalAccount` — Личный счёт: использование ранее внесённого денежного остатка без условий депозита;
4. `bonus` — Бонусы: использование бонусного номинала.

Каналы могут использоваться одновременно в одной операции.

Пример одной операции на 4 000:
- Деньги: 2 000;
- Депозит: 1 000;
- Личный счёт: 700;
- Бонусы: 300.

Это одна операция, а не четыре операции.

Инвариант операции:

`money + deposit + personalAccount + bonus = settlementApplied`

`settlementApplied` не может превышать остаток к погашению.

## 3. Чаевые

Чаевые не являются пятым способом погашения долга.

Они хранятся отдельно от четырёх каналов.

Для нового физического кассового движения:

`cashReceivedNow = money + tips`

Для погашения расчёта:

`settlementApplied = money + deposit + personalAccount + bonus`

Чаевые не уменьшают остаток к оплате услуги / товара / заказа.

## 4. Кто владеет, кто транслирует

### Единая операция расчёта

Владеет:
- идентичностью операции;
- суммой к погашению;
- четырьмя каналами;
- фактом полного / частичного погашения;
- возвратом;
- отменой;
- корректировкой;
- связью с исходным рабочим событием.

### Финансы

Не владеют общей операцией расчёта.

Финансы получают проекцию реальных денежных последствий:
- новые деньги → движение Кассы / ДДС;
- чаевые → денежное движение;
- возврат реальных денег → денежный расход / возврат.

Использование Депозита, денежного остатка Личного счёта и Бонусов не создаёт повторного нового кассового прихода в момент использования.

### Лояльность

Не владеет общей операцией расчёта.

Каждый инструмент Лояльности владеет только собственными правилами и остатком:
- Депозит проверяет допустимость и уменьшает / восстанавливает остаток конкретного депозита;
- Личный счёт проверяет и уменьшает / восстанавливает денежный остаток;
- бонусный номинал проверяет срок жизни партий и уменьшает / восстанавливает бонусы;
- Сертификат / Абонемент владеют своими правами и ограничениями, но не становятся отдельной общей оплатой.

Все результативные движения Лояльности обязаны ссылаться на `operationId` единой операции расчёта.

## 5. Атомарность

Создание / возврат / отмена / корректировка одной операции выполняются как единая серверная транзакция.

Нельзя допускать состояния:
- деньги записались, а бонусы не списались;
- бонусы списались, а операция не создалась;
- депозит восстановился, а возврат не записался;
- операция удалена, а её движения Лояльности остались сиротами.

При ошибке любого канала вся операция должна откатываться.

## 6. Paid / due

Состояние оплаты нельзя определять только по кассовому ledger.

Оплачено по операции:

`paid = money + deposit + personalAccount + bonus - reversedChannels`

Остаток:

`due = planTotal - paid`

Касса отвечает только на вопрос о реальных денежных движениях. Она не является источником истины для полного статуса погашения.

## 7. ДДС / Excel

Каждая единая операция расчёта выгружается отдельной строкой.

Обязательные отдельные колонки:
- `Деньги`;
- `Депозит`;
- `Личный счёт`;
- `Бонусы`.

Чаевые сохраняются отдельной колонкой.

Нельзя заменять четыре канала одной колонкой `Сумма`, если это приводит к потере происхождения погашения.

Для смешанной операции все использованные каналы находятся в одной строке одной операции.

Возврат / отмена сохраняет разложение по тем же каналам, чтобы история и аудит сходились.

## 8. Корректировка и возврат

Корректируется единая операция, а не независимые копии её каналов.

Система сначала определяет новое канальное разложение операции, затем в одной транзакции:
- корректирует денежную проекцию;
- корректирует остатки Депозита / Личного счёта / Бонусов;
- сохраняет аудитную связь с исходной операцией.

При возврате система хранит, какая часть возврата относится к каждому из четырёх каналов.

## 9. UI

Рабочий контур показывает один расчёт и один сценарий оплаты.

Shared payment UI управляет одной операцией и её четырьмя каналами. Нельзя создавать отдельные локальные формы оплаты для Журнала, Продажи, Заказа или Лояльности.

Финансы и Лояльность показывают свои проекции одной операции в своих существующих UI-примитивах.

## 10. Запреты

Запрещено:
- создавать отдельную родительскую payment-операцию на каждый канал;
- делать Бонусы псевдокошельком Кассы;
- считать использование Депозита / Личного счёта новым кассовым приходом;
- считать `paid/due` только по FinanceLedgerEntry;
- позволять рабочему контуру самостоятельно менять остатки Лояльности;
- иметь несколько независимых runtime-владельцев одной оплаты;
- выгружать смешанную операцию так, что происхождение погашения теряется.
